# 报告解析企业级实现方案 V0（检修结构化 · LangGraph · 版面+OCR 前置）

> **定位**：在**不替换、不降级**现网「检修报告结构化提取」主链路的前提下，新增 **V0 企业级解析管线**——将 **预处理 → 版面分析/OCR → 结构化重组 → 单阶段 LLM 语义组装 → 规则后处理** 显式编排；大模型仅承担**最后一环**，以降低输出波动、提升可审计性。  
> **策略**：V0 与现接口 **长期并存**，以指标达标为切换前提；本文档为 **实现级方案**（目录、接口、状态机、开源选型、配置与风险），供研发与评审落地。

---

## 0. 已确认需求清单（本轮基线）

| 编号 | 事项 | 确认结论 |
|------|------|----------|
| 1 | 输入类型 | V0 **仅支持**与现网相同的 `source_type`（`docx`/`doc`/`pdf`/`markdown`/`md`/`text`/`txt`/`html`），不新增 `image/png` 等独立类型；**扫描类 PDF 仍归类为 `pdf`**，由内部管线分支处理。 |
| 2 | 第一期能力边界 | **已锁定**：**PaddleOCR + PP-StructureV3（PaddleX）** 作为唯一版面+OCR 引擎栈（原 §4.1 组合 A）；**必须**以 **仓库根目录独立部署工程** 交付，目录与编排风格 **参照 `mineru-deploy/`**（见 §4.2～§4.4），与「仅 LangGraph、无独立容器服务」区分。 |
| 3 | HTTP 路径 | 固定 **`/inspection-extract-v0/**`**，**镜像**现网：`upload`、`run`、`run/async`、`jobs/*` 等语义等价路由。 |
| 4 | 数据模型 | **V0 独立**请求/响应（及异步 Job 相关模型），在 **Trace / Metrics** 上增加 **V0 专用可选字段**（阶段耗时、OCR 引擎标识、低置信度/需复核标记等）；现网模型不改。 |
| 5 | 异步与存储 | V0 异步 **复用** `INSPECT_EXTRACT_ASYNC_JOBS_DIR` 与 **Redis 取消键前缀策略**；通过 **子目录或 `job_meta.pipeline=v0`** 区分任务，避免任务混跑逻辑冲突。 |
| 6 | LangGraph 运行时 | **FastAPI 进程内**发起；**异步 + worker 线程** 与现检修异步消费模式对齐；图执行要求 **可 checkpoint**（LangGraph Checkpointer），支持长跑断点续跑。 |
| 7 | LLM 形态 | V0 **单阶段 LLM**（相对现网 parse/classify/repair 多阶段）；提示词与评测需 **独立重写**（`inspection_extract_v0_*`）。 |
| 8 | 上线策略 | V0 与现接口 **并存长期**，以离线评测 + 线上影子指标 **达标后再评估**是否切换主链路（本文不绑定具体阈值，由后续指标文档定义）。 |

## 1. 与现网能力的关系（并存原则）

### 1.1 保留范围（不得破坏）

- **路由前缀**：`/inspection-extract/*` 行为、模型、配置、默认 `pipeline_version` 等均保持现网契约。
- **核心代码路径**：`app/api/inspection_extract.py`、`app/services/inspection_extract_service.py`、`app/services/inspection_extract_llm_orchestrator.py`、`app/inspection_v2/*`、`configs/prompts.yaml` 中 `inspection_extract*` 等 **继续服务现网**。

### 1.2 V0 新增范围（建议物理隔离）

| 层级 | 建议路径/命名 |
|------|----------------|
| API | `app/api/inspection_extract_v0.py`，`router` 挂载 `prefix="/inspection-extract-v0"` |
| 模型 | `app/models/inspection_extract_v0.py`（`InspectionExtractV0Request` / `InspectionExtractV0Response` / `InspectionExtractV0Trace` / `InspectionExtractV0JobMetrics` 等） |
| 服务 | `app/services/inspection_extract_v0_service.py`（提交异步、读状态、取消与现逻辑对齐） |
| LangGraph | `app/inspection_extract_v0/graph/`：`state.py`、`checkpointer.py`、`builder.py`、`nodes/*.py` |
| 版面/OCR 适配层 | `app/inspection_extract_v0/vision/` 或 `layout_ocr/`（封装对外部进程的调用与版本上报） |
| 提示词 | `configs/prompts.yaml` 增加 `inspection_extract_v0_extract`（及可选 `inspection_extract_v0_system`）；或独立 YAML + 注册加载（二选一，见 §8） |
| 配置 | `app/core/config.py` 增加 `InspectionExtractV0Config`（模型路径、设备、超时、是否启用各子引擎等） |
| **版面+OCR 容器工程（新建）** | 仓库根目录 **`paddleocr-layout-deploy/`**（与 `mineru-deploy/` **同级**）：完整容器化交付，见 §4.2 |

### 1.3 工程风格与可维护性（与项目整体一致）

实现 V0 时，须与现网检修、MinerU、RAG 等模块保持同一套工程习惯，便于评审与运维：

- **接口层（FastAPI）**  
  - 路由模块顶部保留 **模块级 docstring**（职责、鉴权、与现网路径对照）。  
  - 每个 `@router.*` 使用 **`summary` / `description` / `responses`**：与 `app/api/inspection_extract.py` 同级粒度说明 **入参（含 multipart 字段名）**、**出参 Pydantic 模型**、**常见错误码**。  
  - `response_model`、必要时 `response_model_exclude` 与现网对齐策略一致。

- **数据模型（Pydantic）**  
  - `Field(..., description="...")` **中英可读**、与 OpenAPI 展示一致；枚举与 `source_type` 校验方式对齐 `app/models/inspection_extract.py`。  
  - V0 专用 Trace/Metrics 字段一律 **`Optional`** 或默认值，避免破坏「可选扩展」语义。

- **日志**  
  - 统一 `from app.core.logging import get_logger` → `logger = get_logger(__name__)`。  
  - 业务日志 key 建议带前缀：`inspection_extract_v0`（如 `inspection_extract_v0 layout_ocr_ms=...`），关键阶段 **INFO**，失败 **WARNING/ERROR** 带 `job_id` / `user_id`（脱敏规则与现网一致）。  
  - 禁止在热路径打印整页 OCR 原文；大对象长度参照现网 `INSPECT_EXTRACT_LOG_*` 截断策略。

- **代码与包注释**  
  - 新建包 `app/inspection_extract_v0/`、`app/api/inspection_extract_v0.py` 等须有 **包/文件头说明**（职责、依赖外部服务、配置项索引）。  
  - LangGraph 节点函数：**简短 docstring** 说明输入状态字段、输出状态字段、是否可重试。

### 1.4 契约对齐说明

- **入参/出参**：字段语义 **尽量与现网 `InspectionExtractRequest` / `InspectionExtractResponse` 对齐**；V0 独立模型便于 **扩展 Trace/Metrics** 而不污染现网 JSON Schema。
- **上传**：V0 `POST /inspection-extract-v0/upload` 可 **复用** 现 `InspectionExtractService.upload_file` 实现，避免重复 MinIO 逻辑。

> 上文 **§1.3** 为编码规范约束；评审 PR 时与 OpenAPI 生成结果一并核对。

## 2. V0 总体处理流程（五阶段 + LangGraph）

```mermaid
flowchart TB
  subgraph P0[接入与路由]
    A[POST /inspection-extract-v0/run|async] --> B[解析 source_type 与 content 来源]
  end

  subgraph P1[预处理 无LLM]
    B --> C{介质分支}
    C -->|pdf 扫描倾向| C1[图像预处理: 纠偏/去噪/对比度 可选]
    C -->|pdf 文本层充足| C2[跳过或弱预处理]
    C -->|docx| C3[解压与页面渲染可选 或 直接结构流]
    C -->|md/txt/html| C4[轻量清洗]
  end

  subgraph P2[Paddle PP-Structure + PaddleOCR 容器]
    C1 --> D[版面检测: 区域与阅读顺序]
    C2 --> D
    C3 --> D
    C4 --> D
    D --> E[OCR / 表格结构: 字级框+类型]
  end

  subgraph P3[结构化重组 无LLM]
    E --> F[生成统一中间表示 IRT]
    F --> G[表格网格/HTML 或 JSON 拓扑 + 置信度]
  end

  subgraph P4[单阶段 LLM]
    G --> H[Prompt: IRT + Schema + Few-shot]
    H --> I[一次 LLM 调用输出 records]
  end

  subgraph P5[后处理与验证]
    I --> J[Pydantic 校验 + 规则归一 + 阈值]
    J --> K[输出 + Trace/Metrics 填充]
  end
```

**IRT（Intermediate Representation for Tables）建议最小字段**（实现时细化）：

- 页面级：`page_no`、页面尺寸、旋转角。
- 块级：`block_id`、`type`（title/text/table/figure）、`bbox`、`reading_order`。
- 表级：`table_id`、`cells[][]`（文本、`cell_bbox`、合并信息 `rowspan/colspan`、`ocr_confidence`）。
- 全局：`ocr_engine`、`layout_engine`、`pipeline_build` 版本号（写入 Trace）。

## 3. LangGraph 编排设计要点

### 3.1 State（示意）

- 输入：`user_id`、`session_id`、`content`、`source_type`、`strict`、`return_evidence`、V0 专用 `prompt_version` 等。
- 中间：`artifact_dir`（可选）、`preprocess_meta`、`layout_result_path`、`ocr_result_path`、`irt_path`、`llm_raw_path`、`records_raw`、`errors[]`、`retry_counts`。
- 输出：`InspectionExtractV0Response` 构件、`trace`、`summary`。

### 3.2 节点（建议最小集合）

| Node | 职责 | LLM |
|------|------|-----|
| `ingest` | 下载/落盘、MIME 校验、与现网一致的 URL/路径处理 | 否 |
| `preprocess` | 扫描 PDF 渲染页图、纠偏/去噪（可配置开关） | 否 |
| `layout_ocr` | 调用 **`paddleocr-layout-deploy`** 暴露的 HTTP API，拉取版面+表格+OCR JSON | 否 |
| `build_irt` | 阅读顺序排序、表网格重建、合并单元格还原 | 否 |
| `llm_extract_once` | 单阶段：IRT + 片段证据 → 符合 Schema 的 `records` | **是** |
| `validate_normalize` | 复用或对齐现网 `InspectionRecord` 规则集；低置信打标 | 否 |
| `finalize` | 组装响应、写 metrics、异步落盘 | 否 |

**条件边**：`source_type` 与「是否扫描倾向」决定 preprocess 深度；`layout_ocr` 失败可 **重试节点**（限次）或降级策略（需产品确认，默认 **失败即报错** 以保持「强制版面」口径）。

### 3.3 Checkpointer 与断点续跑

- **持久化**：使用 LangGraph 支持的 **Sqlite / Postgres** 等 Checkpointer（推荐 **Postgres** 若已有中间件；否则 **按 job 子目录的 Sqlite** 与 `INSPECT_EXTRACT_ASYNC_JOBS_DIR` 共存，路径如 `{job_dir}/langgraph_checkpoint.sqlite`）。
- **异步 worker**：与现网一致由线程消费队列；**每个 job 一次 graph.invoke/ainvoke**，在节点边界 `interrupt` 前写入 checkpoint（或由 LangGraph 自动持久化，取决于 checkpointer 绑定方式）。
- **恢复**：`job_meta` 记录 `thread_id`（与 `job_id` 绑定）；重启 worker 后以相同 `thread_id` **resume**。

### 3.4 与「单阶段 LLM」的衔接

- 现网多阶段提示词 **不直接复用**；V0 的 `inspection_extract_v0_extract` 必须明确：
  - 输入为 **IRT 摘要 + 关键表片段**（控制 token）；
  - 输出 **仅 JSON**（`records` 数组），字段与现网 `InspectionRecord` 对齐；
  - **禁止**让模型承担 OCR 纠错以外的「编造表格数字」——数字优先来自 IRT，LLM 做 **映射、缺省、分类与证据句**。

## 4. 版面+OCR 技术栈（已锁定）与容器化交付

> **本期唯一选型**：**PaddleOCR + PP-StructureV3（PaddleX）** — 版面区域、表格结构、中文 OCR 一体化；**Apache 2.0**，可私有化。  
> **交付要求**：在仓库根目录 **`paddleocr-layout-deploy/`** 实现 **与 `mineru-deploy/` 同级的完整容器化部署**（非「仅 Dockerfile 片段」）；主应用通过 **HTTP** 调用该服务，不在 FastAPI 进程内直接 `import paddle`。

### 4.1 引擎职责边界

| 能力 | 实现 | 说明 |
|------|------|------|
| 版面 | PP-Structure / 版面分析模块 | 区域类型、阅读顺序、bbox；输出需可映射到 IRT `block` |
| 表格 | 表格识别分支 | 单元格文本、合并格、置信度；为 **IRT `cells[][]`** 主来源 |
| OCR | PaddleOCR | 中文为主；扫描页、渲染 PDF 页图为输入时的字级识别 |
| 对外形态 | **独立 HTTP API 容器** | 与 `mineru-api` 类似，供 `app/inspection_extract_v0/vision/` 薄客户端调用 |

### 4.2 部署工程：目录与文件清单（须对齐 `mineru-deploy/` 风格）

**物理路径**：`<repo_root>/paddleocr-layout-deploy/`（与 `<repo_root>/mineru-deploy/` **并列**）。

| 交付物 | 参照 `mineru-deploy/` 的对应物 | 说明 |
|--------|-------------------------------|------|
| `README.md` | `mineru-deploy/README.md` | 含：**目录结构**、**前提条件**、**CPU/GPU 两套 compose**、**在线/离线模型**、**构建启动命令**、**验证 `/health` 与 `/docs`** |
| `Dockerfile.cpu` / `Dockerfile.gpu` | `Dockerfile.cpu` / `Dockerfile.gpu` | 多阶段构建、国内 `PIP_INDEX_URL` build-arg、非 root（可选）与现网安全策略对齐 |
| `docker-compose.yml` | `docker-compose.yml` | 默认 **CPU** 兼容入口；`ports` 映射 `${PADDLE_LAYOUT_PORT:-8010}:8000` 等 |
| `docker-compose.cpu.yml` / `docker-compose.gpu.yml` | 同名 | GPU 版 `deploy.resources.reservations.devices` 或 `runtime: nvidia` 等与 MinerU GPU 栈一致 |
| `docker/entrypoint.sh` | `docker/entrypoint.sh` | 创建 `/io/.cache`、`/io/layout-output` 等；离线模式下检查模型挂载路径 |
| `.env.example` | `.env.example` | **必选**：模型卷、IO 卷、端口、设备模式、线程数、离线开关；**命名前缀**建议 `PADDLE_LAYOUT_*` / `PPSTRUCT_*`，避免与 `MINERU_*` 混淆 |
| `healthcheck` | `mineru-deploy` 中 `curl .../health` | `interval`/`timeout`/`retries` 与现网同级，便于编排拉起顺序 |

**网络与主应用**：与 `mineru-api` 相同模式 —— `models_app` 与 `paddleocr-layout-api`（服务名示例）置于 **同一 Docker network** 时，主应用配置 `INSPECT_EXTRACT_V0_LAYOUT_OCR_ENDPOINT=http://paddleocr-layout-api:8000`（端口以 compose 为准）。

### 4.3 HTTP API 契约（实现 PR 中定稿并写入本 README）

须在 `paddleocr-layout-deploy/README.md` 与 OpenAPI 中同时固定，建议最小能力：

- **输入**：`multipart` 上传 PDF/图像 **或** JSON `{ "file_path": "/io/..." }`（与 MinerU 共享只读 IO 卷时可选）。  
- **输出**：JSON，含 `engine_version`、`pages[]`、`blocks[]`（`type`/`bbox`/`text`/`confidence`）、`tables[]`（行/列/合并信息/单元格置信度）。  
- **错误**：4xx 参数错误、413 过大、500 引擎异常；**超时**由主应用 `httpx` 超时与 compose 内 `gunicorn/uvicorn` timeout 对齐。

主应用在 `InspectionExtractV0Trace` 中写入 **`layout_engine`** / **`ocr_engine`** 字符串（含 `engine_version`）。

### 4.4 与 LangGraph `layout_ocr` 节点对接

- `app/inspection_extract_v0/vision/layout_ocr_client.py`（示例名）：封装 **请求构建、重试、超时、响应校验**；日志键 `inspection_extract_v0 layout_ocr_*`。  
- 节点失败：默认 **不静默降级**（符合「强制版面」）；可配置 **限次重试** 仅针对网络抖动，不对 OCR 结果做「换引擎」降级（本期无二引擎）。

### 4.5 docx / 文本类 PDF 分支（与引擎协同）

- **原生 docx**：仍以 **python-docx / docx_v2 序列化** 为主生成结构流；**含扫描插入页**的 docx 可将对应页 **渲染为图** 后送 **4.3** 服务，IRT 标注 `source_mixed=docx+ocr`。  
- **文本层充足 PDF**：`pypdf` 文本可选；**表格以矢量/文本存在**时以解析结果为主；**表格以位图存在**则必须走 **4.3**。

### 4.6 第一期验收建议

在扫描 PDF、「Word 内嵌扫描表」样本上，先验收 **IRT 表格行列与置信度**，再放开单阶段 LLM 灰度。

### 4.7 本期不采用的方案（记录）

原方案文档中的 **组合 B（LayoutParser+Tesseract）**、**docTR / Surya / Marker** 等 **本期不纳入交付**；若 POC 发现 Paddle 栈在特定版式上不达标，另开评审变更 §0/§4，不在本期 silently 切换。

## 5. HTTP 与异步语义（对齐现网）

### 5.1 路由镜像（建议一一对应）

| 现网 | V0 |
|------|-----|
| `POST /inspection-extract/upload` | `POST /inspection-extract-v0/upload` |
| `POST /inspection-extract/run` | `POST /inspection-extract-v0/run` |
| `POST /inspection-extract/run/async` | `POST /inspection-extract-v0/run/async` |
| `GET /inspection-extract/jobs/{id}` | `GET /inspection-extract-v0/jobs/{id}` |
| `GET .../chunks`、`GET .../chunks/{work_idx}` | 同结构（若 V0 单阶段仍按「页/表块」落盘，可保留 chunk 语义；**字段名保持一致**） |
| `DELETE .../jobs/{id}` | 同路径语义；**复用 Redis 取消键命名空间**（见下） |

### 5.2 异步目录与取消键（复用 + 隔离）

- **目录**：仍使用 `INSPECT_EXTRACT_ASYNC_JOBS_DIR`；每个 `job_id` 下：
  - `request.json` 增加 **`pipeline: "v0"`**；
  - `job_meta.json` 增加 **`langgraph_thread_id`**、各阶段耗时汇总；
  - `checkpoints/` 或 `langgraph_checkpoint.sqlite` 存 Checkpointer。
- **Redis 取消**：键模式与现网一致时，须在 value 或 hash 字段中写入 **`pipeline=v0`**，worker 仅处理本 pipeline 的 job，避免误读（若现网键仅含 `job_id`，则 **v0 使用独立 key 前缀** `inspection:extract:v0:jobs:cancel:{id}` 更稳——**实现前需与现网 cancel 逻辑做一次代码级对齐评审**）。

## 6. V0 独立模型与 Trace / Metrics 扩展

### 6.1 请求体（示意字段，与现网对齐）

- 与 `InspectionExtractRequest` **同名字段**优先：`user_id`、`session_id`、`content`、`source_type`、`doc_name`、`strict`、`return_evidence`。
- V0 扩展（可选）：`prompt_version`、`layout_profile`（`aggressive`/`lite`）、`ocr_lang` 等。

### 6.2 响应体

- 顶层仍建议：`ok`、`records`（类型对齐 `InspectionRecord` 或共享同一 Pydantic 模型）、`summary`、`trace`。
- **`InspectionExtractV0Trace`**（扩展现有语义，**不修改** `InspectionExtractTrace`）建议包含：
  - `parse_route` 或等价 **`irt_source`**（`native_docx` / `pypdf_text` / `rendered_pdf_ocr` 等）；
  - `llm_model`、`prompt_version`；
  - **`stage_latency_ms`**：`preprocess`、`layout_ocr`、`build_irt`、`llm`、`postprocess`；
  - **`ocr_engine`** / **`layout_engine`**（字符串，含版本）；
  - **`low_confidence`**：布尔或计数；**`review_flags`**：字符串列表（如 `table_cell_conf_lt_0.7`）。

### 6.3 Job Metrics（异步轮询）

- 与 `InspectionExtractJobMetrics` 对齐基础上增加 V0 字段：`irt_build_ms`、`ocr_engine`、`layout_engine`、`llm_tokens_est` 等（均为可选）。

## 7. 单阶段 LLM：提示词与评测

### 7.1 提示词原则

- **输入**：压缩后的 IRT（表头行、合并信息、关键数值格 + 置信度），必要时附 **原文片段**（非全量 OCR 原文）。
- **输出**：严格 JSON Schema；**数值字段优先引用 IRT 中的单元格**；`evidence` 引用 IRT `block_id` 或页码+bbox 文本片段。
- **温度**：建议沿用现网检修独立 `INSPECT_EXTRACT_LLM_TEMPERATURE` 的 V0 配置项（如 `INSPECT_EXTRACT_V0_LLM_TEMPERATURE`），默认偏低。

### 7.2 评测集

- **结构化指标**：字段完备率、枚举合法率、与标注 JSON 的 **cell-level 对比**（在 IRT 对齐前提下）。
- **稳定性指标**：同输入多次采样的一致性（可定义 δ 阈值）。
- **回归**：现网黄金集 + V0 新增「扫描表/斜线表/跨页表」集。

## 8. 配置与环境变量（建议草案）

下列为 **主应用**（`models_app`）侧建议名；**版面容器**侧变量以 `paddleocr-layout-deploy/.env.example` 为准（风格对齐 `mineru-deploy/.env.example`）：

- `INSPECT_EXTRACT_V0_ENABLED`：总开关。
- `INSPECT_EXTRACT_V0_LAYOUT_OCR_ENDPOINT`：版面+OCR 服务 **HTTP 根地址**（如 `http://paddleocr-layout-api:8000`，与 compose 服务名一致）。
- `INSPECT_EXTRACT_V0_LAYOUT_OCR_TIMEOUT_SECONDS`：调用版面服务总超时（含大 PDF）。
- `INSPECT_EXTRACT_V0_CHECKPOINTER_URL`：如 `postgresql://...` 或 `sqlite:///{job_dir}/...`。
- `INSPECT_EXTRACT_V0_LLM_*`：超时、`max_tokens`、温度等。
- `INSPECT_EXTRACT_V0_PROMPT_VERSION`：默认提示词版本。

**部署目录环境变量（容器工程内）**：须包含与 MinerU 同类的 **`_MODELS_HOST_PATH` / `_IO_HOST_PATH`**、**`PIP_INDEX_URL`**、**离线 HuggingFace/ModelScope 开关** 等，便于 CI 与离线机房复用同一套运维习惯。

## 9. 风险与缓解

| 风险 | 缓解 |
|------|------|
| 版面+OCR 延迟高 | 异步默认；同步 `/run` 限制文档大小与超时；**主应用** `INSPECT_EXTRACT_V0_LAYOUT_OCR_TIMEOUT_SECONDS` 与容器 **worker timeout** 对齐 |
| 依赖服务 OOM / 启动失败 | 独立容器、限并发、队列隔离；**compose 资源上限**参照 `mineru-deploy` 的 `cpus`/`mem_limit` 写法 |
| 与 `mineru-deploy` 运维习惯不一致 | **CR  checklist**：目录、`.env.example` 键风格、`healthcheck`、README 章节是否与 MinerU 同级 |
| IRT 与 LLM 字段对不齐 | 强 Schema + 自动重试（限次）+ `review_flags` |
| Checkpointer 与 job 目录一致性 | `job_meta` 原子写；恢复时校验 sqlite/pg 存在性 |
| 与现网取消键冲突 | 评审 §5.2，必要时 **v0 独立 cancel 前缀** |

## 10. 实现优先级（企业级交付顺序）

> 下列每一步均为 **可合并 PR、可验收、可上线** 的完整实现；**禁止**合并「空路由 / 未实现的 TODO 节点 / 无健康检查的容器」。顺序体现 **依赖先后**：版面服务先于主链路联调。

### Step 1 — `paddleocr-layout-deploy` 可投产服务

- **交付**：`Dockerfile.cpu` / `Dockerfile.gpu`、`docker-compose.{yml,cpu.yml,gpu.yml}`、`docker/entrypoint.sh`、`.env.example`、`README.md`（构建/离线模型/健康检查/排障）；FastAPI（或等价）实现 **§4.3** OpenAPI：`/health`、`/docs`、主推理路由；请求体大小限制、进程级超时、**结构化 JSON 错误体**；`engine_version` 字段写入响应。  
- **验收**：`docker compose up` 后 `curl` 通过；CPU/GPU 两套各有一份 CI 或文档内「最小构建命令」；镜像内 **无开发占位路由**。

### Step 2 — 主应用配置与 V0 数据模型

- **交付**：`InspectionExtractV0Config` + `app/app-deploy/.env.example` 键；`app/models/inspection_extract_v0.py`（Request/Response/Trace/JobMetrics/Chunk 响应），**全部 `Field(description=...)`**；`main.py` 注册路由在 **开关为真** 时挂载。  
- **验收**：OpenAPI 生成与现网 `/inspection-extract` 字段对照表一致（扩展字段单独列出）；**未开开关时零行为变化**。

### Step 3 — 版面 HTTP 客户端（生产级）

- **交付**：`app/inspection_extract_v0/vision/layout_ocr_client.py`：`httpx` 异步、连接池、**可配置重试（仅 idempotent GET/health）**、POST **单次超时 + 总超时**、4xx/5xx/JSON 解析失败映射为 **应用内异常类型**；日志 `inspection_extract_v0 layout_ocr_*`；可选 **上传体积上限** 与现网 MinIO 策略对齐。  
- **验收**：对 Step 1 服务 **契约测试**（pytest + 录制的 golden response 或 testcontainer）。

### Step 4 — IRT 构建管线（无 LLM）

- **交付**：`ingest`（路径/URL 下载与落盘、MIME）、`preprocess`（PDF 渲染页图分支）、`layout_ocr`（调 Step 3）、`build_irt`（Pydantic 模型固定 IRT schema、合并格与置信度写入、**版本号**）；单元测试 + **固定样本 JSON** 回归；大结果 **原子写** `job_dir/artifacts/irt.json`。  
- **验收**：IRT JSON 通过 schema 校验；与 Step 1 真实服务跑通 **至少一类** 扫描 PDF 与一类 docx 嵌入图。

### Step 5 — LangGraph 图 + Checkpointer

- **交付**：`state.py`、`builder.py`、`nodes/*.py`；编译图；**Sqlite 或 Postgres checkpointer** 与 `job_id`/`thread_id` 绑定写入 `job_meta`；节点失败映射 `job status=failed` + `error_code`；**协作取消**在节点边界检查（与现网 cancel 评审结论一致的前缀或字段）。  
- **验收**：异步任务 **kill 进程后重启 worker** 可从 checkpoint 续跑至完成或干净失败；无「半写」损坏 `job_meta`。

### Step 6 — 单阶段 LLM + 后处理闭环

- **交付**：`configs/prompts.yaml` 中 `inspection_extract_v0_extract`（及 registry 加载）；`llm_extract_once` 节点；**严格 JSON 解析 + 一次限次自动重试**（仅 LLM 调用）；`validate_normalize` 复用/对齐 `InspectionRecord` 与现网阈值逻辑；`review_flags` / `low_confidence` 写入 Trace。  
- **验收**：黄金集 **结构化字段合法率** 达标线（由团队在评测文档写死）；同步 `/run` 在超时配置下 **可预测失败**（不挂死）。

### Step 7 — API 与异步任务全镜像

- **交付**：`app/api/inspection_extract_v0.py` 全路由；`inspection_extract_v0_service.py`（同步、异步提交、chunk 列表、chunk 内容、取消）；**复用** `INSPECT_EXTRACT_ASYNC_JOBS_DIR` 与 Redis；`job_meta.pipeline=v0`；metrics 与现网 **独立计数器前缀** `inspect_extract_v0_*`。  
- **验收**：与现网 **同套集成测试模式**（新目录 `tests/test_inspection_extract_v0_*.py`）覆盖 upload/run/async/jobs/cancel；**与现网 jobs 互不串单**。

### Step 8 — 可观测、安全与发布门禁

- **交付**：日志字段（`job_id`、`stage`、`latency_ms`）；Prometheus `inspect_extract_v0_*`（请求数、失败原因、分阶段耗时）；**运维 Runbook**（资源、回滚、磁盘）；版面镜像 **CVE 扫描**结论写入 `paddleocr-layout-deploy/README.md`。  
- **验收**：压测记录模板 + `INSPECT_EXTRACT_V0_ENABLED` 灰度说明；首发 PR 附 Runbook 链接。
