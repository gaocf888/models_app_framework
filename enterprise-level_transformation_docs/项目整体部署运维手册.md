# 项目整体部署运维手册

> **文档性质**：面向运维、交付与集成方的**部署与日常运维**指南，覆盖容器化多栈部署顺序、必要环境变量、启动验证、备份与排障要点。  
> **适用范围**：本仓库 **大模型在线应用** 能力面（FastAPI 应用 + vLLM + EasySearch + Redis 等）；小模型训练与 YOLO 离线工程不在本文范围。  
> **详细参数**：完整变量说明见 `app/app-deploy/.env.example`；业务能力关键配置见本文 **§5**（对照 [`系统整体技术实现-简版.md`](./系统整体技术实现-简版.md)）；快速上线步骤见 `app/app-deploy/README-simple-deploy.md`。

**版本**：与仓库当前部署结构对齐（2026-06）

## 1. 部署架构概览

### 1.1 组件清单

| 组件 | 部署目录 | 容器/服务名 | 是否必需        | 说明 |
|------|----------|-------------|-------------|------|
| 大模型推理 | `vllm-deploy/` | `vllm-service` | **是**       | OpenAI 兼容 `/v1/chat/completions` |
| 向量 + 全文库 | `rag_db-deploy/` | `rag-easysearch` | **是**       | EasySearch（ES API 兼容），RAG 与索引元数据 |
| 应用 API | `app/app-deploy/` | `models-app` | **是**       | FastAPI：客服、分析、NL2SQL、RAG 运维等 |
| 会话 / 队列 | `app/app-deploy/` | `models-app-redis` | **生产建议**    | 多轮会话、异步任务队列 |
| 对象存储 | `app/app-deploy/` | `models-app-minio` | 按场景生产建议     | 检修上传、客服图片等 |
| PDF 扫描解析 | `mineru-deploy/` | `mineru-api` | 按知识文档类型生产建议 | 扫描件 PDF → Markdown |
| 版面 OCR 侧车 | `paddleocr-layout-deploy/` | `paddleocr-layout-api` | 可选          | 检修 V0（`/inspection-extract-v0`） |
| 图数据库 | `graphrag_db-deploy/` | `graph-neo4j` | 可选          | GraphRAG |
| 小模型 GPU | `app/app-deploy/` | `models-app-gpu` | 可选          | `--profile small-model-gpu`，`/small-model/*` |

### 1.2 推荐部署顺序

```
EasySearch → vLLM →（可选 MinerU）→（可选 Paddle 版面侧车）→（可选 Neo4j）→ 应用栈
```

各栈通过 **Docker 外部网络** 互联；应用 `docker-compose.yml` 已声明 `vllm-external`、`rag-external`、`mineru-external`、`paddle-layout-external` 等网络，网络名须与各子项目 `.env` 一致。

### 1.3 配置读取分层（重要）

| 消费者 | 读取方式 | 典型变量 |
|--------|----------|----------|
| **Docker Compose（宿主机）** | 解析 `docker-compose.yml` 中的 `${VAR}` | `APP_PORT`、`VLLM_DOCKER_NETWORK`、`REDIS_DATA_HOST_PATH`、模型宿主机路径 |
| **应用进程（容器内）** | `env_file: .env` 注入，由 `app/core/config.py` 的 `os.getenv` 读取 | `LLM_*`、`RAG_ES_*`、`REDIS_URL`、`DB_*`、`SERVICE_API_KEYS` |

> 修改业务配置后需 **重启 `models-app`**；修改 Compose 端口/卷路径后需 **`docker compose up -d`** 重建。

## 2. 环境要求

### 2.1 基础软件

- Docker 与 Docker Compose V2
- Linux 服务器推荐（生产）；Windows 可用于开发（Docker Desktop + WSL2）
- 内存：应用 + EasySearch + vLLM 合计建议 **≥ 32 GB**（视模型规模调整）
- 磁盘：模型权重、EasySearch 索引、日志与备份目录需单独规划（见第 8 节）

### 2.2 内核参数（EasySearch）

若 EasySearch 启动报 `vm.max_map_count` 过低：

```bash
# /etc/sysctl.conf 或 /etc/sysctl.d/99-easysearch.conf
vm.max_map_count=262144

sudo sysctl -p
sysctl vm.max_map_count
```

### 2.3 GPU 环境

- **vLLM / 小模型 GPU**：NVIDIA 驱动 + NVIDIA Container Toolkit（或国产卡对应厂商容器运行时）
- **沐曦等国产卡**：使用 `vllm-deploy` 中对应平台 compose overlay（`deploy.sh --platform mthreads` 等）

## 3. 分步部署

### 3.1 EasySearch（RAG 数据库）

```bash
cd rag_db-deploy
cp .env.example .env
# 编辑 .env：EASYSEARCH_PASSWORD、EASYSEARCH_DATA 等

docker compose --env-file .env -f docker-compose.easysearch.yml up -d
```

**首次设置 admin 密码**（若 401）：进入容器执行 `reset_admin_password.sh`，或通过 API 设置（见 `rag_db-deploy/README.md`）。

**验证**：

```bash
curl -k -u admin:你的密码 "https://127.0.0.1:9200/_cluster/health?pretty"
```

### 3.2 vLLM（大模型推理）

```bash
cd vllm-deploy
cp .env.example .env
# 编辑：BASE_IMAGE、VLLM_PLATFORM、MODEL_PRESET、MODEL_PATH、GPU 可见设备等

chmod +x deploy.sh
./deploy.sh
# 或指定平台：./deploy.sh --platform nvidia|mthreads|cambricon|ascend
```

**验证**：

```bash
curl -s "http://127.0.0.1:8000/health"
curl -s "http://127.0.0.1:8000/v1/models"
```

> `LLM_DEFAULT_MODEL`（应用侧）必须与 `config/models.yaml` 中对应预设的 `served_model_name` 一致。

### 3.3 MinerU（生产建议，扫描 PDF）

```bash
cd mineru-deploy
cp .env.example .env
docker network create mineru-stack || true
docker compose --env-file .env -f docker-compose.cpu.yml up -d
# GPU 环境可用 docker-compose.gpu.yml
```

应用侧需 `MINERU_ENABLED=true`，且 `MINERU_IO_HOST_PATH` 与 `app/app-deploy` 挂载目录一致。

### 3.4 Paddle 版面侧车（可选，检修 V0）

```bash
cd paddleocr-layout-deploy
cp .env.example .env
docker network create paddle-layout-stack || true
docker compose -f docker-compose.cpu.yml up -d --build
```

应用侧需 `INSPECT_EXTRACT_V0_ENABLED=true`，且 `INSPECT_EXTRACT_V0_LAYOUT_OCR_ENDPOINT=http://paddleocr-layout-api:8000`。

### 3.5 Neo4j / GraphRAG（可选）

```bash
cd graphrag_db-deploy
cp .env.example .env
docker compose -f docker-compose.neo4j.yml --env-file .env up -d
```

应用侧设置 `GRAPH_RAG_ENABLED=true` 及 `NEO4J_*` 变量，并确保 `GRAPH_DOCKER_NETWORK` 与 Neo4j 网络名一致。

### 3.6 应用栈（主服务）

```bash
cd app/app-deploy
cp .env.example .env
# 按第 4 节修改必要环境变量

# 部署前创建数据目录（Linux 示例）
sudo mkdir -p /aidata/data/{redis_data,minio_data,session_storage,inspect_extract_jobs}
sudo mkdir -p /aidata/models/{embeddings,reranker,llm}

# 核对外部网络名
docker network ls   # 确认 ai-stack、docker_vllm-network 等已存在

docker compose up -d --build
```

**沐曦 / 国产重排加速**（可选）：

```bash
cd app/app-deploy/docker-mx
cp ../.env .env
docker compose --env-file .env -f docker-compose-mx.yml up -d --build
```

**小模型 GPU**（可选）：

```bash
cd app/app-deploy
docker compose --profile small-model-gpu up -d --build
```

## 4. 必要环境变量配置

> 以下仅列 **上线必须确认** 的配置项。完整列表与高级调参见 `app/app-deploy/.env.example`。

### 4.1 配置方法

1. 进入 `app/app-deploy/`，复制模板：`cp .env.example .env`
2. 用编辑器修改 `.env`（**勿提交真实密钥到 Git**）
3. 生产环境可通过 CI/Secret 平台注入同名变量，效果与 `env_file` 相同
4. 修改后执行：`docker compose restart models-app` 或 `docker compose up -d --build`

### 4.2 鉴权（必配）

| 变量 | 说明 | 示例 |
|------|------|------|
| `SERVICE_API_KEYS` | 业务 HTTP 鉴权密钥，逗号分隔可轮换 | `key1,key2` |
| `SERVICE_API_KEY` | 单密钥写法（与上二选一） | `your_secret` |

**配置方法**：

- 请求头：`Authorization: Bearer <密钥>`
- 生成密钥（仓库根目录）：

```bash
# Linux / macOS
PYTHONPATH=. python -c "from app.auth.keygen import generate_service_api_key; print(generate_service_api_key())"
```

```powershell
# Windows PowerShell
$env:PYTHONPATH = (Get-Location).Path
python -c "from app.auth.keygen import generate_service_api_key; print(generate_service_api_key())"
```

> 未配置任何密钥时，业务路由返回 **503**。与 vLLM 的 `LLM_DEFAULT_API_KEY` 无关。

### 4.3 大模型 vLLM（必配）

| 变量 | 说明                                                                    | 示例 |
|------|-----------------------------------------------------------------------|------|
| `LLM_DEFAULT_MODEL` | 模型别名，须与 vLLM `served_model_name` 一致(vllm-deploy/config/models.yaml中 served_model_name) | `qwen2.5-vl-32b-instruct-awq` |

### 4.4 RAG / EasySearch（必配）

| 变量 | 说明 | 示例 |
|------|------|------|
| `RAG_VECTOR_STORE_TYPE` | 向量库类型 | `es` |
| `RAG_ES_HOSTS` | EasySearch 地址，逗号分隔 | `https://rag-easysearch:9200` |
| `RAG_ES_USERNAME` | 账号 | `admin` |
| `RAG_ES_PASSWORD` | 密码，须与 `rag_db-deploy/.env` 一致 | `ChangeMe_123!` |
| `RAG_ES_VERIFY_CERTS` | 自签证书通常为 `false` | `false` |

**索引相关**（一般保持默认即可）：

| 变量 | 说明                                   | 默认 |
|------|--------------------------------------|------|
| `RAG_ES_INDEX_NAME` | 物理索引前缀                               | `rag_knowledge_base` |
| `RAG_ES_INDEX_ALIAS` | 应用读写用的逻辑别名(逻辑索引名)                    | `rag_knowledge_base` |
| `RAG_ES_INDEX_VERSION` | 物理索引版本号，实际物理索引名为 `{NAME}_v{VERSION}` | `2` |
| `RAG_ES_AUTO_MIGRATE_ON_START` | 启动时是否自动建当前版本物理索引，并将 alias 切到该版本      | `true` |

**`RAG_ES_AUTO_MIGRATE_ON_START` 说明**：应用读写走 alias（门牌号），数据存于带版本号的物理索引（如 `rag_knowledge_base_v2`）。设为 `true` 时，启动会自动创建缺失的物理索引并将 alias 指向当前 `RAG_ES_INDEX_VERSION`；**不会**复制旧版数据、**不会**删除旧索引。升级 `INDEX_VERSION` 后须重新摄入或 reindex。设为 `false` 则索引切换完全由运维脚本或管理 API 手工控制。

**RAG 知识库 namespace（按业务能力摄入）**：

| namespace | 用途 | 依赖业务 |
|-----------|------|----------|
| （业务知识库） | 客服、综合分析业务 RAG | `/chatbot`、`/analysis` |
| `nl2sql_schema` | 表结构、字段、表间关系 | NL2SQL、综合分析取数 |
| `nl2sql_biz_knowledge` | 业务口径、字段语义文档 | NL2SQL、综合分析规划 |
| `nl2sql_qa_examples` | 问法 → 标准 SQL 问答对 | NL2SQL、综合分析 QA 回放 |

## 5. 业务能力关键配置

> 本节与 [`系统整体技术实现-简版.md`](./系统整体技术实现-简版.md) 对齐，说明各业务模块**上线时需确认**的环境变量与知识库前置条件。  
> **原则**：`.env.example` 当前默认值可直接用于大多数场景；非定制报告模板、非切换 synthesis 策略时**不必修改**。

### 5.1 NL2SQL 基座（多业务共用）

NL2SQL 为 **综合分析取数、智能客服问数、看图诊断 NL2SQL 臂** 的公共能力，部署时需同时满足：

| 类别 | 配置 / 前置 | 说明                                                                                                                                        |
|------|-------------|-------------------------------------------------------------------------------------------------------------------------------------------|
| **连接** | §4.6 `DB_*` / `DB_URL` | 业务库只读执行目标                                                                                                                                 |
| **知识库** | 摄入 `nl2sql_schema`、`nl2sql_biz_knowledge`、`nl2sql_qa_examples` | 表结构认知 = RAG + 数据库反射；新项目 `qa_examples` 可经半自动录入接口维护                                                                                         |
| **表域白名单** | `ANALYSIS_NL2SQL_TABLE_SCOPE_DEFAULT` | 允许进入提示词/校验的表集合；**库表变更后须同步更新**                                                                                                             |
| **问句范围解析** | `NL2SQL_INTENT_PARSE_MODE` | `rule`（默认，程序规则解析机组/受热面/管排等）\  **解析范围内容变化须同步更新对应 规则程序**                                                                                    | `llm` \| `rule_with_llm_fallback`；`llm` 时使用 `configs/prompts.yaml` → `nl2sql_scope_parse` |
| **范围 SQL 改写** | `NL2SQL_SCOPE_SQL_REWRITE_ENABLED` | 看图诊断-缺陷识别/泄爆分析强烈依赖，默认 `true` **同上，范围内容变化需同步更新 重写规则**                                                                                      |
| **QA 槽位回放** | `NL2SQL_QA_SLOT_STRICT_REPLAY` | `true` 时命中 QA 五元组则直接回放校验通过的 SQL(前提需要 业务场景应用中传入analysis_type、plan_item_id 等参数 实现nl2sql_qa_examples SQL对自动写入)，跳过 LLM 生成；默认 `false` 走 LLM 链路 |

**时间/范围替换逻辑（排障参考）**：优先用数据 plan 中的时间窗口，其次用户问句解析结果；plan 含「锚点向前 N 天」时用锚点回溯；SQL 中 `@t_start`/`@t_end`/`@device_keyword` 等占位符优先替换。

### 5.2 综合分析（`/analysis`）

#### 5.2.1 链路概览

**通用综合分析**（超温、检修策略等）：

```
plan_context_rag → acquire_data（NL2SQL 并行）→ rag_enrichment → synthesis(v1/v2) → finalize
synthesis v1: 统一一次调用LLM
synthesis v2: 多槽位并行调用LLM
```

**看图诊断**（缺陷识别、泄爆分析）：
```
人机协同(问句范围解析确认) → 视觉臂 + NL2SQL 臂并行 → RAG → synthesis（固定 v1，独立编排）。
synthesis v1: 统一一次调用LLM
```

两次 RAG 分工：

| 阶段 | scene | namespace | 用途 |
|------|-------|-----------|------|
| 规划前 `plan_context_rag` | nl2sql | `nl2sql_schema` / `nl2sql_biz_knowledge` / `nl2sql_qa_examples` | 辅助数据计划，不写入最终报告 user 消息 |
| 取数后 `rag_enrichment` | analysis | 业务知识库（排除上述三库） | 写入 synthesis 的「RAG 参考片段」 |

#### 5.2.2 synthesis 策略（v1 / v2）

| 策略 | 行为 | 当前完整实现专项 |
|------|------|------------------|
| **v1** | 取数 + RAG 整包给 LLM，**一次**生成报告 | 看图诊断；检修策略/泄爆/四管健康（框架已有） |
| **v2** | 多槽位（表/图程序渲染 + 叙述 LLM 有限并行），**按章流式**输出 | **超温分析** `overheat_guidance`（14 槽） |

**关键环境变量**（`.env.example` → `应用进程 · 综合分析 Analysis`）：

| 变量 | 作用 | 部署建议 |
|------|------|----------|
| `ANALYSIS_SYNTHESIS_STRATEGY` | 全局 synthesis 策略兜底 `v1`\|`v2` | 默认 `v1` |
| `ANALYSIS_SYNTHESIS_STRATEGY_<专项>` | 按 `analysis_type` 覆盖，如 `_OVERHEAT_GUIDANCE=v2` | 超温生产常用 `v2` |
| `ANALYSIS_PLAN_TEMPLATE_VERSION` / `ANALYSIS_PLAN_TEMPLATE_VERSION_<专项>` | 数据计划模板版本（`analysis_plan_*` 的 v1/v2） | 与 plan 中 q1～qN 对齐 |
| `ANALYSIS_SYNTHESIS_TEMPLATE_VERSION` / `_*_<专项>` | 报告 synthesis 模板版本 | v2 超温叙述用 `analysis_synthesis_overheat_narrative`，非整篇 `analysis_synthesis_overheat_guidance` |
| `ANALYSIS_SYNTHESIS_GATHERED_JSON_MAX_CHARS` | 传入 LLM 的取数 JSON 上限 | 默认 `16000` |
| `ANALYSIS_SYNTHESIS_MAX_TOKENS` | v1 整篇报告输出 token 上限 | 默认 `8192`，长报告勿过小 |
| `ANALYSIS_NL2SQL_LLM_PLANNER_ENABLED` | 是否跑意图+计划 LLM 节点 | 默认 `false`（走预制 plan） |
| `ANALYSIS_NL2SQL_ACQUIRE_PARALLEL_ENABLED` | 同 dependency 层 NL2SQL 并行 | 默认 `true` |

**上线必要前置（非改 env 能替代）**：

- RAG 三 namespace 已摄入（§5.1）
- `nl2sql_qa_examples` 中有校验通过的 SQL 问答对（综合分析成功取数后会**自动写入**；新项目需半自动录入或跑通一次分析）
- `LLM_DEFAULT_MODEL` 与 vLLM 一致；长报告场景确认 `max_model_len` 足够

**更换超温 v2 报告模板时须备份**（运维变更清单）：`configs/prompts.yaml` 中 `analysis_synthesis_overheat_guidance` v2、`analysis_plan_overheat_guidance` v2、`analysis_synthesis_overheat_narrative` v1、`app/llm/graphs/analysis_synthesis_v2.py`、以及 `nl2sql_qa_examples` 中相关 QA 对。

### 5.5 看图诊断（`/analysis/run-img-diag*`）

链路：用户问题 **人机协同** 解析时间与范围 → 视觉臂 + NL2SQL 臂并行 → RAG → synthesis（**固定 v1**）。

| 变量 | 作用                    | 部署建议 |
|------|-----------------------|----------|
| `ANALYSIS_IMG_DIAG_USE_LANGGRAPH` | 是否启用 scope 子图(人机协同节点) | 默认 `true` |
| `ANALYSIS_IMG_DIAG_SCOPE_HITL_ENABLED` | 两层人机协同（LLM 解析 + 库表校验） | 默认 `true` |
| `ANALYSIS_IMG_DIAG_SCOPE_VALIDATE_SQL` | 校验机组+受热面是否在账册中存在      | **须为单行 SQL**，保留 `:boiler`、`:device_name`，返回 `record_count` |
| `ANALYSIS_IMG_DIAG_CHECKPOINT_BACKEND` | HITL 断点               | 生产多 worker **`redis`** |
| `ANALYSIS_IMG_DIAG_SESSION_STORE_BACKEND` | resume_token          | 生产多 worker **`redis`** |
| `ANALYSIS_IMG_DIAG_RAG_MODE` | RAG 模式                | 默认 `vision_augmented` |

**提示词**：人机协同范围解析与 NL2SQL 共用 `configs/prompts.yaml` → `nl2sql_scope_parse`。

**验证 SQL 示例**（`.env` 中整行双引号包裹）：

```env
ANALYSIS_IMG_DIAG_SCOPE_VALIDATE_SQL="SELECT COUNT(*) AS record_count FROM account_boiler ab INNER JOIN account_static_device asd ON ab.boiler_id = asd.boiler_id WHERE ab.boiler_name = :boiler AND asd.device_name = :device_name"
```

## 7. 日常运维

### 7.1 常用命令

在 `app/app-deploy/` 目录：

```bash
# 查看应用日志（stdout）
docker compose logs -f models-app

# 查看文件日志（若 LOG_FILE_ENABLED=true）
tail -f logs/app.log

# 重启应用（不影响 vLLM / EasySearch）
docker compose restart models-app

# 停止应用栈
docker compose down

# 查看容器状态
docker compose ps
```

**vLLM / EasySearch** 分别在各自目录用 `docker compose logs -f` 查看。

### 7.2 日志配置

| 变量 | 说明 | 建议 |
|------|------|------|
| `LOG_LEVEL` | `INFO` / `DEBUG` | 生产 `INFO` |
| `LOG_FILE_ENABLED` | 是否写文件 | 生产 `true` |
| `LOG_FILE` | 容器内路径 | `/workspace/logs/app.log`（bind 到 `app/app-deploy/logs`） |

### 7.3 升级与重启顺序

1. 先升级/重启 **EasySearch**（注意索引兼容性）
2. 再 **vLLM**（模型变更时同步改 `LLM_DEFAULT_MODEL`）
3. 最后 **models-app**（`docker compose up -d --build`）
4. 可选组件（MinerU、侧车）可独立滚动

### 7.4 密钥轮换

1. 生成新 `SERVICE_API_KEY`，追加到 `SERVICE_API_KEYS`（逗号分隔，新旧并存）
2. 重启 `models-app`，通知调用方切换
3. 确认无旧钥流量后，从列表移除旧钥

## 9. 故障排查速查

| 现象 | 优先检查 |
|------|----------|
| 业务接口 503 | `SERVICE_API_KEYS` 是否已配置 |
| 连接 vLLM 失败 | `LLM_DEFAULT_ENDPOINT` 是否为 `http://vllm-service:8000/v1`；`docker network ls` 网络是否互通 |
| RAG / 检索失败 | `RAG_ES_HOSTS`、账号密码是否与 EasySearch 一致；`RAG_ES_VERIFY_CERTS` |
| 会话丢失 / 队列不续跑 | `REDIS_URL` 是否指向 `redis:6379`；Redis 容器是否 healthy |
| NL2SQL 失败 | `DB_*` 连接；业务库白名单 `ANALYSIS_NL2SQL_TABLE_SCOPE_DEFAULT`；RAG 三 namespace 是否摄入 |
| MinerU 超时 | `MINERU_BASE_URL` 须为 `http://mineru-api:8000`（非宿主机映射端口） |
| 检修 V0 侧车不可达 | `PADDLE_LAYOUT_DOCKER_NETWORK` 与侧车网络一致；endpoint 为 `http://paddleocr-layout-api:8000` |
| EasySearch 启动失败 | `vm.max_map_count`；磁盘空间；端口 9200 占用 |
| compose 报 external network 不存在 | 先启动对应子栈，或 `docker network create <网络名>` |

**值班排障**：`deploy-docs/online-services-oncall-runbook.md`（含智能客服 5 分钟检查与降级开关）。

## 12. 小结

本平台采用 **多栈容器化** 交付：底座 **EasySearch + vLLM** 先行，**应用栈** 通过 Docker 外部网络与可选 **MinerU / 版面侧车 / Neo4j** 互联。运维核心是：**`.env` 分层理解**（Compose vs 应用进程）、**必要变量对齐**（§4）、**业务能力前置**（§5：NL2SQL 三 namespace、综合分析 synthesis 策略、看图诊断 HITL Redis 等）、**按序启动与网络名一致**。日常以健康检查 + 日志 + 持久化目录备份为主；专项实现细节见 [`系统整体技术实现-简版.md`](./系统整体技术实现-简版.md) 与同目录企业级说明。
