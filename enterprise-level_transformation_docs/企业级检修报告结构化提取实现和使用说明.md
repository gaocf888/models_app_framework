## 2. 对照检查结论（先给结论）

### 2.1 是否按主文档实现

结论：**核心链路已实现，且 Phase 1 + Phase 2 的主体能力已落地。**

已实现项：
1. 独立模块与独立接口：`/inspection-extract/upload`、`/inspection-extract/run`。
2. 两段式生产调用：先上传到 MinIO，再传 URL 到 run。
3. 文档解析路由：`docx/pdf` 支持；`pdf` 扫描件可自动走 MinerU。
4. LLM 三阶段抽取：`parse` → `classify` → `repair`。
5. 规则后处理：枚举归一、缺陷类型映射、检测类型判定、是否换管归一。
6. 阈值绑定增强：位置匹配 + 段落近邻优先 + 谨慎全局回退。
7. 可追溯 warnings：记录阈值绑定值与命中来源。
8. 监控指标、配置项、测试覆盖已补齐。

### 2.2 是否达到企业级生产要求

结论：**达到“可生产试运行（Beta）”水位。**

已具备：
1. 与智能客服/综合分析同级的模块化接入。
2. 结构化输出契约 + Pydantic 强校验。
3. 对象存储化上传链路（MinIO）与远程 URL 解析。
4. 阈值规则可解释（命中来源可追溯）。
5. 指标与日志可用于排障与质量追踪。

建议继续优化（Phase 3）：
1. 场景化模板（机组/锅炉型式分版）。
2. 更细粒度段落块与表格块作用域绑定。
3. 引入人工修正闭环数据做提示词迭代。

## 4. 业务流程与实现细节

### 4.1 端到端流程（生产调用）

```mermaid
flowchart LR
  A[调用方上传文档] --> B[/inspection-extract/upload]
  B --> C[MinIO 持久化 + 预签名 URL]
  C --> D[调用 /inspection-extract/run]
  D --> E[文档解析路由 docx/pdf/mineru]
  E --> F[LLM parse 按分块]
  F --> F2{V2 且含 DOCX_V2_TABLE?}
  F2 -->|是| F3[确定性颜色校正 color_guard]
  F2 -->|否| G
  F3 --> G[LLM classify 可选跳过]
  G --> H[LLM repair 可选跳过]
  H --> I[规则后处理 + 阈值绑定]
  I --> J[Pydantic 校验 + 输出 records/summary/trace]
```

### 4.2 解析路由

- **`INSPECT_EXTRACT_PIPELINE_VERSION=v2`**（推荐 docx 强表格场景）：`app/inspection_v2` 专用摄入，表格序列化为 `[DOCX_V2_TABLE …]` + 行级 `rN: cK='…'[颜色标注:…]`，再按 Processing Unit 分块送入 parse（详见 `framework-guide/报告解析企业级实现方案V2.md`）。
- **`INSPECT_EXTRACT_PIPELINE_VERSION=v1`**（默认）：`source_type=docx/doc` 走 `DocumentParser`（`[DOCX_TABLE]` 扁平表 + 管道符）。
- `source_type=pdf`：
  - 文本层充足：普通 PDF 解析；
  - 扫描件：MinerU 路由解析为 markdown 再抽取。
- `content` 支持 URL（如 MinIO 预签名链接）：
  - 服务端先下载为临时文件，再进入上述解析流程。

### 4.3 结构化字段与规则判定

必填字段：
- 检测位置、行号、管号、壁厚、检测类型、缺陷类型、是否换管

约束规则：
1. `检测类型` 只能是 `测厚` / `缺陷`。
2. `缺陷类型` 仅允许 8 类枚举值。
3. 当 `检测类型=测厚` 时，`缺陷类型` 必须为空。
4. 当 `检测类型=缺陷` 且缺陷类型缺失时，按规则补齐并写告警。

### 4.4 DOCX V2：分块 Parse 后的确定性颜色校正（`color_guard`）

> **背景**：检修表中常见「上/下」并排（如 `c0-c1=上`、`c2-c3=下`）。下侧壁厚列有 Word 高亮时，LLM 仍可能把**同一行上侧**（无 `[颜色标注]`）误标为「缺陷」。仅改 `inspection_extract_parse` 提示词无法稳定消除该问题。

**触发条件**（同时满足）：

1. `INSPECT_EXTRACT_PIPELINE_VERSION=v2`，parse 路由为 `docx_v2`；
2. 当前分块正文含 `[DOCX_V2_TABLE`；
3. `INSPECT_EXTRACT_V2_COLOR_GUARD=true`（默认开启）。

**执行时机**：每个分块 **LLM parse 成功并合并 NDJSON/JSON 之后**、进入 classify 之前（`InspectionExtractLlmOrchestrator._parse_one_chunk`）。

**实现**：`app/inspection_v2/detection_type_color_guard.py` → `apply_docx_v2_color_guard(records, chunk)`。

**规则摘要**：

| 步骤 | 说明 |
|------|------|
| 解析分块 | 从 `rN:` 行解析列组（`r1` 的 `c0-c1='上'` 等）与各单元格 `[颜色标注:…]` |
| 对齐记录 | 用 **管号 + 壁厚 + 上/下方向**（上侧管号常为负，如 `-8`）匹配到对应 **壁厚列**（上组一般为 `c1`，下组为 `c3`） |
| 降级 | 壁厚列**无**高亮/超标候选标注，但 LLM 标为「缺陷」→ 改为 **测厚**，清空缺陷类型、`是否换管=否` |
| 升级 | 壁厚列**有**高亮等标注，但 LLM 标为「测厚」→ 改为 **缺陷** |
| 可追溯 | `warnings` 追加 `color_guard:…`；日志键 `inspection_extract color_guard chunk=… defect_count X->Y` |

**典型反例（必须纠正）**：

```text
r5: c0='8' | c1='6.1' | c2='12' | c3='4.73'[颜色标注:高亮=red]
```

- 上组 `8 / 6.1` → **测厚**（`c1` 无颜色标注）
- 下组 `12 / 4.73` → **缺陷**（仅 `c3` 有高亮）

**与阈值绑定的关系**：`canonicalize` 中若 LLM 已明确输出「测厚」，**不会**再因壁厚低于阈值升格为缺陷；上侧误标主要来自 parse 阶段 LLM，由 `color_guard` 纠正。若 parse 未输出检测类型且壁厚低于正文阈值，仍可按 §4.6 阈值规则标缺陷。

**关闭校正**（仅排障对比 LLM 裸输出）：`INSPECT_EXTRACT_V2_COLOR_GUARD=false`。

### 4.5 行号/管号设备语义校正（`record_normalization`，v1/v2 通用）

> **背景**：提示词已规定水冷壁系「行号=1、编号=管号」、过热器/再热器/省煤器系「编号=行号、管号=1」，但 LLM 偶发将编号写入错误字段。

**执行时机**：`InspectionExtractService._canonicalize_record` 内，**Pydantic 校验之前**，与管号正负号校正同一入口（`apply_deterministic_rules_to_record` → `normalize_location_row_tube`）。

**实现**：`app/inspection_v2/record_normalization.py` → `normalize_device_row_tube_by_location`。

| 检测位置关键词 | 强制规则 | 常见误标纠正 |
|--------------|---------|-------------|
| 水冷壁、包墙、后竖井、冷灰斗 | **行号 → `"1"`** | 纯整数写在行号、管号为 1/空 → 迁到 **管号** |
| 再热器、低再、高再、过热器、低过、高过、省煤器 | **管号 → `"1"`** | 纯整数写在管号、行号为 1/空 → 迁到 **行号**；行号 **去字母留数字** |

**顺序**：先设备语义校正，再管号上/下 **正负号** 校正（避免先改符号后迁字段）。

**可追溯**：`warnings` 含 `deterministic_row_fix:` / `deterministic_tube_fix:` / `deterministic_row_tube:` 等前缀。

**局限**：仅当 **检测位置字符串** 含上述关键词时生效（如仅有「右墙 B02」而无「水冷壁」则不会触发）；「2-1」等组合编号不自动拆分。

### 4.6 阈值绑定（当前增强版）

阈值来源从报告文本中抽取（如“低于3.15mm超标”），并按以下优先级匹配：
1. **段落近邻**（位置语句与阈值语句在近邻行窗口内）
2. **位置强匹配**（`hint in location`）
3. **位置相似匹配**（token 重叠评分）
4. **全局回退**（仅当文档中只有一个阈值规则）

每条记录会写入：
- `阈值绑定:<x.xxx>mm`
- `阈值命中来源:<段落近邻/位置强匹配/位置相似匹配/全局回退/未命中>`

## 5. 接口使用说明

### 5.1 上传接口

- 路径：`POST /inspection-extract/upload`
- 请求：`multipart/form-data`，字段 `file`

响应示例：

```json
{
  "ok": true,
  "file_name": "2024检修报告.docx",
  "object_name": "inspection_extract/xxxx_2024检修报告.docx",
  "source_type": "docx",
  "url": "https://minio.xxx/presigned-url",
  "bucket": "chatbot-images"
}
```

### 5.2 运行接口

- 路径：`POST /inspection-extract/run`
- 请求模型：`InspectionExtractRequest`

最小示例：

```json
{
  "user_id": "u_demo",
  "session_id": "s_demo",
  "source_type": "docx",
  "content": "https://minio.xxx/presigned-url",
  "strict": false,
  "return_evidence": true,
  "prompt_version": "v1"
}
```

响应关键字段：
- `records[]`：结构化明细
- `summary`：总数/缺陷数/换管数/warnings
- `trace`：解析路径、模型、模板版本、耗时

## 6. 提示词与配置说明

### 6.1 提示词（`configs/prompts.yaml`）

- `inspection_extract`：兜底模板
- `inspection_extract_parse`：候选记录抽取
- `inspection_extract_classify`：分类判定
- `inspection_extract_repair`：结构修复

建议：
1. 保持“仅输出 JSON”硬约束；
2. 枚举白名单写死在模板中；
3. 版本变更时优先保留旧版做灰度。

### 6.2 环境变量（`InspectionExtractConfig`）

| 环境变量 | 默认值 | 作用 |
|---|---|---|
| `INSPECT_EXTRACT_ENABLED` | `true` | 模块开关 |
| `INSPECT_EXTRACT_STRICT_DEFAULT` | `false` | 默认 strict 行为 |
| `INSPECT_EXTRACT_MAX_REPAIR_RETRIES` | `1` | 结构修复重试次数 |
| `INSPECT_EXTRACT_PROMPT_VERSION` | `v1` | 默认提示词版本（`v2` 权重更高时需显式指定 `v2`） |
| `INSPECT_EXTRACT_PIPELINE_VERSION` | `v1` | 文档解析与分块管线：`v1`（DocumentParser）\| `v2`（`app/inspection_v2` + `[DOCX_V2_TABLE]`） |
| `INSPECT_EXTRACT_V2_COLOR_GUARD` | `true` | V2：parse 后按分块 `[颜色标注]` 校正检测类型（纠正同行/跨列误标） |
| `INSPECT_EXTRACT_V2_PARSE_UNIT_MAX_CHARS` | `6000` | V2 单分块最大字符 |
| `INSPECT_EXTRACT_V2_SHADING_CANDIDATE_FILLS` | 见 `.env.example` | 单元格底纹命中时序列化「超标候选」 |
| `INSPECT_EXTRACT_MODEL_NAME` | 空 | 指定模型（为空回退 `LLM_DEFAULT_MODEL`） |

MinIO 复用配置（chatbot image）：
- `CHATBOT_IMAGE_MINIO_ENDPOINT`
- `CHATBOT_IMAGE_MINIO_ACCESS_KEY`
- `CHATBOT_IMAGE_MINIO_SECRET_KEY`
- `CHATBOT_IMAGE_MINIO_BUCKET`
- `CHATBOT_IMAGE_MINIO_SECURE`
- `CHATBOT_IMAGE_MINIO_AUTO_CREATE_BUCKET`
- `CHATBOT_IMAGE_MINIO_PRESIGN_TTL_SECONDS`

## 7. 监控与运维

指标（`app/core/metrics.py`）：
1. `inspect_extract_requests_total{status}`
2. `inspect_extract_parse_latency_seconds`
3. `inspect_extract_llm_latency_seconds`
4. `inspect_extract_records_total`
5. `inspect_extract_validation_fail_total`

运维建议：
1. 监控 `failed` 请求与 `validation_fail` 增长趋势；
2. 抽样分析 `warnings` 中“阈值命中来源”分布；
3. 针对扫描 PDF 关注 MinerU 耗时与失败率；
4. V2 docx 场景：若上/下并排表仍出现「无高亮却标缺陷」，查日志 `color_guard` 是否执行、`INSPECT_EXTRACT_PIPELINE_VERSION` 是否为 `v2`；单条记录 `warnings` 含 `color_guard:壁厚单元格无高亮→测厚` 表示已纠正。
