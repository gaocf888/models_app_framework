

## 1. 综合分析

> 当前综合分析模块分为两种链路专项：通用综合分析、看图诊断
> - 通用综合分析：NL2SQL数据计划并行执行(生产sql并查数) -> RAG知识召回重排 -> synthesis LLM分析生成报告(synthesis又分为v1和v2版本)
>   - synthesis v1: 查询数据和RAG召回整体给到LLM，进行LLM一次调用 【专项：检修策略、泄爆分析、四管健康报告解读 框架已实现，数据计划和报告模板还需要明确】
>   - synthesis v2: 分槽位(报告模板和数据)并行多次调用LLM，最后融合 【专项：超温分析 完整实现】
> - 看图诊断：视觉臂+NL2SQL数据计划并行 -> RAG知识召回重拍 -> LLM分析生成报告【专项：新版泄爆分析、缺陷识别】

### 1.0 综合分析整体配置和必要配置说明
  - 当前综合分析(包含各专项)的整体链路图如下面 1.1
  - synthesis 图节点支持 **v1 / v2** 双策略(两个分支)（通过配置项实现走哪个链路 -- `ANALYSIS_SYNTHESIS_STRATEGY` 全局 + `ANALYSIS_SYNTHESIS_STRATEGY_<专项>` 覆盖；`img_diag` 固定 v1）

    - .env.example -- ANALYSIS_PLAN_TEMPLATE_VERSION_OVERHEAT_GUIDANCE/_MAINTENANCE_STRATEGY/_FOUR_TUBE_HEALTH_INTERPRETATION/_LEAKAGE_BURST_ANALYSIS： 各专项 数据计划 提示词模板版本（如: analysis_plan_overheat_guidance）
    - .env.example -- ANALYSIS_SYNTHESIS_TEMPLATE_VERSION_OVERHEAT_GUIDANCE/_MAINTENANCE_STRATEGY/_FOUR_TUBE_HEALTH_INTERPRETATION/_LEAKAGE_BURST_ANALYSIS：各专项 报告分析 提示词模板版本(如：analysis_synthesis_overheat_guidance)

### 1.1 综合分析LangGraph图节点链路

```
normalize_request
  → plan_context_rag      （规划前 RAG，scene=nl2sql）
  → intent_llm
  → plan_llm              （生成/补充数据计划 tasks(analysis_plan_overheat_guidance). intent_llm/plan_llm 目前通过环境变量默认关闭）
```

#### 1.1.1 两次 RAG 分别干什么
① plan_context_rag（取数之前）
命名空间：nl2sql_schema / nl2sql_biz_knowledge / nl2sql_qa_examples
每库 top_k=3，合计最多约 9 条 snippet
用途：喂给 intent_llm / plan_llm，或写入 plan task 的 question 引导（_apply_plan_context_guide）
不写入 synthesis 的 user 消息（RAG参考片段）
② rag_enrichment（取数之后）
查询：{analysis_type} {query}
scene=analysis，top_k=8，排除 nl2sql 三个命名空间
用途：写入 context_snippets，在 synthesis 的 user 消息中拼入「RAG参考片段」
受 req.options.enable_rag 控制（默认 true）

#### 1.1.3 最终生成报告 LLM 调用的提示词说明（v1 路径）
报告分析提示词：prompts.yaml中analysis_synthesis_overheat_guidance的v1
实现位置：`app/llm/graphs/analysis_graph_runner.py`（`_build_summary_messages`、`_generate_summary`、`_stream_summary_text`）。

**调用方式**：通过 `VLLMHttpClient.chat` / `stream_chat` 发送 **两条消息**（OpenAI 兼容 `messages`），不再把 system 模板与事实数据拼成单条 `user` prompt。

| 消息 role | 内容来源 | 说明 |
|-----------|----------|------|
| **system** | `_resolve_stage_template(stage="analysis_synthesis")` | 优先 `analysis_synthesis_<analysis_type>`（如 `analysis_synthesis_overheat_guidance`），含角色、输出结构、硬约束 |
| **user** | `_build_summary_user_content(...)` | 本轮可变事实：类型、数据模式、用户问题、可选规划意图、gathered_data、业务 RAG |

**user 消息内各块：**

- **gathered_data**（`acquire_data` 产出）：`dict[item_id, rows]` 整包 `json.dumps` 后截断，默认 **`ANALYSIS_SYNTHESIS_GATHERED_JSON_MAX_CHARS=16000`**（与 per-query `max_rows_per_query` 是两层限制）
- **synthesis 输出**：`ANALYSIS_SYNTHESIS_MAX_TOKENS=8192`（默认；六章+附录四表时 3072 易 `finish_reason=length` 中途截断）
- **业务 RAG**（`rag_enrichment`）：每条为 chunk 全文；最多 **8** 条，以 `- ` 列表拼入 user
- **规划意图**（可选）：`nl2sql_llm_planner_enabled` 时附带 intent JSON，**[:2000] 字符**

报告结构以 **system 模板**为准；代码中已移除旧的「请输出：1) 核心结论；2) 关键依据；3) 可执行建议。」硬编码结尾。

```python
# _build_summary_messages：system + user
messages = [
    {"role": "system", "content": system_prompt},  # analysis_synthesis_overheat_guidance 等
    {"role": "user", "content": user_content},     # _build_summary_user_content(...)
]

# 非流式 synthesis
summary = await self._llm.chat(
    model=None, messages=messages,
    timeout=..., max_tokens=ANALYSIS_SYNTHESIS_MAX_TOKENS,  # 默认 8192
)

# 流式（run-with-nl2sql-stream / run-img-diag-stream）
async for chunk in self._llm.stream_chat(
    model=None, messages=messages,
    timeout=..., max_tokens=ANALYSIS_SYNTHESIS_MAX_TOKENS,
):
    yield chunk
```

```python
# _build_summary_user_content（user 消息正文，节选）
data_preview = json.dumps(data_blob, ensure_ascii=False, default=...)[:max_chars]  # max_chars 来自配置，默认 16000
rag_text = "\n".join(f"- {s}" for s in context_snippets[:8])
# planning_block：intent JSON，[:2000]
return (
    f"分析类型: {analysis_type}\n"
    f"数据来源模式: {data_mode}\n"
    f"用户问题: {query}\n"
    f"{planning_block}"
    f"数据摘要(JSON截断): {data_preview}\n"
    f"RAG参考片段:\n{rag_text}"
).strip()
```

#### 1.1.4 最终生成报告 LLM 调用的提示词说明（v2 多槽路径）

报告分析提示词：prompts.yaml中analysis_synthesis_overheat_guidance v2仅作为蓝图，实际报告分析提示词在槽位文件 analysis_synthesis_v2.py中硬编码实现。

| 消息 role | 内容来源 | 说明 |
|-----------|----------|------|
| **system** | `analysis_synthesis_overheat_narrative`（`version: v1`） | 全局硬约束：禁止编造、禁止 Markdown 标题行、字段名=值、RAG 不作数值源等 |

#### 1.1.5 acquire_data 中 NL2SQL SQL 问答对自动写入 RAG

## 2. 综合分析智能体

> 路由 `/analysis-agent/*`，代码 `app/analysis_agent/`。**与 §1 现网 `/analysis` 独立**，不复用 `AnalysisGraphRunner` / synthesis v1·v2 分支。

### 2.0 整体配置说明

- **报告章节（事实源）**：`configs/analysis_agent_reports/{type}.analysis_agent.json`（兜底）；可选 `{type}.{plan_template_version}.json`
- **数据计划 / 章节合成**：`configs/prompts.yaml` → `analysis_agent_plan_*`、`analysis_agent_synthesis_*`
- **NL2SQL SQL 生成**：公共 scene `nl2sql`（与 chatbot 共用基座，传真实 `analysis_type` + QA 五元组）
- **逻辑 plan 版本**：环境变量 `ANALYSIS_AGENT_PLAN_TEMPLATE_VERSION`（默认 `analysis_agent_v1`），用于 trace 与 NL2SQL QA 去重，**与 §1 的 v1/v2 隔离**
- **四类专项**：`overheat_guidance` / `maintenance_strategy` / `four_tube_health_interpretation` / `leakage_burst_analysis`
- **详细 env 注释**：`app/app-deploy/.env.example` → **G2. 综合分析智能体**

### 2.1 整体链路图

```
POST /analysis-agent/run-stream
  → initialize          （加载 report JSON + plan 任务列表 + 章节顺序）
  → intent_rag          （可选业务 RAG，scene=analysis）
  → slot_nl2sql         （按章绑定 q* 调 NL2SQL 取数，同 q 跨章去重）
  → slot_quality        （mandatory 缺失 → 重试 / HITL / strict 失败）
  → slot_human          （可选：interrupt → resume-stream 续跑）
  → slot_synthesize     （llm_section → ReAct 合成；static/table/chart → 程序渲染）
  → slot_emit           （SSE：slot_start / nl2sql_done / summary_delta / table|chart / slot_complete）
  → （下一章循环 slot_nl2sql …）
  → finalize            （report_complete + finished）
```

**与 §1 核心差异**：**按章节串行**「取数 → 合成 → 推送」，非整篇一次 synthesis LLM。

### 2.2 提示词模板说明

| 用途 | prompts.yaml scene | 说明 |
|------|-------------------|------|
| NL2SQL 问句清单 | `analysis_agent_plan_{type}` | JSON 数组 q*；report 内嵌 `plan.items` 时优先用 JSON |
| 章节合成 system | `analysis_agent_synthesis_{type}` | 短 system（角色 + 硬约束）；**本章 outline/任务在 report JSON 章节字段** |
| SQL 生成 | `nl2sql` | 公共模板；请求带 `analysis_type` + `plan_item_id` + `plan_template_version` |
| 报告结构 | **不在 yaml** | `configs/analysis_agent_reports/*.json` 的 `chapters[]`（`llm_section` / `static_markdown` 等） |

**LLM 调用（llm_section）**：`analysis_agent_synthesis_*` 作 **system** + user 消息含用户 query、本章 outline、绑定 q 的 JSON 切片、业务 RAG。

### 2.3 重要配置项说明

| 变量 | 作用（概要） |
|------|----------------|

## 4. NL2SQL(基座能力)

### 4.1 重要配置项(环境变量配置文件)
    
    - NL2SQL_INTENT_PARSE_MODE：NL2SQL 问句意图解析模式（解析用户问句中的 范围(机组、受热面、管排位置、排数、管数)）：rule（默认）| llm | rule_with_llm_fallback    rule--使用程序规则解析  llm--使用大模型(提示词模板对应 nl2sql_scope_parse)进行解析

### 4.2 重要提示词模板
    - nl2sql_scope_parse： 上述 NL2SQL_INTENT_PARSE_MODE配置为 llm时，使用大模型进行用户问题范围解析时的系统提示词模板
    - 相关各个专项 的数据计划 提示词模板

### 4.3 NL2SQL链路中，时间窗口解析和替换逻辑说明
    - 默认逻辑：用户问题中解析日期时间(time_window--@t_start/@t_end，time_anchor--具体时间锚点)和范围(机组/受热面/管排位置/排数/管数)，然后数据计划plan中解析类似"近三天"，sql中时间和范围窗口替换(数据计划plan中解析时间优先，用户问题次之；范围直接使用用户问题解析结果进行替换)
    - 特殊逻辑：若数据计划plan中包含「锚点向前*天」，替换时使用 锚点时间-*天 ~ 锚点时间 进行替换
    - sql窗口替换逻辑：首先匹配sql中的关键词(@t_start/@t_end/@unit_keyword/@device_keyword/@row_no/@tube_no)进行优先替换，次之针对sql中硬编码的时间和范围进行兜底改写
