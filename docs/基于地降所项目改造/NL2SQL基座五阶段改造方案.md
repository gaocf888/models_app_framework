## 0. 相对现网的优势结论（聚焦：自然语言 → SQL 准确性）

> 本节回答：本改造方案相对 **当前 NL2SQL 基座现网能力**，在 **NL→SQL 准确性** 上是否优势明显。  
> 结论限于生成准确性；可控性、澄清分层、安全网关等见后文，不在此夸大成“更准”。

### 0.1 总判断

**有条件地具备优势，不是无条件、立刻、全面明显更准。**

| 判断 | 说明 |
|------|------|
| **真正可能明显抬高准确率的** | **语义建模**（指标口径 / 同义词 / 行政区·站点码 / 单位）+ **显式 Schema 链接**（先钉表列再生成）——前提是语义资产与白名单建设到位 |
| **提升有限、不宜算作“更准”主因的** | 查询类型识别（间接帮助 Prompt）；`refuse` / `best_effort` 充分性策略（提升的是可控与“开口时的把握”，不是同一句生成算法本身） |
| **现网已很强、改造边际收益通常不大的** | 分析计划预写问句、QA 槽位严格回放、时间/范围程序改写、校验后 refine |

一句话：**优势主要来自“少选错表错字段、少用错口径”，取决于地降语义资产质量；不是换一套五阶段流水线名称就能自动更准。**

### 0.2 准确性维度拆解

| 维度 | 含义 | 改造相对现网 |
|------|------|--------------|
| 选对表 / 字段 / JOIN | Schema 对齐 | 显式链接 + 收窄 catalog → **潜在较强**（自由问数） |
| 过滤条件对 | 时间 / 区域 / 站点 | 码表 + **叠加**现网改写 → 有增益；改写能力本身现网已有 |
| 指标口径对 | 速率 / 单位 / 同比定义 | 语义层补现网短板 → **潜在最大** |
| 自由问数仍稳 | 开放自然语言 | 五阶段更有针对性 → 资产到位时可明显 |
| 已知问句可复现 | 计划槽 / QA | 现网往往已很高 → **优势通常不明显** |

### 0.3 分能力对准确率的贡献

| 能力 | 对 NL→SQL 准确率 | 说明 |
|------|------------------|------|
| ① 查询类型意图 | 间接、中等偏弱 | 改善结构与结果形态提示，不直接保证表字段正确 |
| ② 语义建模 | **直接、潜在最大** | 现网易错在“听懂人话、对错业务含义”；无资产则几乎无优势 |
| ③ 显式 Schema 链接 | **直接、较强**（自由问数） | 约束前移，降低幻觉表/错列；事后白名单挡不住“白名单内的错表错列”。链接链错会系统性带偏 |
| 充分性判定 + refuse/best_effort | 主要非“生成更准” | `refuse` 抬高有答子集把握、降低覆盖率；`best_effort` 接近现网尽量生成 |
| ④ 现网后半段（改写/校验/QA/缓存/refine） | 基线已强 | 本方案**保留**；改造是前半段加约束，不是替换更强生成器 |

### 0.4 分场景预期

| 场景 | 现网 | 改造后预期 | 准确率优势是否明显 |
|------|------|------------|--------------------|
| 预写槽位问句 + QA 回放 | 已很高 | 略增或持平 | **不明显** |
| 地降自由问数，语义资产与核心白名单到位 | 中等，易错口径/错列 | 选表选列 + 口径更好 | **较明显** |
| 自由问数但无口径/码表/白名单 | 靠 LLM+RAG | 五阶段徒有其名 | **不明显甚至更差**（空拒绝或链错） |
| 时间/实体已由程序改写兜住的问句 | 已较好 | 持平为主 | **不明显** |

### 0.5 为何不是“自动明显更优”

1. 准确率瓶颈常在 **领域资产**，不在阶段命名。  
2. 现网 **后处理改写 + QA 回放** 已解决一大类生成不稳问题。  
3. **链接/字典错误会放大错误**，优势可变成劣势。  
4. 评测口径易骗人：多 `refuse` 会抬高“有答准确率”，业务体感未必更好——须同时看覆盖率与黄金集。

### 0.6 怎样才算优势落地（建议评测）

用同一黄金集对比现网 vs 改造（勿只凭架构感觉）：

- 自由问数：表字段正确率、可执行率、结果与业务口径一致率，并单列 `refuse` 率  
- 固定计划集：应 **无明显回退**  
- 投入产出：若 KPI 主要是“SQL 更准”，应 **押在语义资产与链接质量**，而非“五阶段”形式本身

### 0.7 本节结论（决策用）

> **改造方案在 NL→SQL 准确性上：对地降自由问数、且语义建模 + 显式 Schema 链接做实时，优势可以明显；对现网已擅长的计划问句/QA 路径，优势通常不明显。查询类型与拒绝策略主要换可控性，不是生成精度的主杠杆。**

因此后文改造仍值得做，但对外/对内应如实预期：**准确性收益是条件收益；无 §5 前置条件则不应宣称“比现网明显更准”。**

## 1. 背景与结论

### 1.1 问题

实施方案将 NL2SQL 描述为五阶段受控链路；现网基座是「检索增强生成 + 强后处理校验」工程链路：

| 对比 | 实施方案五阶段 | 现网 NL2SQL 基座 |
|------|----------------|------------------|
| 意图 | 查询类型（趋势/对比/统计/异常…）+ 槽位；不清则澄清 | 主要是时间窗 + 实体范围（当前偏锅炉域） |
| 语义 | 显式业务语义层（指标口径、字典、单位） | 隐式（Prompt / biz RAG / lexicon / entity rules） |
| Schema | 显式链接到预登记表/字段后再生成 | DB 反射 + RAG + 白名单（隐式链接） |
| 生成校验 | SELECT + 安全网关 | **已较强**（改写、Validator、缓存、QA 回放、refine） |
| 呈现 | 表/图/摘要纳入能力描述 | 基座返回 `sql + rows`；呈现由调用方完成 |

### 1.2 改造原则

1. **演进基座，不推倒重写**：冻结后半段（生成 / 改写 / 校验 / 缓存 / 执行）。  
2. **向前插管**：在 `resolve_question_intent` 与 Prompt 构建之间插入①②③。  
3. **可灰度**：整链与分阶段均用 feature flag，保证锅炉等既有调用方可回归。  
4. **澄清分层（关键修订）**：  
   - 基座一等能力 = **意图充分性判定 + 结构化不确定信号**（缺槽位、置信度、`intent_quality`）；  
   - **对人多轮澄清交互** = 对话类业务的一等能力，**不是**基座默认行为；  
   - 报告/分析等批处理：用任务参数补全或降级/失败审计，**禁止默认进入“等人回话”**。  
5. **呈现以契约形式进入基座**：输出 `result_shape` / `chart_hint` / 口径元数据即可，不在基座内做图表引擎。  
6. **不确定时的处置可策略化**：由请求参数 / 配置决定 `refuse` / `best_effort`，避免单一硬门闸绑架所有调用方。

### 1.3 总体结论

**可行。** 最大工作量在 **语义资产建设与 Intent 域模型扩展**，不在重写 SQL 生成器。  
**意图识别、语义建模不能“只靠代码”落地**，必须具备下文 §5 所列业务与数据条件。  
**若把「交互式澄清」做成基座默认硬门闸，报告生成等无人值守链路存在中断/超时风险**——必须按 §3 分层设计规避。  
**NL→SQL 准确性相对现网的预期见文首 §0**：优势有条件、非无条件明显。

## 2. 改造目标与非目标

### 2.1 目标

| 编号 | 目标 |
|------|------|
| G1 | 基座支持查询类型意图识别 + **意图充分性判定**（输出置信度/缺失槽位/`intent_quality`） |
| G2 | 基座具备可版本化的业务语义层（指标/同义词/单位/维度码） |
| G3 | 基座具备显式 Schema 链接阶段（`LinkedSchema`），再进入现有生成链路 |
| G4 | 保留并继续强化现有生成、改写、校验、缓存、QA、执行能力 |
| G5 | 响应契约扩展：`parsed_intent`、`intent_quality`、`missing_slots`、可选 `status=insufficient_intent`；可选 `chart_hint` / 口径元数据 |
| G6 | 支持域 profile（如 `boiler` / `subsidence`），地降改造不破坏锅炉路径默认行为 |
| G7 | 支持 `on_insufficient` 策略（`refuse` / `best_effort`），**默认不假设存在终端用户可澄清** |

### 2.2 非目标（本方案不包含）

- chatbot 路由、analysis 计划模板、报告任务编排的产品改造（调用方自行适配新契约与策略）  
- 在 NL2SQL 基座内实现多轮追问会话、等待用户回复、自动续跑协议  
- 独立训练专用 Schema-Linking 大模型（P1 之后按效果再评估）  
- 一次性语义化业务库全表全字段  
- 在 NL2SQL 基座内实现完整报表/BI 前端

## 3. 澄清能力分层（架构决策）

### 3.1 三种能力不可混为一谈

| 类型 | 含义 | 放置位置 | 本方案态度 |
|------|------|----------|------------|
| **A. 不确定信号** | 基座判定类型不清 / 缺时间 / 缺区域 / 指标多义等，返回结构化结果 | **NL2SQL 基座** | **必须做** |
| **B. 澄清交互** | 向用户发问、多轮补全、等人回复再继续 | **对话业务层**（智能问答/查数 Console） | **基座不做**；由调用方消费 A 后发起 |
| **C. 编排 HITL** | 分析/看图等流水线暂停等人确认（如现网 `confirmed_scope`） | **业务编排层** | **基座只接受已确认入参**，不负责暂停会话 |

现网已有分层先例：chatbot 侧 `need_clarify`；看图诊断在 analysis 编排确认后再调 NL2SQL。本方案与之对齐，避免在基座再做第三套“等人”协议。

### 3.2 为何交互式澄清不宜作为基座默认行为

1. **职责**：基座是取数引擎（问句/约束 → SQL → rows），不是会话产品。  
2. **调用方形态差异大**：对话适合追问；报告/多槽分析多为无人值守，默认澄清会结构性冲突。  
3. **报告中断风险**：若默认“未澄清不生成/不返回”，报告多次 NL2SQL 调用易出现缺段、整单失败或挂起超时（见 §3.4）。  
4. **协议负担**：所有调用方被迫实现同一套多轮 UX，可组合性下降。

### 3.3 推荐分工

```text
基座：
  - 产出 intent_quality / missing_slots / confidence / parsed_intent
  - 按 on_insufficient=refuse|best_effort 决定：拒绝生成 或 尽力生成（仍走白名单校验）
  - 接受 confirmed_* / 结构化 filters 作为「已确认约束」

对话查数调用方：
  - refuse + 展示追问（B）→ 用户补全后再调基座

报告生成 / 分析槽位调用方：
  - 任务创建时收齐时间/站点/区域/指标等参数并注入基座
  - on_insufficient=refuse 或 best_effort（项目选定）
  - 禁止默认走「等人回话」；不足则跳过段落 / degrade / 失败可审计
```

### 3.4 对报告生成的影响（必须写清）

报告典型路径：模板参数 → 多次 NL2SQL 取数 → 计算/图文 →（可选）人工复核成稿。  
此处「人工」主要是 **成果复核**，不是每条 SQL 前向用户澄清。

| 基座策略 | 对报告的影响 |
|----------|--------------|
| 默认强制交互澄清（等人） | **高概率中断/超时**，自动化报告不可用 |
| 默认硬拒绝且报告未处理 `insufficient_intent` | 缺数段落失败，可能整报告失败或空洞产出 |
| 仅给不确定信号 + 报告侧 `on_insufficient` 明确 + 参数预置 | **可不中断**；与「受控 NL2SQL」不矛盾 |

**结论**：澄清交互不放基座默认路径；报告调用必须 **参数完备优先**，基座策略显式配置，避免静默「等人」。

### 3.5 与实施方案表述的对齐方式

实施方案「无法准确识别则进入澄清、不直接生成 SQL」——落地解释为：

- **自由对话查数**：调用方根据基座 `insufficient` 信号发起澄清（满足方案体验）。  
- **报告/批处理**：等价于「不直接瞎生成」——通过 **拒绝或参数补全**，而不是向终端用户聊天。  
- 对外演示可分开讲两条路径，避免暗示「所有 NL2SQL 调用都会弹澄清」。

## 4. 目标架构（基座内）

```text
NL2SQLQueryRequest
  question
  (+ 可选：time_intent_text / confirmed_scope / 结构化 filters /
           analysis_type / profile / on_insufficient …)
        │
        ▼
┌───────────────────────────────────────────────────────────┐
│ ① 意图识别（增强）                                         │
│    query_type + 关键槽位 + confidence / missing_slots         │
│    + 现有：时间窗 / 范围实体（profile 可扩展）               │
│    → 计算 intent_quality = ok | weak | insufficient         │
└───────────────────────────────────────────────────────────┘
        │
        ├─ insufficient 且 on_insufficient=refuse
        │     → 返回 status=insufficient_intent（无 SQL、不执行）
        │     → 【不】在基座内向用户发问或等待
        │
        ├─ insufficient 且 on_insufficient=best_effort
        │     → 继续后续阶段（依赖白名单与校验兜底），并标记质量告警
        │
        ▼
┌───────────────────────────────────────────────────────────┐
│ ② 语义建模（新增）                                         │
│    指标/同义词/单位/行政区·站点等码表对齐                     │
│    输出写入 parsed_intent（含口径引用）                      │
└───────────────────────────────────────────────────────────┘
        │
        ▼
┌───────────────────────────────────────────────────────────┐
│ ③ Schema 链接（显式化）                                     │
│    意图+语义 → 候选表/列/JOIN/过滤                           │
│    ∩ DB反射目录 ∩ 预登记白名单 → LinkedSchema                │
│    失败 → 按策略 refuse（返回可机读原因）或 best_effort 降级  │
└───────────────────────────────────────────────────────────┘
        │
        ▼
┌───────────────────────────────────────────────────────────┐
│ ④ 生成与校验（现网保留）                                     │
│    RAG/QA回放/L1·L2缓存/LLM生成                              │
│    时间·范围改写 → Validator →（可选 EXPLAIN）→ Executor     │
└───────────────────────────────────────────────────────────┘
        │
        ▼
┌───────────────────────────────────────────────────────────┐
│ ⑤ 结果契约（基座侧）                                         │
│    sql + rows + parsed_intent + intent_quality              │
│    + result_shape / chart_hint / metric_definition / 时间口径 │
│    （实际画图、对人澄清均由调用方完成）                       │
└───────────────────────────────────────────────────────────┘
```

**主挂载点**：`NL2SQLChain.generate_sql_with_validation_context`（意图解析之后、RAG/Prompt 之前）。  
**策略短路**：建议在 `NL2SQLService.query` 根据 `intent_quality` + `on_insufficient` 决定是否进入生成；**短路只返回机读状态，不开启会话等待**。

## 5. 前置条件总表（重点：意图识别 & 语义建模）

> 说明：下列「必须 / 强烈建议 / 可选」按能力阶段划分。没有对应条件，该阶段只能做原型演示，无法达到实施方案所述可控水准。

### 5.1 条件总览

| 条件项 | 意图识别① | 语义建模② | Schema 链接③ | SQL 生成校验④ | 说明 |
|--------|:---------:|:---------:|:------------:|:-------------:|------|
| 高频自然语言问句样本集（≥50，含标准答案意图） | **必须** | 强烈建议 | 强烈建议 | 建议 | 分类规则/评测集 |
| 查询类型枚举与业务确认 | **必须** | — | 建议 | — | 趋势/对比/统计/异常等 |
| 指标口径说明书（业务确认） | 建议 | **必须** | 强烈建议 | 建议 | 速率、沉降量、同比等怎么算 |
| 同义词/别名词典 | 强烈建议 | **必须** | 强烈建议 | 建议 | 「沉降量」「累计沉降」等 |
| 维度码表（行政区、站点编码、设备类型等） | 强烈建议 | **必须** | **必须** | 强烈建议 | 通州≠字符串瞎匹配 |
| **数据库结构文档**（表/字段/注释/关系） | 建议 | **必须** | **必须** | **必须** | 见 §5.2 |
| **只读库访问**（可反射 Schema + 抽样验数） | 可选* | 强烈建议 | **必须** | **必须** | 见 §5.3 |
| 预登记可查对象清单（表/视图白名单） | — | 强烈建议 | **必须** | **必须** | 安全边界 |
| 跨区网络与只读账号策略 | — | — | 强烈建议 | **必须**（生产） | 地降政务场景 |
| 单位与时间维度约定 | 建议 | **必须** | 强烈建议 | 强烈建议 | mm/月 vs mm；业务月 vs 自然月 |
| **充分性判定规则**（哪些槽位缺失 → insufficient） | **必须** | 建议 | 建议 | — | 基座机读判定用 |
| **各调用方处置策略确认**（对话澄清 / 报告拒绝或降级） | **必须**（产品） | — | — | — | **不属于基座实现，但必须事先约定** |
| 对话侧澄清话术（若有自由查数） | 对话层必须 | — | — | — | **不进基座** |

### 5.2 意图识别（①）需要什么条件

#### 5.2.1 必须具备

| 条件 | 内容要求 | 不满足的后果 |
|------|----------|--------------|
| **查询类型体系** | 业务确认的枚举：如趋势、对比、统计、异常、站点详情、设备运行等（可按地降裁剪） | 无法实现方案所述「意图识别阶段」 |
| **标注样本** | 每类 ≥10 条真实问句 + 期望类型 + 关键槽位；另准备混淆集 | 规则/小模型无法评测，上线易误判 |
| **充分性判定规则** | 哪些槽位缺失或低置信度 → `insufficient` / `weak` | 只能「猜了就生成」，或误用硬澄清打断批处理 |
| **时间表达约定** | 「近三个月」「本月」「去年同期」的业务定义 | 与现有时间解析冲突或口径错误 |
| **调用方策略矩阵** | 对话 / 报告 / 分析各自 `on_insufficient` 取值 | 基座行为与产品预期不一致 |

#### 5.2.2 强烈建议具备

| 条件 | 说明 |
|------|------|
| 行政区 / 站点标准名称列表 | 支撑范围槽位；可先 Excel/CSV，后与维表对齐 |
| 监测主题词表 | 水准 / GNSS / InSAR / 地下水等，便于类型与主题联立 |
| 与原型/需求文档对齐的快捷问法 | 参考 `智能数据查询及分析-需求剖析.md` 中的交互问法 |
| 对话侧澄清话术模板 | 由查数/问答产品维护；基座只提供 `missing_slots` 枚举 |

#### 5.2.3 意图识别是否必须「能访问真实数据库」？

| 阶段 | 是否必须连真实库 |
|------|------------------|
| 做 query_type 分类器（规则/LLM） | **不必**。有问句样本即可开发与单测 |
| 做「通州区 / 某站点」等范围解析 | **强烈建议有码表**；有只读库维表更佳 |
| 验收「识别后能正确查数」 | **必须**有只读库或等价脱敏库 |

**结论**：意图识别的**算法骨架**可不连库启动；**地降可交付的意图识别**必须至少有维度词典，端到端验收必须有库。

### 5.3 语义建模（②）需要什么条件

语义建模 = 建设并运行期使用 **业务语义层**（不是再训一个大模型）。

#### 5.3.1 必须具备

| 条件 | 内容要求 | 责任方建议 |
|------|----------|------------|
| **数据库结构文档** | 表名、字段名、类型、中文注释、主外键/关联说明、分区或时间字段 | 甲方 / 业务库维护方 |
| **核心指标口径** | 每个开放查询指标：定义、计算公式、单位、统计粒度、数据截止规则、适用表/视图 | 业务人员书面确认 |
| **字段语义覆盖目标范围** | 先圈定「允许 NL2SQL 使用的核心表/视图集合」，再谈覆盖率≥95%（按该集合计，勿按全库） | 甲乙双方共同圈定 |
| **同义词与禁混用词** | 业务别名；明确不可等同的概念（如沉降量 ≠ 地下水降深） | 业务确认 |
| **维度字典** | 行政区划代码、站点 ID/名称映射、设备类型编码等 | 最好来自库内维表或权威导出 |

仓库内已有部分结构材料（需核对是否为最新、是否完整）：

- `docs/地降所需求及数据相关/数据库结构及逻辑/沉降标准数据库表结构说明260325.docx`
- `docs/地降所需求及数据相关/数据库结构及逻辑/_extracted_schema.txt`（含多类监测表字段摘录）

> **注意**：文档抽取稿可能含连接信息，正式改造应以甲方提供的**受控只读账号与最新结构**为准，文档仅作启动输入，不能替代生产元数据。

#### 5.3.2 强烈建议具备

| 条件 | 说明 |
|------|------|
| **只读数据库访问** | 用于：① Schema 反射校验文档准确性；② 抽样核对指标口径；③ 建设预登记白名单 |
| **业务确认的查询白名单视图** | 优先对视图/稳定宽表建模，避免直接暴露过多明细表 |
| **样例问句 ↔ 期望 SQL 或期望结果** | 语义是否正确的黄金集 |
| **单位与时间维度书面约定** | 写入语义配置，禁止模型临场发明 |

#### 5.3.3 语义建模是否必须「能访问真实数据库」？

| 工作 | 仅有结构文档 | 文档 + 只读库 |
|------|--------------|---------------|
| 起草字段中文名 / 同义词初稿 | 可以 | 更好（以库为准纠偏） |
| 确认指标计算公式与数值 | **不够**（缺实数验证） | **需要** |
| Schema 反射、白名单、联调 | 不够 | **必须** |
| 达到方案「口径可追溯、可验收」 | 不够 | **必须** |

**结论**：

1. **数据库结构文档：语义建模的准入条件（必须）**。没有结构文档（或等价的表结构导出），无法做严肃语义层。  
2. **实际只读库访问：语义建模达标与 Schema 链接/生成联调的准出条件（强烈建议→生产必须）**。  
3. 仅有文档、无库：最多完成「语义字典草稿 + 离线 Demo」；不能宣称 NL2SQL 五阶段已按实施方案落地。

### 5.4 Schema 链接 / 生成校验另需条件（简述）

| 条件 | 用途 |
|------|------|
| 预登记表/视图清单 | 链接与校验白名单 |
| 只读账号 + 最小权限 | 禁止 DML；跨区策略按实施方案 |

| 行数上限、超时、函数白名单策略 | 安全网关参数 |

现网基座已具备反射、白名单、Validator、Executor 骨架；地降侧主要是 **换域配置 + 权限落库**，而非从零开发。

## 6. 分期实施计划

### 6.1 P0 — 基座可解释、可策略门控（意图识别 MVP + 轻量语义）

**依赖条件**：查询类型确认、样本集、充分性判定规则、调用方策略矩阵；结构文档（可先用现有抽取稿）；语义轻量字典初稿。只读库建议具备，非阻塞分类器开发。

| 工作项 | 基座落点 |
|--------|----------|
| 扩展 `QuestionIntent`（`query_type` / `confidence` / `missing_slots` / `intent_quality`） | `question_scope_models.py` |
| `query_type_parser`（rule 优先，LLM 兜底） | 新模块，并入 `resolve_question_intent` |
| `on_insufficient` + `status=insufficient_intent` | `NL2SQLQueryRequest/Response` + `NL2SQLService` 策略短路（**无会话等待**） |
| 轻量 `semantic_dict`（指标同义词/单位） | 配置资产 + 对齐写入 intent |
| 打开并规范 intent 注入 Prompt | 现有 `inject_parsed_intent` 产品化 |
| feature flag | 如 `NL2SQL_STAGE_PIPELINE=off\|p0\|full` |
| 域 profile 骨架 | `boiler` 默认保持；`subsidence` 可启用新槽位 |
| 默认策略 | 无显式传参时：**不假设可澄清**；建议默认 `best_effort` 或按 profile 配置，**禁止默认“等人”** |

**验收**：

- 给定问句可稳定输出 query_type、missing_slots、intent_quality  
- `on_insufficient=refuse` 时不生成 SQL，返回机读不足状态（可被对话层转澄清）  
- `on_insufficient=best_effort` 时仍可走生成+校验（用于批处理过渡）  
- 锅炉默认路径回归通过（flag=off 或 profile=boiler）  
- **单测证明：基座自身不阻塞等待用户输入**

### 6.2 P1 — 正式语义层 + 显式 Schema 链接

**依赖条件**：**结构文档（最新）+ 只读库 + 指标口径业务确认 + 白名单视图 + 维度码表**。

| 工作项 | 基座落点 |
|--------|----------|
| 版本化语义资产（YAML/表）与加载校验 | `semantic_layer.py` |
| `_link_schema` → `LinkedSchema` | `chain.py` 前半段 |
| Prompt catalog 仅用链接结果 | `PromptBuilder` / catalog 注入 |
| 链接失败按 `on_insufficient` / 独立 link 策略返回机读原因 | Service 契约 |
| 全链路 trace（意图→对齐→链接→SQL→行数） | 现有 trace 扩展 |
| 地降 profile 范围改写 | 扩展 `_rewrite_query_filters` / scope 模型 |
| 报告调用约定落地（文档+示例） | 参数注入 + `on_insufficient` 推荐值 |

**验收**：

- 无白名单表不会出现在可执行 SQL  
- 口径可追溯到语义资产版本号  
- 黄金集（问句→结果/SQL）准确率相对 P0 可量化提升  
- 只读、LIMIT、超时等策略可演示  
- 报告模拟调用（连续多槽、无人工输入）在约定策略下**不出现等待澄清挂起**

### 6.3 P2 — 结果契约与治理

| 工作项 | 说明 |
|--------|------|
| `result_shape` / `chart_hint` | 按 query_type 输出，调用方画图 |
| 口径/时间窗脚注元数据 | 满足方案「结论注明统计口径与时间范围」 |
| 语义覆盖率度量 | 按「登记核心集」统计，对齐≥95% 目标口径 |
| 坏例回流 | 接入现有 QA feedback，强化基座 |

## 8. 配置与灰度建议

| 配置项（示例名） | 作用 |
|------------------|------|
| `NL2SQL_STAGE_PIPELINE` | `off` / `p0` / `full` |
| `NL2SQL_DOMAIN_PROFILE` | `boiler` / `subsidence` |
| `NL2SQL_ON_INSUFFICIENT_DEFAULT` | 默认 `best_effort` 或 `refuse`（**禁止**隐含“等人澄清”） |
| `NL2SQL_SEMANTIC_DICT_PATH` | 语义资产路径 |
| `NL2SQL_SCHEMA_ALLOWLIST` | 预登记表/视图 |
| `NL2SQL_INJECT_PARSED_INTENT` | 已有；P0 建议对地降 profile 默认 true |

请求级覆盖（优先于全局默认）：

- `on_insufficient=refuse|best_effort`  
- 结构化约束 / `confirmed_scope`（视为已确认，提升 `intent_quality`）

建议策略：

- 既有锅炉调用：默认 `off` 或 `boiler` + `best_effort`（保持兼容）  
- 地降对话查数：`p0/full` + 调用方传 `refuse` + 业务澄清  
- 地降报告：`p0/full` + 参数注入 + **显式** `refuse` 或 `best_effort`，并实现缺数降级  
- 缓存键必须包含 profile、语义版本、pipeline、`on_insufficient`，避免脏命中

## 9. 风险与对策

| 风险 | 对策 |
|------|------|
| 结构文档过时或与库不一致 | 以只读反射为准，文档差异出差异报告给甲方确认 |
| 指标口径迟迟无法业务确认 | P0 只用轻量同义词；P1 准入门槛写进项目计划 |
| **基座强制澄清导致报告中断** | **不做交互等待**；策略化 `on_insufficient`；报告参数预置（§3） |
| 对话层未消费 `insufficient` 导致乱生成 | 自由查数强制 `refuse` + 联调检查清单 |
| 前半段过严导致零 SQL | 过渡期 `best_effort` + 宽 catalog 降级（打点告警） |
| 域模型与锅炉耦合 | profile 隔离；禁止删改锅炉默认字段语义 |
| 无真实库却承诺五阶段落地 | 对外区分「设计已对齐」与「联调已验收」；无库不宣称 P1 完成 |
| 与实施方案话术不一致 | 对外按 §3.5 分路径说明：对话澄清 vs 批处理拒绝/补参 |
