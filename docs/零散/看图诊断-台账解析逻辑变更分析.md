# 看图诊断：台账解析逻辑变更分析

> 状态：分析 / 方案（**未实施**）  
> 背景：梳理看图诊断（缺陷识别 / 泄爆）台账解析与业务库校验现状；说明自动放宽未生效原因；评估「定位失败字段 → 上级拉候选 → LLM 匹配 → 用户选择」的可行性与实现方案。  
> 触发时机约定：在 **约两轮台账校正 HITL 之后** 再进入候选选择（与现有 auto_relax 的 `hitl_rounds >= 2` 节奏对齐，但建议用独立计数更干净）。  
> 相关代码：`img_diag_scope_intent.py`、`img_diag_scope_parser_llm.py`、`scope_parser_rule.py`、`img_diag_scope_validate.py`、`img_diag_scope_graph.py`、`img_diag_scope_display.py`。

---

## 1. 背景与问题

### 1.1 典型现象

用户输入台账自然语言，例如：

> 机组：1号锅炉　受热面：水冷壁螺旋段前墙　检测位置：吹灰孔71

业务库校验未命中后进入人机协同，展示「业务库中未匹配到下面台账信息…」，并回显当前解析（含机组 / 受热面 / 检测位置 / 排数等）。

 intuitively 期望：校验失败时能 **自动放宽** 细粒度字段再查；或进一步能知道 **哪一层失败**，再按上级拉出同级全部标准台账，交给大模型给出最接近选项供用户选择。

### 1.2 要回答的问题

1. 当前台账解析与库校验的详细逻辑是什么？  
2. 基于当前配置，自动放宽是否会执行？为何日志里看不到放宽？  
3. **当前实现能否直接得到「哪个字段校验失败」？**  
4. 若要做「失败层诊断 + 候选查询 + LLM TopK + 用户选择」，可行性如何？建议如何挂到「两轮校正之后」？

---

## 2. 当前台账解析逻辑（现状）

看图诊断台账不是单次 LLM 调用，而是 LangGraph 流水线：

```text
累计文本 scope_cumulative_text
  → 规则 + LLM 解析 → ImgDiagScopeDraft
  → 必填门禁（机组 + 受热面）
  →（缺字段则 HITL）
  → 业务库 existence 校验（可选自动放宽）
  → 确认 / 放行（再叠加视觉门禁等）
```

图节点：`scope_preflight_llm` →（可选）`scope_human_confirm` → `scope_db_validate`。

### 2.1 解析字段

| 字段 | 含义 | 必填 |
|------|------|------|
| `boiler` | 机组 / 锅炉 | **是** |
| `device_name` | 受热面 | **是** |
| `check_location_name` | 检测位置 | 否 |
| `row_no` | 排数 | 否 |
| `tube_no` | 管数 | 否 |

时间窗口 / 锚点由程序从问句抽取，**不**交给 scope LLM 填。

多轮 HITL：`user_supplement` 换行并入 `scope_cumulative_text` 后整体重解析；`scope_patch` 可直接改 draft；「不要排数」等写入 `scope_field_exclusions`。

### 2.2 第一层：文本 → Draft（`parse_img_diag_scope_draft`）

| 来源 | 作用 |
|------|------|
| 规则 `parse_scope_rule` | 机组抽取、受热面词表最长匹配、层/屏等位置、排/管正则；水冷壁类未写排数时默认 `row_no=1` |
| LLM `img_diag_scope_parse` | 抽受热面 / 检测位置 / 排 / 管；多段输入以文末为准；支持排除可选字段 |
| 合并 | **机组以规则为主**；受热面 LLM 优先否则规则；位置/排/管以 LLM 为主（LLM 失败则规则兜底） |
| 置信度 | 规则与 LLM 受热面不一致、或受热面不在词表 → `low` |

### 2.3 第二层：必填门禁

仅强制 `boiler` + `device_name`。缺任一 → HITL（「未识别解析到台账信息，请补充！」）；齐全 → 进库校验。

### 2.4 第三层：业务库校验（`validate_scope_in_catalog`）

默认 SQL（可被 `ANALYSIS_IMG_DIAG_SCOPE_VALIDATE_SQL` 覆盖）对以下条件做 **合取** `COUNT(*)`：

- `account_boiler`：机组名  
- `overhaul_new_checklocation`：受热面（表面节点）+ 可选检测位置（子节点 `parent_id`）  
- `base_temp_point`：可选排 / 管（`device_id` 取自表面）

返回值只有：

- `(record_count, error_message)`  
- 失败时图状态：`interrupt_reason = db_validate_zero_rows`，**无失败字段名**

日志中 `SQLExecutor.execute done row_count=1` 表示 COUNT 查询 **返回了 1 行结果集**，**不是** `record_count > 0`。

### 2.5 自动放宽（`validate_scope_with_relaxation`）

若 `allow_auto_relax=True` 且首轮 COUNT=0，按顺序丢掉细字段再查：

```text
tube_no → row_no → check_location_name
```

直到命中或只剩机组+受热面。成功放宽会打日志：`img_diag scope auto-relaxed fields=...`。

是否允许放宽由 `scope_auto_relax_allowed` 决定：

```text
ANALYSIS_IMG_DIAG_SCOPE_AUTO_RELAX_ENABLED 默认 false
开启后还要求 hitl_rounds >= 2
```

因此：**首轮库校验（hitl_rounds 通常为 0）即使打开开关也不会放宽**；默认配置下更是完全关闭。

### 2.6 与「自动放宽未执行」实例的对照

某次缺陷识别请求日志特征：

- 两次校验 SQL 条件相同（含 `吹灰孔71`、`row_num=1`），无逐级放宽后的后续 SQL；  
- 无 `auto-relaxed fields` 日志；  
- HITL 文案为业务库未匹配，当前解析仍带完整细粒度。

结论与配置一致：**未执行自动放宽**。另：用户未写排数时出现 `row_no=1`，来自水冷壁类默认规则，会使首轮条件更严。

## 3. 目标能力（变更方向）

在保留现有「自由文本台账校正 HITL」的前提下，增加：

1. **定位**哪一层台账信息导致业务库校验失败（机组 / 受热面 / 检测位置 / 排数 / 管数）；  
2. 用 **已命中的上级** 查询该失败层级下的 **全部（或截断后的）标准台账候选**；  
3. 交给大模型，结合用户自然语言，给出最匹配的若干选项；  
4. 以 HITL 形式让用户选择；  
5. **仅在约两轮台账校正 HITL 之后** 触发（避免首轮未匹配就打扰用户选列表）。

与自动放宽关系建议：

| 策略 | 说明 |
|------|------|
| **A（推荐主路径）** | 先候选选择，不依赖偷偷放宽 |
| A→B | 候选选择仍失败后再考虑 auto_relax |
| 仅 B | 只开 auto_relax，**无法**满足「给选项」 |

## 4. 可行性分析

### 4.1 当前能否直接得到「哪个字段失败」？

**不能。**

现有合取 `COUNT(*)` 失败时只知道「整单未命中」，状态里没有 `failed_field` / `matched_prefix`。  
自动放宽成功时的 `relaxed_fields` 表示「最终丢掉了什么」，**不是**「诊断出的失败层」。

### 4.2 以现有库表能否实现目标？

**能**，但必须 **新增**「逐级诊断 + 候选拉取 + LLM 排序 + 选择式 HITL」，不能指望改 prompt 或只打开 auto_relax。

#### A. 定位失败层级 —— 可行（前缀探测）

台账层级与放宽顺序同源：

```text
boiler → device_name → check_location_name → row_no → tube_no
```

对当前 draft 做前缀存在性探测，取 **最长已命中前缀的下一层** 为 `failed_field`。  
不要指望单条合取 COUNT 反推失败字段。

注意歧义：

1. 受热面 `LIKE` 命中错误表面时，表面「假命中」会导致检测位置「假失败」。  
2. 水冷壁默认 `row_no=1`：诊断时应区分「用户显式排数」与「默认注入」。  
3. 若现场覆盖了 `ANALYSIS_IMG_DIAG_SCOPE_VALIDATE_SQL`，诊断 SQL 必须与线上校验口径一致。

#### B. 按上级查同级候选 —— 可行

| 失败层 | 上级条件 | 候选来源（与现校验一致） |
|--------|----------|--------------------------|
| 机组 | （无） | `account_boiler` |
| 受热面 | 机组 | `overhaul_new_checklocation` 表面节点 |
| 检测位置 | 机组 + 受热面 | 子节点 `parent_id = 表面.id` |
| 排数 | 机组 + 受热面（+可选位置） | `base_temp_point.row_num` |
| 管数 | … + 排 | `base_temp_point.pipe_num` |

例：检测位置失败 → 用机组+受热面列出全部检测位置 —— 与现表模型一致。

风险：**候选量**（位置 / 排 / 管可能很多）。需 `LIMIT`、预筛或分页，再交给 LLM。

#### C. LLM TopK —— 可行

输入：累计自然语言 + 当前 draft + 候选列表（截断）。  
输出：仅从候选中选 Top-K + 短理由；禁止幻觉新台账名。  
建议新 scene：`img_diag_scope_candidate_rank`。

#### D. 用户选择 HITL —— 可行

在现有 `scope_human_confirm` / interrupt 上扩展，例如：

- `hitl_mode = scope_candidate_pick`（名称示意）  
- `failed_field`、`candidates[]`、`llm_suggestions[]`  
- 用户通过点选或 `scope_patch` 回写后再 `db_validate`

可与自由文本补充并存：前两轮自由校正，之后进入选项选择。

### 4.3 触发时机与 `hitl_rounds`

现有 auto_relax：`enabled && hitl_rounds >= 2`（`hitl_rounds` 在每次进入 `scope_human_confirm` 时递增）。

**不建议直接复用 `hitl_rounds` 作为「两轮台账校正」的唯一条件**：其中可能混入缺字段 HITL、视觉相关 HITL 等，导致触发过早或过晚。

**推荐**：独立计数 `scope_db_mismatch_rounds`（仅统计「`db_validate_zero_rows` 后用户做了台账校正又再校验」的轮次），当 `>= 2` 且再次未命中时进入候选选择 HITL。

示意状态机：

```text
R0: 解析 → 库失败 → 普通「业务库未匹配」HITL（自由补充）
R1: 校正 → 再失败 → 再一轮自由补充 HITL
R2+: 仍失败 → 失败层诊断 + 候选 + LLM TopK + 选择 HITL
     （可选：仍失败后再 auto_relax）
```

## 5. 推荐实现方案（未落地）

### 5.1 模块划分

| 模块 | 职责 |
|------|------|
| `img_diag_scope_diagnose.py`（新建） | 前缀探测 → `failed_field` + `matched_prefix` + `user_value` + 可选 `injected_defaults` |
| 候选查询（可同文件或 `img_diag_scope_candidates.py`） | 按失败层 + 上级拉 DISTINCT 列表，带上限 |
| LLM 排序 | 新 prompt scene，强制从候选中选 |
| `img_diag_scope_graph.py` | 在库失败且 mismatch 轮次达标时走候选 HITL；选择后回写 draft 再校验 |
| `img_diag_scope_display.py` / SSE | 展示候选与建议；`hitl_mode` / `ui_buttons` 或列表协议 |
| 配置 | 开关、TopK、候选 LIMIT、是否与 auto_relax 串行 |

### 5.2 诊断 API 输出示意

```json
{
  "failed_field": "check_location_name",
  "matched_prefix": {
    "boiler": "1号锅炉",
    "device_name": "水冷壁螺旋段前墙"
  },
  "user_value": "吹灰孔71",
  "injected_defaults": ["row_no"]
}
```

### 5.3 与自动放宽

- 主路径走候选选择（策略 A）。  
- 可选 A→B：选择后仍失败再启用现有 `validate_scope_with_relaxation`。  
- 保持 `ANALYSIS_IMG_DIAG_SCOPE_AUTO_RELAX_ENABLED` 默认 false，避免与「必须用户确认标准名」冲突。

### 5.4 风险与边界

1. 现状开箱 **做不到** 失败字段定位，必须加诊断查询。  
2. 受热面模糊匹配错误 → 位置假失败；可对表面做多候选再查位置。  
3. 机组 / 受热面本身失败时，上级与候选集不同，需单独文案。  
4. 排 / 管默认值：诊断前可先试「去掉非显式默认排」再判失败层。  
5. 性能：候选 SQL + LLM **仅**在第 3 轮+触发。  
6. 前端需能展示选项；过渡期可用「回复选第 N 个」或回填标准全名。

## 6. 结论摘要

| 项 | 结论 |
|----|------|
| 当前库校验 | 合取 COUNT，**不能**直接知道失败字段 |
| 自动放宽 | 默认关；开了也要 `hitl_rounds>=2`；首轮不会放宽 |
| 目标能力 | **可行**，依赖新诊断 / 候选 / LLM / 选择 HITL |
| 触发 | 建议独立 `scope_db_mismatch_rounds >= 2` 后再进入候选选择 |
| 与放宽 | 优先「用户选标准台账」，放宽作可选兜底 |
