# 09 · NL2SQL 与结构化数据

> 面试定位：企业应用高频，和 RAG 并列的「数据基座」。重点是 **安全、Schema Linking、自修正**，不是把表结构全塞进 Prompt。  
> 预计：45 分钟。  
> 本项目锚点：`app/nl2sql/*`；`POST /nl2sql/query` 可独立集成；客服 `data_query` 内嵌同一服务；只读 SELECT 校验；schema/biz/qa 多命名空间 RAG。

---

## 0. 30 秒能讲清楚

NL2SQL（Text-to-SQL）把自然语言变成 **受控 SQL**。难点是歧义、库表太大、业务口径、注入风险。做法是：**先链到相关表/字段 → 检索业务口径与金样例 → 生成 → 静态校验 → 执行（或 dry-run）→ 失败自修正 → 结果自然语言化**。绝不能让模型直接连库裸跑。

---

## 1. 和 RAG 的分工（必考）

| | RAG | NL2SQL |
|--|-----|--------|
| 数据 | 非结构化文档 | 关系数据库 |
| 输出 | 带引用的段落答案 | 数字/表格 + 解释 |
| 对错 | 软（语义） | 硬（SQL 对错、口径） |
| 风险 | 幻觉 | **写库、拖库、错口径** |

同一客服里用 **意图分流**：问制度走 RAG，问「上个月超温次数」走 NL2SQL。本项目就是这样。

---

## 2. 典型流水线

```text
问句 → 时间/范围解析与改写 → Schema Linking
     → Schema/业务/QA 样例 RAG → Prompt 生成 SQL
     → 安全校验（只 SELECT、禁多语句、限表）
     → 执行 → 空结果/语法错则修正 → 结果解释
```

本项目还有问句意图、缓存、指纹（相似问复用）等，面试提到「缓存要绑 schema 版本和口径」。

---

## 3. Schema Linking

库有几百张表时，不能全塞上下文。

做法：

- 用向量/关键词召回表名、字段、注释  
- 业务词典（机组、专业）约束  
- 金样例 QA：相似问直接提供 SQL 骨架  
- 显式列出 **允许的表**，生成后校验不在白名单则拒绝  

**歧义**：「温度」可能是主汽温或壁温。要用范围解析 + 澄清，而不是猜。

---

## 4. 时间与范围（工业场景加分）

口语：「昨天白班」「这次检修以来」「#3 炉」。需要：

- 相对时间 → 绝对时间窗  
- 默认时区、班次制度  
- 实体规范化（厂/机组编码）  

本项目有时间与范围窗口解析改写方案。面试讲：**先改写成规范问句，再生成 SQL**，比让模型同时做三件事稳。

---

## 5. 安全（一定要主动讲）

| 规则 | 为什么 |
|------|--------|
| 只读账号 | 即便 SQL 绕过校验 |
| 只允许单条 SELECT | 禁 DROP/UPDATE；禁 `;` 拼接 |
| 表/字段白名单 | 防跨库、防敏感列 |
| LIMIT | 防全表拖出 |
| 超时与最大行数 | 防慢查询打爆库 |
| 参数化 | 拼接用户字符串进 SQL 是事故 |
| 审计日志 | 谁在何时查了什么 |

校验应是 **解析 AST**（sqlglot 等），不是正则黑名单。

---

## 6. 自修正与执行

失败类型：语法错、字段不存在、空结果、超时、超行。

策略：把 **引擎报错 + schema 片段** 回灌模型改一次，限制轮数（1~2）。空结果不一定是 SQL 错，可能是时间窗不对——要和用户澄清，不要瞎改表。

结果解释：表格不要原样丢给领导，用模板/二次 LLM **只基于结果行** 描述，防止脱离数据发挥。

---

## 7. 评测

- **执行准确率**（EX）：跑出来的结果集对不对（比字符串相等的 SQL 更合理）  
- 精确匹配 / 成分匹配（表、选择列、过滤）  
- 业务口径集（金标问句）  
- 延迟与缓存命中率  

不要只 demo 三句「会写 SQL」。公开榜：**Spider**（干净学术库）、**BIRD**（脏值与效率，更接近企业）、**Spider 2.0**（更长上下文/真实套件）。见 [21](./21-评测基准与行业榜单.md)。

行业方法名（认得即可）：DIN-SQL（分解子问题）、DAIL-SQL（样例选择）、C3、RESDSQL（schema 编码）。生产仍是 **linking + 样例 + 校验 + 修正** 这条工程链，论文名词加分但不替代安全。

除 SQL 外还有：Text-to-Pandas、指标中台 API、Cube/语义层。口径稳定时 **先语义层再 NL**，比让模型直接 join 底表更稳。

## 8. 高频问答

**Q：为什么不直接给模型看全部 schema？**  
A：超窗口、噪声表诱导乱 join、泄露无关敏感表。必须 linking。

**Q：LLM 生成 SQL 能保证对吗？**  
A：不能。所以校验 + 只读 + 评测集 + 必要时澄清。

**Q：和 ChatBI / Agent 查数的区别？**  
A：NL2SQL 是受控生成 SQL；Agent 还可能选图、选 API。企业里 SQL 仍是最通用落地。

**Q：缓存怎么做？**  
A：问句规范化后哈希；key 含 schema 版本、权限、时间是否相对。相对时间不能缓存「昨天」的死结果除非键含日期。

**Q：多表 join 幻觉？**  
A：样例 RAG、限制 join 深度、外键元数据、执行计划检查。

---

## 9. 本项目怎么答

> NL2SQL 是独立基座：schema 同步、三命名空间 RAG（schema/biz/qa）、Prompt 生成、只读校验、自检修正。HTTP 可单独给 BI 调；客服意图为 data_query 时内嵌同一服务且不重复写会话。分析智能体按槽位多次查数再合成。安全默认只 SELECT。

---

## 10. 速记口诀

> **先链表，再生成；先校验，再执行；先限权，再缓存。**  
> **问文档走 RAG，问数字走 SQL。**
