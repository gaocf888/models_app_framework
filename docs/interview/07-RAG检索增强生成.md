# 07 · RAG 检索增强生成

> 面试定位：应用开发第一考点。要能画全链路，并能排查「幻觉到底出在哪一层」。  
> 预计：70~90 分钟。  
> 本项目锚点：摄入 8 步编排；语义+关键词+metadata → RRF → CrossEncoder；namespace 启用/优先级；BASIC/AGENTIC；默认 ES/EasySearch，可选 FAISS；嵌入/重排默认 MIS-TEI。

---

## 0. 30 秒能讲清楚

RAG = **检索私有知识 + 把证据塞进 Prompt 再生成**。解决模型知识过期、幻觉、不可引用。生产级不是「向量库 top_k」，而是 **摄入治理 + 多路召回 + 融合重排 + 场景路由 + 引用与拒答**。

---

## 1. 标准链路（对着画）

```text
文档 → 解析/清洗 → 切块 → 嵌入/索引
用户问题 →（可选改写/指代消解）→ 多路召回 → 融合 → 重排
→ 拼证据 Prompt → LLM → 带引用的答案
```

本项目摄入 8 步：`validate → parse → clean → chunk → enrich → index → quality_check → finalize`。

检索：`semantic + keyword + metadata` → **RRF** → **CrossEncoder**（如 Qwen3-Reranker / bge-reranker）。

---

## 2. 切块（Chunking）——最容易被问穿

| 策略 | 做法 | 适合 | 风险 |
|------|------|------|------|
| 固定滑窗 | size + overlap | 纯文本底线 | 切断句子/表格 |
| 结构切分 | 标题/段落/Markdown | 手册、规程 | 依赖解析质量 |
| 语义切分 | 相似度断点 | 叙事文本 | 慢、不稳 |
| 父文档 / 小检索大切生成 | 小 chunk 召回，大窗口生成 | 要精度又要完整 | 实现复杂 |
| 表格/图片专项 | 描述 + 原文/图 URL | 报告、图纸 | 管道要分支 |

本项目默认 **structure**，`chunk_size≈500`，`overlap≈80`，`min_chunk≈40`。面试带上这些数量级。

原则：

- 一块表达一个完整事实  
- overlap 防止边界答案被切开  
- 元数据必须带上：doc、页、版本、namespace、权限  

**解析**：PDF/扫描件要用 OCR/版面（如 MinerU），否则「检索差」其实是「字都没提对」。

---

## 3. 嵌入与向量

- 中文常用 bge / gte / 厂商 embedding  
- **query 和 doc 是否对称**：有的模型 query 要加 instruction  
- 维度（本项目 MIS-TEI 侧常见 1024）影响存储与召回  
- **归一化**后才能用点积当余弦  

不要用聊天大模型的最后一层当向量（除非它就是 embedding 模型）。

---

## 4. 检索：为什么不能只靠向量

| 通道 | 擅长 | 不擅长 |
|------|------|--------|
| 语义向量 | 同义、改写 | 精确编号、专有代号、少语料术语 |
| 关键词/BM25 | 精确匹配、编号 | 同义表达 |
| metadata | 厂/机组/时间/类型过滤 | 单独当搜索 |
| 图谱 | 关系、多跳 | 文档原文细节 |

**混合检索**是工业默认。本项目三路召回后 RRF 融合。

### 4.1 RRF（Reciprocal Rank Fusion）

\[
\mathrm{RRF}(d)=\sum_{\text{通道}} \frac{1}{k + \mathrm{rank}_i(d)}
\]

不依赖分数可比较（向量分和 BM25 分不可直接比）。\(k\) 常取 60。

### 4.2 重排 Rerank

召回 20~50，用 **CrossEncoder** 看「query+doc」真相关性，留 top_n。比双塔准、比全库扫可行。

本项目场景 profile 不同：分析 top 更宽，NL2SQL 更窄。面试讲 **「召回要宽、进模型要窄」**。

## 5. 进阶形态

| 形态 | 一句话 | 本项目 |
|------|--------|--------|
| Naive RAG | 单次检索+生成 | BASIC 模式 |
| HyDE | 先生成假答案再检索 | 可选思路 |
| 查询改写 / 多 query | 解决口语、指代 | C-RAG 低分重写 |
| Agentic RAG | 计划→多步检索→够不够再搜 | `RAGMode.AGENTIC` |
| GraphRAG | 实体关系辅助 | Neo4j，配置开关 |
| Self-RAG / CRAG | 自判证据是否够 | 质量门、软直通闸 |

**GraphRAG 不是替代向量**，是补「关系/全局摘要」。本项目 `RetrievalPolicy`：vector / graph / hybrid。

行业里还会听到（不绑本仓库）：

| 名词 | 一句话 |
|------|--------|
| RAPTOR | 递归摘要树，适合问「整本书主题」 |
| ColBERT / 晚交互 | token 级 MaxSim，比双塔准、比交叉便宜一档 |
| SPLADE | 可学习稀疏表示，补词法 |
| Corrective RAG | 检索质量差则 web/再检索 |
| Self-RAG | 模型决定是否检索、是否批判证据 |
| 查询分解 | 多跳拆子查询并行搜 |
| 假设文档 HyDE | 先写假答案再嵌入检索，领域偏移时不稳 |

向量库与 ANN 横向对比见 [22](./22-嵌入向量库与检索引擎.md)。公开 RAG/嵌入榜见 [21](./21-评测基准与行业榜单.md)。

## 6. 生成与防幻觉

- Prompt：只根据编号证据；没有则澄清或拒答  
- **引用对齐**：答案句子能指回 chunk；无引用当风险  
- 温度降低  
- 软直通：最高 rerank 分过阈才「确信回答」  
- 权限：检索阶段按 ACL 过滤，不要生成后再删（会泄漏）

评测指标见 [11](./11-评测对齐与可观测性.md)：召回率、nDCG、引用率、答案正确率、拒答正确率。

---

## 7. 工程治理（企业加分）

- **namespace / 租户**：本厂库 vs 通用库；`kb_enabled`、`priority`（数字越小越优先）  
- 版本与幂等删除  
- 异步摄入、质量门（chunk 太少/太空失败）  
- 嵌入服务进程内单例或独立 TEI，避免每请求加载模型  
- 图片：存 MinIO，chunk 带 URL，多模态问答再拉图  

---

## 8. 效果差怎么拆（面试必背）

按层问：

1. **解析**：文本是否乱码、表格是否散  
2. **切块**：答案是否跨块、块是否过大稀释  
3. **query**：指代未消解、该走 SQL 却走了文档  
4. **召回**：三路是否都开、过滤是否过严、namespace 是否错  
5. **融合/重排**：好文档 rank 低；重排模型是否匹配语言  
6. **生成**：证据在但模型没用 → Prompt/窗口/中间迷失  
7. **知识不在库**：该摄入或该 NL2SQL，不是调参能解决

## 9. 高频问答

**Q：chunk 多大？**  
A：没有万能值。中文手册常见 300~800 字，overlap 10%~20%。以「一块一事 + 评测」为准。我们默认 500/80。

**Q：top_k 越大越好吗？**  
A：召回阶段可以大，送进 LLM 的上下文过大则噪声、时延、中间丢失一起增加。靠 rerank 收口。

**Q：RAG 还要不要微调？**  
A：要微调「引用格式、拒答、领域语气」；不要微调「把整本制度背进权重」。

**Q：向量库怎么选？**  
A：ES/EasySearch：全文+向量+过滤一体，运维贴近搜素；Milvus/Qdrant 向量强；FAISS 本地/离线。我们生产默认 EasySearch，开发可 FAISS。

**Q：Agentic RAG 会不会更慢？**  
A：会多轮检索和规划。只对复杂多跳开，简单 QA 走 BASIC。

---

## 10. 本项目怎么答（浓缩）

> RAG 是基座能力：摄入 8 步可观测；检索三路 + RRF + CrossEncoder；按场景调 top_k；支持 namespace 启停和优先级；编排层 BASIC/AGENTIC 可切；存储默认 EasySearch。客服在意图 `kb_qa` 时走这条链，低分会 query rewrite 再检索。嵌入重排默认独立 TEI 服务，避免和在线 API 抢进程。

---

## 11. 速记口诀

> **切好块，多路召，RRF 融，交叉排，带引用。**  
> **先定位坏在哪一层，再调参。**
