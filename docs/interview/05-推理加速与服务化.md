# 05 · 推理加速与服务化

> 面试定位：这是平台岗核心、应用岗高频。要能讲 KV、PagedAttention、Continuous Batching、vLLM。  
> 预计：60 分钟。  
> 本项目锚点：`vllm-deploy/` 提供 OpenAI 兼容 HTTP；应用用 `VLLMHttpClient` / LangChain ChatOpenAI；`LLM_DEFAULT_ENDPOINT` 可切云或本地。

---

## 0. 30 秒能讲清楚

LLM 推理分 **Prefill（吃 Prompt）** 和 **Decode（逐 token）**。Decode 反复读写 KV Cache，瓶颈常在显存带宽。vLLM 用 **PagedAttention** 把 KV 分页，配合 **Continuous Batching** 让 GPU 一直有活干，从而在同样显存下提高并发和吞吐。应用侧还要通过 **截断输入、控 max_tokens、前缀缓存、少调用** 把负载降下来。

---

## 1. 指标（先会算账）

| 指标 | 含义 | 谁关心 |
|------|------|--------|
| TTFT | 首 token 时延 | 流式体验 |
| TPOT / ITL | 每输出 token 间隔 | 打字流畅度 |
| 吞吐 tokens/s | 系统总产出 | 容量规划 |
| 并发 / QPS | 同时请求数 | 网关与排队 |
| 显存占用 | 权重 + KV + 激活 | 能跑多大模型、多大 batch |

关系：提高吞吐往往牺牲单请求尾延迟；Continuous Batching 就是在两者间找利用率。

本项目还有业务指标：SSE 是否断流、历史裁剪后是否丢关键指代。

---

## 2. KV Cache（所有加速的底座）

第 \(t\) 步生成只需当前 token 的 Q，与缓存的 \(K_{1:t-1}, V_{1:t-1}\) 做注意力。

占用粗估（面试够用）：

\[
\mathrm{KV} \approx 2 \times L \times n_{\mathrm{layers}} \times n_{\mathrm{kv\_heads}} \times d_{\mathrm{head}} \times \mathrm{bytes}
\]

再乘 batch。GQA 减少 `n_kv_heads`；量化减少 `bytes`。

**前缀缓存（Prefix Caching）**：系统 Prompt、RAG 模板相同前缀可复用 KV，降 TTFT。多租户要按前缀哈希命中。

---

## 3. PagedAttention 与显存碎片

传统实现：每请求预留「最大长度」的连续 KV，短请求浪费，长请求难以插入 → **内部碎片**。

PagedAttention（vLLM）：KV 像虚拟内存一样 **按块（page/block）分配**，逻辑连续、物理离散。好处：

- 显存按实际生成长度增长  
- 更容易做并行采样、共享前缀  
- batch 里能塞进更多请求

面试别只会背名字：要说到 **「按最大长度预留 vs 按块分配」**。

---

## 4. Continuous Batching（持续批处理）

静态 batch：等最慢的那条生成完，短请求被拖死。

持续批处理：某个请求 EOS 后，**立刻插入新请求的 prefill**，decode 步对齐执行。GPU 利用率高。

和 **动态 batch / 等待组批** 的区别：后者是在入口等齐再发；vLLM 是在迭代级调度。

## 5. 其他加速手段

| 技术 | 原理 | 注意 |
|------|------|------|
| 投机解码 Speculative | 小模型出草稿，大模型一次验证多 token | 草稿命中率低则更慢；领域偏移要命中 |
| 并行采样 | 同前缀多候选 | 费 KV |
| CUDA Graph | 减少 CPU launch 开销 | 形状固定时收益大 |
| FlashAttention | IO-aware 注意力 | 训练推理都用 |
| 量化 | 见 04 | kernel 必须跟上 |
| 拆分预填充 | chunked prefill | 超长 Prompt 避免饿死 decode |
| 约束解码 / logits 处理器 | JSON/语法掩码 | NL2SQL、结构化输出 |

**张量并行 TP**：多卡切一层，降单卡权重与部分 KV。延迟可能因通信上升。适合单模型服务多卡。

### 5.1 行业补充：PD 分离、Radix、调度

| 技术 | 要点 |
|------|------|
| Prefill/Decode 分离（PD 分离） | 预填充和解码集群拆开，避免长 Prompt 饿死短解码；业界高水位方案 |
| Chunked prefill | 长预填充切块，与 decode 交错 |
| RadixAttention（SGLang） | 用前缀树复用多轮/多分支 KV，适合 Agent 和并行采样 |
| 抢占 / 优先级队列 | 交互请求优先于离线批 |
| Disaggregated KV | KV 可放 CPU/远端，换容量（延迟上升） |
| 推测解码变体 | 草稿模型、Medusa/EAGLE 多头、查找表；看接受率 |
| TensorRT-LLM | 编译期图优化，换引擎成本高、NVIDIA 极致性能 |

调度面试句：

> 在线系统要把 **交互短请求** 和 **长预填充/长报告** 隔离队列，否则 P95 会被长任务拖死。

## 6. 引擎怎么选

| 引擎 | 定位 |
|------|------|
| **vLLM** | 数据中心高吞吐，PagedAttention + 持续批处理，OpenAI API |
| SGLang | Radix 前缀树 KV、结构化生成、Agent/多分支友好 |
| TensorRT-LLM + Triton | NVIDIA 编译期优化与多模型并发，换引擎成本高 |
| TGI | Hugging Face 生态，上手快 |
| llama.cpp / Ollama / MLX | 端侧、CPU、苹果芯片、快速试用 |
| 厂商运行时 | 昇腾 MindIE、寒武纪等，国产私有化必问 |

本项目策略：**应用只依赖 OpenAI 兼容接口**，换引擎不改业务代码。这是面试加分设计。

## 8. 服务化架构（结合本项目讲）

```text
Client → FastAPI (鉴权/限流/SSE)
       → Service (会话/RAG/编排)
       → LLMClient (httpx 复用)
       → vLLM OpenAI API (continuous batch + paged KV)
```

要点：

- LLM 调用异步，避免阻塞 event loop  
- 连接池复用，不每次新建 Client  
- 推理与训练进程分离  
- 超长/过载：排队、降级（关 RAG、缩短历史、切小模型）  
- 流式：SSE `delta` + `stop`；取消要能传到后端（尽力而为）

基准脚本：仓库有 `benchmarks/bench_llm_infer.py`、`bench_vllm_chat_completions.py`，面试可提「我们用脚本压 TTFT/吞吐」。

## 9. 慢请求排查清单（高频实战题）

1. Prompt 是否过长（历史+RAG 堆满）  
2. 是否同步阻塞、重复建连  
3. vLLM 是否已达 KV 上限（抢占、抢占抖动）  
4. 量化 kernel / 图编译是否生效  
5. 业务是否串行多次 LLM（意图+改写+生成+润色）  
6. 输出太长（报告场景）——该不该分段生成  

本项目客服：意图可用规则/BERT，避免每轮都上大模型分类。

## 10. 高频问答

**Q：为什么 Decode 吃带宽？**  
A：每步计算量小，但要读全部历史 KV，算术强度低，卡在内存。

**Q：PagedAttention 和操作系统分页？**  
A：类比虚拟内存：逻辑块表映射物理 KV block，减少预留浪费。

**Q：投机解码一定会快吗？**  
A：不一定。验证失败要回滚。草稿模型和目标模型分布要近。

**Q：如何提高同一 GPU 并发？**  
A：GQA/MLA、KV 量化、PagedAttention、缩短输入、限制 max_tokens、前缀共享。

**Q：流式和非流式对引擎的差别？**  
A：引擎都是逐 token；流式是把 token 立刻回推。TTFT 对体验更敏感。
