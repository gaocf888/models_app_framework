# 13 · 本项目技术栈对照面试话术

> 用法：把下面「一段话」改成你真实参与过的模块。没做过的删掉，被追问会穿。  
> 对应实现说明在 `framework-guide/`，此处只给 **面试口述**。

---

## 1. 项目一句话

> 一套面向工业场景的 **大小模型应用基座**：统一 FastAPI 接入，大模型用 vLLM（OpenAI 兼容）+ LangChain/LangGraph 编排，沉淀 RAG、NL2SQL、智能客服、综合分析/看图诊断、LoRA 训练和小模型视频通道，并补齐观测与国产化部署。

---

## 2. 架构 90 秒

> 接入层 FastAPI，负责鉴权、限流、SSE。  
> 编排层 LangGraph：客服按意图走知识问答或 NL2SQL；综合分析做规划、检索、取数、成文；看图诊断是视觉、SQL、RAG 并行再合成。  
> 知识层：文档走混合检索 RAG（ES/EasySearch，RRF + 重排，namespace 治理）；结构化数据走 NL2SQL 基座，只读校验。  
> 模型层：聊天走独立 vLLM；向量和重排走 MIS-TEI；检测类小模型走通道架构。  
> 训练：PEFT LoRA + HF Trainer，和在线镜像分开。  
> 基础设施：Redis 会话、Prometheus/LangSmith、MinIO 存图。

可画四层：接入 / 编排 / 模型与知识 / 数据基础设施。

## 4. 技术选型答辩（为什么这样选）

**为什么 LangGraph 而不是纯 Agent？**  
主路径要可控、可观测、可降级。自由 Agent 步数和费用不可预期。节点里该调服务就调服务。

**为什么 EasySearch 而不是只上 Milvus？**  
要同时做向量、关键词、metadata 过滤和运维习惯贴近 ES。开发可用 FAISS。

**为什么嵌入独立 TEI？**  
避免每个 API worker 加载一份模型；嵌入和重排与生成扩缩比不同。

**为什么 NL2SQL 做成基座？**  
客服、分析、外部 BI 都要问数，安全策略必须只有一份。

**为什么训练不用全参、不以 Factory 为主？**  
领域适应 LoRA 足够；自研通道好接标注和权限；Factory 留给实验。

**为什么大小模型分开？**  
生成 vs 视频检测的调度、线程模型、依赖完全不同；统一只在 API 与监控。

## 5. 量化成绩怎么说（没有数也要有结构）

优先用你真实的：

- 某类客服人工改写率、SQL 执行正确率、摄入任务成功率  
- TTFT、并发路数、GPU 卡数  
- 文档量、namespace 数  

没有数就说 **评测方法**：金标集、分层指标、trace 回放。不要编造。

## 6. 难点与复盘（准备 2 个）

**难点示例 A：检索噪音 vs  gener 幻觉**  
先分层定位。我们加了重排、引用约束、低分改写和 namespace，避免全库混召。

**难点示例 B：上下文顶满 vLLM**  
历史+证据+max_tokens 联合预算，动态压输出长度；分析长报告改分段。

**难点示例 C：NL2SQL 口径**  
时间窗改写 + 业务词典 + qa 样例；空结果走澄清而不是乱改表。

**难点示例 D：国产离线**  
厂商基镜像不覆盖业务依赖，离线 wheel 再提交镜像，应用仍走兼容 API。

## 8. 诚实边界（建议主动说）

按你实际情况勾选：

- 预训练 / 完整 RLHF：只用到开源基座与 SFT  
- GraphRAG：有骨架，深度因项目而异  
- 推理内核：用 vLLM，不自研 PagedAttention  
- 评测：有的环境 LangSmith 未全量开启  

主动划边界显得专业。
