# 08 · Agent 与工作流编排

> 面试定位：会区分「单次 LLM」和「有状态多步系统」；能讲 ReAct、Tool Calling、LangGraph。  
> 预计：50~60 分钟。  
> 本项目锚点：LangGraph 客服 / 综合分析 V2 / 看图诊断并行图 / 分析智能体分槽流水线；LangChain 用于编排而非堆业务。

---

## 0. 30 秒能讲清楚

Agent = 模型在循环里 **决策 → 调工具 → 观察 → 再决策**，直到能回答。生产上更稳的是 **预定义状态机（Graph）**：节点是确定性代码或 LLM，边是路由规则。本项目原则：**该写死的流程写成图，不要让模型自由乱跑。**

---

## 1. 几种形态

| 形态 | 控制权 | 适合 | 风险 |
|------|--------|------|------|
| 单 Prompt | 无 | FAQ、摘要 | 复杂任务崩 |
| Chain | 开发者固定顺序 | 提取→检索→生成 | 难分支 |
| **LangGraph / 工作流** | 开发者定义节点与边 | 企业主路径 | 图要维护 |
| ReAct 自由 Agent | 模型选工具 | 探索性、工具多 | 死循环、费、不可控 |
| Multi-Agent | 多角色分工 | 报告多章节、辩论 | 协调与费用 |

面试金句：

> 业务主路径用 Graph；只有分支组合爆炸、工具集开放时，才给模型有限的 tool-calling 自主权。

---

## 2. ReAct 与 Tool Calling

**ReAct**：Reason + Act。Thought → Action(tool, args) → Observation → … → Answer。

**Function / Tool Calling**：模型输出结构化 `name + arguments`，由运行时执行，比「解析自然语言我要搜xxx」稳。

设计工具的原则：

- 少而精，描述写清 **何时用/何时不用**  
- 参数要有 schema 和校验  
- 超时、重试、幂等  
- 把「搜知识库 / 跑 SQL / 看图」做成工具，而不是让模型假装查过  

本项目 NL2SQL、RAG 更多是 **图节点内调用服务**，不是完全开放的工具箱——更可控，也更好讲安全。

---

## 3. 规划、记忆、终止

- **规划**：先拆子任务（分析报告、多槽位）。计划要可失效重规划。  
- **记忆**：工作记忆=当前 state；长期=会话/摘要/向量。  
- **终止条件**：达到答案、超过步数、工具连续失败、用户取消。  
- **人机协同（HITL）**：缺槽位就澄清，看图诊断结构化解析不过就打回。  

没有终止条件的 Agent 是事故源。

---

## 4. LangChain vs LangGraph（必问）

| | LangChain | LangGraph |
|--|-----------|-----------|
| 强项 | 组件、模型/工具抽象、快速链 | 有状态循环、分支、持久化、人在回路 |
| 弱项 | 复杂控制流绕 | 要自己设计节点 |

本项目用法：ChatOpenAI / Prompt / 少量 Chain；**客服和分析主链路在 Graph**。面试说「编排用 LC，状态机用 LG」即可。

其它框架：LlamaIndex（RAG 重）、Semantic Kernel、自研状态机。面试官听 **你为什么选**，不听名词清单。

## 5. 本项目四条编排（对着讲）

### 5.1 通用推理

可选 planner → RAG → 生成。`rag_mode=basic|agentic`。默认保持简单。

### 5.2 智能客服图（主叙事）

典型节点：载模板 → 历史 → **意图**（规则/BERT/轻量 LLM）→ 分流：

- `kb_qa`：选引擎 → namespace → 检索 → 质量检查 → 低分改写重试 → 流式生成  
- `data_query`：内嵌 NL2SQL（不重复记会话）  
- `clarify`：追问  

另有故障案例门控、流式 SSE、`stop`。失败可回退 legacy 链。

**为什么是图**：意图分支、检索重试、指代和锚点，线性代码会变成面条。

### 5.3 综合分析 / 看图诊断

规划 + RAG +（看图时）视觉 ‖ NL2SQL ‖ 业务 RAG → 合成报告。看图诊断是并行子图再汇合。

### 5.4 分析智能体

分槽 NL2SQL 流水线 + SSE：每个槽位取数，再汇总。展示 **多 Agent/多槽** 比「一个超级 Prompt 写万字报告」更稳。

## 5.5 行业补充：框架、协议与热门 Agent 形态

| 名称 | 怎么记 |
|------|--------|
| OpenAI Swarm / Agents SDK | 轻量交接 handoff |
| AutoGen / CrewAI | 多角色对话式，Demo 快，生产要自己加约束 |
| LlamaIndex Workflows | RAG 重的事件流 |
| Semantic Kernel | 微软生态、插件规划 |
| MCP | 工具插线板，不是编排器，见 [23](./23-结构化输出工具协议与MCP.md) |
| 代码 Agent | 检索仓库 + 改文件 + 跑测试（SWE-bench 叙事） |
| 浏览器 / Computer Use | 高危，必须沙箱 |
| 深度研究 Agent | 多步搜索+引用长文，费用高 |

记忆不要只靠对话窗口：工作记忆 / 情节 / 语义分层见 [18](./18-长上下文记忆与测试时计算.md)。安全见 [20](./20-安全红队与合规.md)。评 Agent 用 GAIA、SWE-bench、τ-bench 等见 [21](./21-评测基准与行业榜单.md)。

## 6. 何时不上 Agent

- 单轮知识问答：RAG 足够  
- 延迟极敏感：每多一跳多一次 LLM  
- 合规路径必须确定：用规则+图，不让模型选「要不要过校验」  
- 工具只有一个且总要调：直接调用

## 7. 可靠性设计

| 问题 | 对策 |
|------|------|
| 死循环 | max_steps、重复工具检测 |
| 幻觉调用 | schema 校验、允许集合枚举 |
| 部分失败 | 节点级重试、降级、返回已有证据 |
| 不可复现 | state 落盘、LangSmith、trace_id |
| 费用 | 小模型做路由，大模型只做生成 |

## 8. 高频问答

**Q：Agent 和 Workflow 区别？**  
A：Workflow 边是确定的；Agent 下一步由模型选。生产常是 **Workflow 为主、节点内偶尔 Agent**。

**Q：多 Agent 一定更好吗？**  
A：不一定。通信损耗大。适合天然分工（检索员/写手/审校）且有汇总协议。

**Q：怎么评 Agent？**  
A：任务成功率、平均步数、工具错误率、时延、费用；用轨迹看是否绕路。

**Q：Plan-and-Execute vs ReAct？**  
A：先出计划再执行，适合长任务、好展示进度；ReAct 适合短、环境反馈强。分析报告偏前者。

## 9. 速记口诀

> **主路径画成图，工具要带壳，步数必须封顶。**  
> **路由用小模型，生成用大模型。**
