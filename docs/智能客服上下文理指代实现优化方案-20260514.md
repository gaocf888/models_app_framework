# 智能客服上下文指代（Coreference / Anaphora）实现优化方案

**版本**：2026-05-14  
**范围**：智能客服（Chatbot）多轮对话中的代词、省略、对比、确认等指代消解与生成约束。  
**目标**：在**企业级生产**环境下，系统性降低「指代不明套话」「忽略上一轮已给信息」等问题，并与现有 LangGraph 主链路、Legacy 流式、RAG、会话存储对齐。

---

## 1. 背景与问题定义

### 1.1 典型失败形态

| 场景 | 用户表达 | 常见错误回复 |
|------|----------|--------------|
| 对比指代 | 上一轮助手分两点说明，本轮问「两者的区别是什么」 | 要求用户再说「哪两个」，忽略对话内已列两项 |
| 元话语确认 | 「你确定吗？」 | 泛化澄清，未承接上一轮结论 |
| 序位指代 | 「第二点展开」「前者为什么」 | 未对齐助手上一轮编号或顺序 |
| 省略主语 | 「怎么处理？」「为什么？」 | 未绑定上一轮主题实体 |

根因归纳：**短句/弱自立 utterance** 在缺少显式「对话锚」时，模型易被 **RAG 噪声** 或 **安全澄清话术** 带偏；仅靠静态 prompt 无法覆盖开放集说法。

### 1.2 与现有实现的关系

当前仓库已具备（可复用、扩展）：

- 多轮历史：`ConversationManager` + `load_history` → `history_messages` → `kb_build_messages`（`app/llm/graphs/chatbot_graph_runner.py`）。
- 确认类短句的 **检索 query 融合**：`app/llm/graphs/chatbot_retrieval_query.py`（`build_retrieval_query_for_chatbot`、`format_rag_snippets_system_block`）。
- 会话规则模板：`configs/prompts.yaml`（`chatbot` 各 version）。
- 流式结束 meta：`rag_citations`、`suggested_questions` 等。

**缺口**：指代类型未系统化枚举；**「两者/区别/对比」** 等未统一走检索增强与 **对话锚块**；无 **会话级结构化槽位** 与 **评测门禁**。

---

## 2. 总体架构原则（企业级）

1. **分层解耦**：检测（轻量）→ 锚定材料（确定性）→ 检索增强（可选）→ 生成约束（prompt/块）→ 观测与评测。
2. **默认可降级**：规则/本地逻辑失败不得阻断主链路；缺失锚时行为可配置（保守澄清 vs 复述假设）。
3. **双轨一致**：**LangGraph 主路径** 与 **Legacy 流式**（`ChatbotService._stream_chat_legacy_events`）行为对齐，避免灰度时体验分叉。
4. **可观测**：结构化日志 +（可选）LangSmith metadata：`anaphora_type`、`retrieval_augmented`、`anchor_block_len`。
5. **隐私与合规**：锚块与槽位仅含业务会话内容，不落第三方；日志脱敏（用户标识哈希化等按现有规范）。

## 3. 指代类型参考清单（实现与评测共用）

建议在代码与文档中统一枚举（示例名，可调整）：

| 代码 | 说明 | 典型触发词/模式 |
|------|------|------------------|
| `pair_compare` | 双实体对比 | 两者、二者、这两个、区别、异同、对比 |
| `ordinal` | 序位/分点 | 第 N 点、前者、后者、上面两点、第一条 |
| `single_entity` | 单实体回指 | 它、这个、该设备、上述现象 |
| `meta_confirm` | 对结论的确认/质疑 | 确定吗、真的吗、靠谱吗、有依据吗 |
| `ellipsis` | 省略主语/主题延续 | 「怎么办」「为什么」且极短、依赖上文 |
| `continuation` | 展开/补充 | 详细说说、继续、展开第二点 |
| `none` | 无特殊指代 | 完整问句、自带实体 |

**说明**：自然语言为开放集；枚举用于 **路由与检索策略**，边界 case 归 `none` 或走 P3 小模型。

## 4. 分阶段实施方案（P0～P3）

### 4.1 P0：指代触发检测 + 检索 Query 融合（优先）

**目标**：对「弱可独立语义」的短句，统一将 **检索 query** 与 **会话尾部 user+assistant 摘要** 融合，减少向量检索飘移；与现有 `build_retrieval_query_for_chatbot` 扩展对齐。

**技术要点**

1. **新建或扩展模块**（建议）：`app/llm/graphs/chatbot_retrieval_query.py`  
   - 在 `is_confirmation_short_query` 旁增加 **`is_anaphora_retrieval_boost_query(query: str) -> bool`**，或合并为 **`should_fuse_history_for_retrieval(query, history) -> bool`**，内部按类型匹配：
     - 对比：`两者|二者|区别|对比|异同|哪个更` 等；
     - 序位：`第[一二三四五六七八九十0-9]+|前者|后者|第一|第二` 等；
     - 单实体短句：`^(它|这个|那个)` + 短长度阈值等（需防误杀，配合历史非空）。
   - **融合格式**：沿用现有「`【检索会话衔接】` + 上轮 user + 上轮 assistant + `【本轮用户原话】`」结构；可增加 **`【指代类型】pair_compare`** 一行供调试（不进用户可见回答）。

2. **调用点**（必须与现有一致）  
   - `ChatbotLangGraphRunner._node_kb_retrieve`：在现有 `rag_query` 计算处合并 P0 新规则。  
   - `ChatbotService._rag_context_and_citations`：Legacy / 非图 `chat()` 路径同样调用统一函数。

3. **配置项**（建议写入 `app/core/config.py` + `app/app-deploy/.env.example`）  
   - `CHATBOT_ANAPHORA_RETRIEVAL_FUSION_ENABLED`（默认 `true`）  
   - `CHATBOT_ANAPHORA_FUSION_MAX_CHARS`（与现有总长上限协调，如 2800）

4. **测试**  
   - 单元测试：`tests/test_chatbot_retrieval_query.py` 增加「两者区别」「第二点」等用例，断言 `rag_query` 含上轮摘要关键词。

**验收标准**

- 给定固定两轮脚本 + 第三轮短问，**检索 query** 日志中可见融合字段；`rag_citations` 与片段相关性主观抽检优于融合前基线。

### 4.2 P1：对话锚块（Dialogue Anchor Block）注入

**目标**：在 `kb_build_messages`（及 Legacy `_build_llm_messages`）中，当检测到需要锚定时，向 **system** 追加一段 **机器生成的、只读对话摘要块**，显式列出「可比较项 / 最近结论要点」，强制模型先绑定再作答。

**技术要点**

1. **新模块**（建议）：`app/llm/graphs/chatbot_dialogue_anchor.py`  
   - **`build_dialogue_anchor_block(history_messages, query) -> str | None`**  
     - 输入：与 `load_history` 同源列表（**不含本轮 user**，与现构图一致）。  
     - 输出：无锚需求时返回 `None`；否则返回一段固定格式的 Markdown/纯文本，例如：  
       `【对话锚·仅供推理】上一轮助手回复中可对照的要点（自动抽取）：\n1. ...\n2. ...\n本轮用户问题中的指代默认绑定以上条目（若仅一项则列出该项并说明另一项未识别）。`  
   - **抽取策略 v0（规则）**：  
     - 取最近一条 `role=assistant` 的全文；  
     - 按 `\n\n`、`\n`、编号 `^\d+[\.、]`、`- `、`* ` 切分候选行；  
     - 过滤过短行；合并为最多 **K 条**（如 K=6），首条过长截断。  
   - **抽取策略 v1（可选）**：对 assistant 文本做一次 **短 LLM**（`json`：`bullets: string[]`），超时则回退 v0。

2. **注入位置**  
   - 与 `format_rag_snippets_system_block` 同层：先模板 `system_prompt`，再 **对话锚块**（若有），再 RAG 块。  
   - 避免与用户可见产品文案混淆：块标题含 **「仅供推理」**，且不要求前端展示。

3. **触发条件**（与 P0 可共用检测结果）  
   - `pair_compare` / `ordinal` / 部分 `ellipsis` 为 true 且 `history_messages` 非空。

4. **风险与缓解**  
   - **误抽取**：块内加一句「若与本轮用户语义不符，以用户明确命名实体为准」。  
   - **Prompt 膨胀**：`CHATBOT_ANCHOR_BLOCK_MAX_CHARS`（如 1200）+ 条数上限。

**验收标准**

- 固定脚本「助手答两点 → 用户问两者区别」：回复中须先出现对两项的 **复述或编号对应**（可用自动化 judge 或人工抽检清单）。

### 4.3 P2：会话级结构化槽位（Structured Dialogue State）

**目标**：在 Redis/内存会话维度维护 **可指代对象列表**，在 assistant 落库后更新；下一轮指代 **优先读槽** 再拼锚块/检索，提高稳定性与可解释性。

**技术要点**

1. **数据模型**（示例 JSON，存 `conv:anaphora:{user_id}:{session_id}` 或并入现有 meta Hash）  
   - `topic`: 可选字符串  
   - `last_assistant_bullets`: `string[]`（最多 N）  
   - `last_entities`: `{ "label": str, "source": "user|assistant" }[]`（可选）  
   - `updated_at`: epoch  
   - `schema_version`: int（便于迁移）

2. **写入时机**  
   - `ChatbotLangGraphRunner._persist_success` / Legacy 落库 assistant 之后，调用 **`update_anaphora_slots(user_id, session_id, assistant_text)`**（异步队列可选，避免阻塞 SSE 尾帧）。  
   - 实现：规则抽取同 P1 v0，或与 P1 共用函数，仅多一步持久化。

3. **读取时机**  
   - `load_history` 之后或 `kb_build_messages` 前：读取槽位；若槽位与本轮检测类型一致，**锚块优先用槽位 bullets**（比纯文本 re-parse 稳）。

4. **一致性**  
   - 多 worker：必须 Redis；内存模式文档声明「槽位不跨进程」。  
   - TTL：与会话 TTL 对齐，避免幽灵键。

5. **配置**  
   - `CHATBOT_ANAPHORA_SLOTS_ENABLED`  
   - `CHATBOT_ANAPHORA_SLOTS_MAX_BULLETS`

**验收标准**

- 长 assistant 回复后，槽位条数与人工标注要点一致性抽检达标率 ≥ 目标阈值；指代轮次 **澄清率** 下降。

---

### 4.4 P3：小模型 Coref JSON + 评测门禁

**目标**：对规则与槽位均 **低置信** 的 utterance，调用 **一次轻量 LLM**（低 `max_tokens`、结构化 JSON），输出指代类型与建议绑定；并建立 **回归评测集** 防止迭代回退。

**技术要点**

1. **契约**（示例）  
   - 输入：`last_user`、`last_assistant`（截断）、`current_query`。  
   - 输出 JSON：`{ "type": "...", "confidence": 0-1, "anchor_indices": [0,1], "rationale_zh": "..." }`  
   - 校验失败 → 回退 P0/P1 规则路径。

2. **调用策略**  
   - 仅当 `rules_confidence < τ` 且 `CHATBOT_ANAPHORA_LLM_GATE_ENABLED=true`；  
   - 超时、429、内容审核失败 → 降级无 LLM。

3. **评测集**（`tests/fixtures/chatbot_anaphora_cases.yaml` 或独立目录）  
   - 每类指代 ≥10 条三轮对话脚本；  
   - CI：可选 **非 LLM** 断言（锚块是否生成、检索 query 是否融合）+ 周期性 **LLM-as-judge**（夜间任务）。

4. **观测**  
   - Metrics：`anaphora_llm_calls_total`、`anaphora_llm_fallback_total`、延迟直方图。

**验收标准**

- 灰区 case 人工盲评：指代正确率提升；P99 延迟在预算内。

## 6. 发布与灰度（企业级）

1. **特性开关**：P0～P2 各自独立开关，默认 P0 on、P1/P2 off，便于 A/B。  
2. **灰度维度**：按 `user_id` 哈希尾号或请求头 `X-Chatbot-Anaphora-Mode`（内网）放量。  
3. **回滚**：开关关闭即回退当前行为；槽位失败不影响主回答。  
4. **监控告警**：融合率、锚块生成率、LLM 门控失败率、平均 prompt tokens 上升阈值。

---

## 7. 安全与合规

- 锚块与槽位仅服务 **当次会话技术推理**，不在对外 API 中单独暴露为产品字段（除非产品明确要求「可解释性面板」）。  
- 日志中避免完整长文；仅记录类型、长度、哈希 id。  
- 跨租户：键必须带 `user_id` + `session_id`，防止串会话。
