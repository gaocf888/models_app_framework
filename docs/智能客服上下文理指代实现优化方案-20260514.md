# 智能客服上下文指代（Coreference / Anaphora）实现优化方案

**版本**：2026-05-14  
**范围**：智能客服（Chatbot）多轮对话中的代词、省略、对比、确认等指代消解与生成约束。  
**目标**：在**企业级生产**环境下，系统性降低「指代不明套话」「忽略上一轮已给信息」等问题，并与现有 LangGraph 主链路、Legacy 流式、RAG、会话存储对齐。

---

## 1. 背景与问题定义

### 1.1 典型失败形态

| 场景 | 用户表达 | 常见错误回复 |
|------|----------|--------------|
| 对比指代 | 上一轮助手分两点说明，本轮问「两者的区别是什么」 | 要求用户再说「哪两个」，忽略对话内已列两项 |
| 元话语确认 | 「你确定吗？」 | 泛化澄清，未承接上一轮结论 |
| 序位指代 | 「第二点展开」「前者为什么」 | 未对齐助手上一轮编号或顺序 |
| 省略主语 | 「怎么处理？」「为什么？」 | 未绑定上一轮主题实体 |

根因归纳：**短句/弱自立 utterance** 在缺少显式「对话锚」时，模型易被 **RAG 噪声** 或 **安全澄清话术** 带偏；仅靠静态 prompt 无法覆盖开放集说法。

### 1.2 与现有实现的关系

当前仓库已具备（可复用、扩展）：

- 多轮历史：`ConversationManager` + `load_history` → `history_messages` → `kb_build_messages`（`app/llm/graphs/chatbot_graph_runner.py`）。
- 确认类短句的 **检索 query 融合**：`app/llm/graphs/chatbot_retrieval_query.py`（`build_retrieval_query_for_chatbot`、`format_rag_snippets_system_block`）。
- 会话规则模板：`configs/prompts.yaml`（`chatbot` 各 version）。
- 流式结束 meta：`rag_citations`、`suggested_questions` 等。

**缺口**：指代类型未系统化枚举；**「两者/区别/对比」** 等未统一走检索增强与 **对话锚块**；无 **会话级结构化槽位** 与 **评测门禁**。

---

## 2. 总体架构原则（企业级）

1. **分层解耦**：检测（轻量）→ 锚定材料（确定性）→ 检索增强（可选）→ 生成约束（prompt/块）→ 观测与评测。
2. **默认可降级**：规则/本地逻辑失败不得阻断主链路；缺失锚时行为可配置（保守澄清 vs 复述假设）。
3. **双轨一致**：**LangGraph 主路径** 与 **Legacy 流式**（`ChatbotService._stream_chat_legacy_events`）行为对齐，避免灰度时体验分叉。
4. **可观测**：结构化日志 +（可选）LangSmith metadata：`anaphora_type`、`retrieval_augmented`、`anchor_block_len`。
5. **隐私与合规**：锚块与槽位仅含业务会话内容，不落第三方；日志脱敏（用户标识哈希化等按现有规范）。

## 3. 指代类型参考清单（实现与评测共用）

建议在代码与文档中统一枚举（示例名，可调整）：

| 代码 | 说明 | 典型触发词/模式 |
|------|------|------------------|
| `pair_compare` | 双实体对比 | 两者、二者、这两个、区别、异同、对比 |
| `ordinal` | 序位/分点 | 第 N 点、前者、后者、上面两点、第一条 |
| `single_entity` | 单实体回指 | 它、这个、该设备、上述现象 |
| `meta_confirm` | 对结论的确认/质疑 | 确定吗、真的吗、靠谱吗、有依据吗 |
| `ellipsis` | 省略主语/主题延续 | 「怎么办」「为什么」且极短、依赖上文 |
| `continuation` | 展开/补充 | 详细说说、继续、展开第二点 |
| `none` | 无特殊指代 | 完整问句、自带实体 |

**说明**：自然语言为开放集；枚举用于 **路由与检索策略**，边界 case 归 `none` 或走 P3 小模型。

### 3.1 指代类型清单在 P0～P3 哪个阶段实现？

**结论**：**清单本身（编码 + 语义定义）在 P0 一并冻结为工程契约**；各阶段实现的是「**检测能力覆盖范围**」与「**消费场景**」，逐层扩大，而非到 P3 才定义类型。

| 阶段 | 与「指代类型清单」的关系 | 实现内容 |
|------|--------------------------|----------|
| **P0** | **首次在代码中落地清单的子集检测**（规则），输出离散类型或 `none` | 用清单中的类型驱动 **「是否做检索 query 与历史融合」**；日志/Meta 可打 `anaphora_type`（可选）。不要求锚块、不要求槽位。 |
| **P1** | **清单全量类型参与「是否注入对话锚块」与锚块文案策略** | 在 P0 检测结果基础上，对清单内各类型配置 **锚块开关与模板句**（哪些类型必须注入、哪些仅加强 prompt）。 |
| **P2** | **清单与槽位字段对齐**：持久化「上轮可指代要点」，类型可作可选字段 | 槽位中建议存 `last_anaphora_type`（上轮用户问被归成的类型，可选）+ `last_bullets`；**下一轮** P0/P1 读槽辅助消歧。 |
| **P3** | **清单作为 LLM JSON 的封闭枚举**（schema `enum`） | 小模型输出必须在清单内 + `confidence`；与规则结果不一致时的仲裁策略。 |

**依赖关系**：P1～P3 **不得重新定义另一套编码**；若扩展类型，须先改清单（本文 §3.2）与代码枚举，再改各阶段逻辑。

### 3.2 工程使用清单（交付级：编码、触发、阶段消费）

下表为 **建议写入代码的单一事实来源**（如 `StrEnum` / 常量模块 `chatbot_anaphora_types.py`）的完整清单；**触发列**为规则首版建议（可迭代，P3 可覆盖规则漏检）。

| 编码 `anaphora_type` | 中文名 | P0：检索融合 | P1：对话锚块 | P2：槽位建议字段 | P3：LLM JSON 输出 |
|----------------------|--------|:------------:|:------------:|:-----------------:|:-----------------:|
| `none` | 无特殊指代 | 否 | 否 | 仅更新常规摘要（可选） | 可输出，表示规则未命中 |
| `meta_confirm` | 元话语确认/质疑 | **是**（已有「确定吗」类，可并入本编码） | 建议 **是**（强调先复述结论） | `last_topic` + 结论摘要（可选） | 是 |
| `pair_compare` | 双对象对比 | **是** | **是** | `last_bullets`（≥2 条优先） | 是 |
| `ordinal` | 序位/分点指代 | **是** | **是** | `last_bullets` + 可选 `ordinal_hint` | 是 |
| `single_entity` | 单实体回指 | 视长度：**极短+历史非空** 则 **是** | 视置信：**是**（列出最近实体候选） | `last_entities[]` | 是 |
| `ellipsis` | 省略主语/谓语延续 | **是**（短句且缺主话题词） | **是** | `last_topic` | 是 |
| `continuation` | 显式展开/续写 | 可选 **是**（与 ellipsis 可合并判定） | **是** | `last_bullets` | 是 |

**规则触发（首版关键词/模式说明，供 P0/P1 实现对照）**：

| 编码 | 建议规则要点（与 §3 表互补，可正则化） |
|------|----------------------------------------|
| `meta_confirm` | 含：确定吗、您确定、真的吗、靠谱吗、有依据吗、对吗、没错吧、肯定吗；或整句极短且以「吗」「么」「嘛」结尾且历史非空。 |
| `pair_compare` | 含：两者、二者、两个、区别、差异、不同、对比、异同、相比、哪个更、哪一种。 |
| `ordinal` | 含：第 + 数字/中文数、第一点/第二点、前者、后者、上面两点、前一条、后一条、其一、其二。 |
| `single_entity` | 句首或全句为：它、这个、那个、该、此、上述、前面说的；且句长不超过阈值（如 40 字）且历史非空（防误杀长问句）。 |
| `ellipsis` | 极短问句（如不超过 16 字）且含：怎么办、怎么处理、为什么、原因、后果、影响；且不包含完整实体名（启发式）。 |
| `continuation` | 含：详细、展开、继续说、补充、还有吗、再说说、具体点；或「展开 + 第/点」。 |
| `none` | 未命中以上任一；或 `enable_context=false` / 历史为空时一律 `none`（检索不融合、不注锚块）。 |

**各阶段对清单的「使用方式」小结**：

- **P0 使用清单**：仅回答「本轮 query 是否属于某类弱指代」→ 控制 **`build_retrieval_query_for_chatbot` 是否拼接上轮摘要**；可选在 `finished.meta` 增加 `anaphora_type`（需评审是否对外暴露）。  
- **P1 使用清单**：在 P0 命中或扩展命中时 → 控制 **`build_dialogue_anchor_block` 是否生成及模板分支**（如 `pair_compare` 必须列出≥2 条候选）。  
- **P2 使用清单**：assistant 落库后 → 将 **`last_bullets` 等与类型相关字段** 写入会话槽；下一轮 P0/P1 **优先读槽** 再跑规则。  
- **P3 使用清单**：LLM 输出 **`anaphora_type` ∈ 上表编码集合** + `confidence` + `anchor_indices`；仅当规则置信低于阈值时调用，结果回写供 P0/P1 消费或仅打日志。

### 3.3 槽位、对话锚与清单（读者须知，与实现对齐）

1. **槽位（P2）**：**上一轮 assistant 已落库之后**，用规则从该条全文抽取要点数组（如 `last_assistant_bullets`），写入 **`user_id + session_id` 会话维**存储（Redis 优先；无 Redis 为进程内）；**落库钩子内同步写入**，**不是**与 Outline 同形态的「回答后异步摘要任务」。
2. **对话锚（P1）**：**本轮**组装 **system** 时在业务模板与 RAG 之间按需生成的 **「对话锚·仅供推理」** 子块；编号要点 **优先消费槽位 bullets**，否则从 **历史中最近一条 assistant** 再抽；**锚块与槽位不是同一对象**（不把槽位 JSON 整段原样塞进模型）。
3. **指代清单**：yaml 封闭类型 + 规则得到 `anaphora_type`，驱动 **P0 检索融合** 与 **P1 是否生成锚块**；灰区 **P3** 可修正类型。此处「消解」指 **路由、检索与 prompt 约束下的绑定**；**「上文第 N 点」** 另由 **Outline 旁路** 承担，与本节 P0～P3 **并列互补**。

## 4. 分阶段实施方案（P0～P3）

> **与 §3 指代清单的强制约定（防实施遗漏）**  
> - 本文 **§3.1 / §3.2** 为 **唯一指代类型编码与阶段消费表**（`anaphora_type` 封闭集合 + 触发说明）。  
> - **§4.1～§4.4 每条实施任务均须显式对照 §3.2**：实现时不得在阶段内另起类型名；扩展类型须先改 §3.2 再改代码。  
> - **规则关键词、长度阈值、各类型是否启用 P0/P1** 等易变项，建议 **配置化**（见 §4.5），代码中仅保留默认值与加载逻辑。

### 4.5 指代清单配置化（推荐落盘位置）

**是否建议配置化**：**是**。生产上关键词与阶段开关会迭代，硬编码在 Python 中不利于运维灰度与热修。

**与本仓库目录对齐**（当前应用配置与提示词均在 **`configs/`** 下，如 `configs/prompts.yaml`；**项目根下并无统一业务用的 `config/` 目录**）：

| 方案 | 路径建议 | 说明 |
|------|-----------|------|
| **推荐** | `configs/chatbot_anaphora.yaml` | 与 `prompts.yaml` 同级，便于运维与 Git 审查；内容含：`types[]`（`code` / `display_name` / `keywords[]` / `regex[]`）、`p0_retrieval_fusion` / `p1_anchor_block` 布尔、`thresholds`（句长等）、**`p3`：窄触发 `τ`/`δ`、需消歧类型列表、`coref_cache_ttl_sec`**、`schema_version`。 |
| 可选 | 环境变量覆盖 | 与现有 `CHATBOT_*` 一致：总开关、路径覆盖 `CHATBOT_ANAPHORA_CONFIG_PATH`；适合容器挂载外置 yaml。 |
| 不推荐 | 新建根目录 `config/` 仅服务本特性 | 与现有 `configs/` 分裂，增加加载路径与文档心智负担；若组织规范强制根 `config/`，可用 **符号链接** 或 CI 拷贝到 `configs/` 再加载。 |

**加载约定**：启动或首次使用时由 `PromptTemplateRegistry` 同类加载器或独立 `AnaphoraConfigLoader` 解析 YAML → 内存不可变对象；校验 **§3.2 编码全集** 与文件内 `types[].code` 一致，否则启动失败（fail-fast，避免半套清单）。

### 4.1 P0：指代触发检测 + 检索 Query 融合（优先）

**目标**：对「弱可独立语义」的短句，统一将 **检索 query** 与 **会话尾部 user+assistant 摘要** 融合，减少向量检索飘移；与现有 `build_retrieval_query_for_chatbot` 扩展对齐。

**指代清单（§3.2）在本阶段必须落地**

| 要求 | 说明 |
|------|------|
| 检测输出 | 规则或融合函数须能输出 **`anaphora_type`**（§3.2 编码之一或 `none`），即使暂不写入 SSE，也建议在内部 state / 日志中保留，供 P1/P3 对齐。 |
| P0 覆盖类型 | 至少覆盖 **`meta_confirm`、`pair_compare`、`ordinal`**；**`ellipsis` / `continuation` / `single_entity`** 按 §3.2 优先级分期启用（首版可关 `single_entity` 降误杀）。 |
| 与清单列对齐 | **「是否做检索融合」** 严格按 §3.2 表中的 P0 列实现；若配置化（§4.5），以 yaml 中 `p0_retrieval_fusion` 覆盖默认。 |
| 检索调试行 | 融合模板中 **`【指代类型】<code>`** 的 `<code>` 必须为 §3.2 编码，禁止临时字符串。 |

**技术要点**

1. **新建或扩展模块**（建议）：`app/llm/graphs/chatbot_retrieval_query.py`  
   - 在 `is_confirmation_short_query` 旁增加 **`is_anaphora_retrieval_boost_query(query: str) -> bool`**，或合并为 **`should_fuse_history_for_retrieval(query, history) -> bool`**，内部按类型匹配：
     - 对比：`两者|二者|区别|对比|异同|哪个更` 等；
     - 序位：`第[一二三四五六七八九十0-9]+|前者|后者|第一|第二` 等；
     - 单实体短句：`^(它|这个|那个)` + 短长度阈值等（需防误杀，配合历史非空）。
   - **融合格式**：沿用现有「`【检索会话衔接】` + 上轮 user + 上轮 assistant + `【本轮用户原话】`」结构；可增加 **`【指代类型】pair_compare`** 一行供调试（不进用户可见回答）。

2. **调用点**（必须与现有一致）  
   - `ChatbotLangGraphRunner._node_kb_retrieve`：在现有 `rag_query` 计算处合并 P0 新规则。  
   - `ChatbotService._rag_context_and_citations`：Legacy / 非图 `chat()` 路径同样调用统一函数。

3. **配置项**（建议写入 `app/core/config.py` + `app/app-deploy/.env.example`）  
   - `CHATBOT_ANAPHORA_RETRIEVAL_FUSION_ENABLED`（默认 `true`）  
   - `CHATBOT_ANAPHORA_FUSION_MAX_CHARS`（与现有总长上限协调，如 2800）  
   - `CHATBOT_ANAPHORA_CONFIG_PATH`（可选，指向 §4.5 yaml）

4. **测试**  
   - 单元测试：`tests/test_chatbot_retrieval_query.py` 增加「两者区别」「第二点」等用例，断言 `rag_query` 含上轮摘要关键词。

**验收标准**

- 给定固定两轮脚本 + 第三轮短问，**检索 query** 日志中可见融合字段；`rag_citations` 与片段相关性主观抽检优于融合前基线。

### 4.2 P1：对话锚块（Dialogue Anchor Block）注入

**目标**：在 `kb_build_messages`（及 Legacy `_build_llm_messages`）中，当检测到需要锚定时，向 **system** 追加一段 **机器生成的、只读对话摘要块**，显式列出「可比较项 / 最近结论要点」，强制模型先绑定再作答。

**指代清单（§3.2）在本阶段必须落地**

| 要求 | 说明 |
|------|------|
| 触发与类型绑定 | **是否注入锚块**、锚块内**固定引导句分支**（如 `pair_compare` 须提示「默认绑定最近两条要点」）须按 §3.2 **P1 列** 与 `anaphora_type` 枚举分支实现。 |
| 全类型预留 | §3.2 中 P1 为「是」的类型须全部有分支或默认策略；未实现的分支须在配置中 **`p1_anchor_block: false`** 并文档注明「未放量」。 |
| 与 P0 衔接 | 输入 **`anaphora_type`** 优先来自 P0 检测结果；缺失时 P1 可本地复判一次，但输出类型仍须落在 §3.2 编码内。 |

**技术要点**

1. **新模块**（建议）：`app/llm/graphs/chatbot_dialogue_anchor.py`  
   - **`build_dialogue_anchor_block(history_messages, query) -> str | None`**  
     - 输入：与 `load_history` 同源列表（**不含本轮 user**，与现构图一致）。  
     - 输出：无锚需求时返回 `None`；否则返回一段固定格式的 Markdown/纯文本，例如：  
       `【对话锚·仅供推理】上一轮助手回复中可对照的要点（自动抽取）：\n1. ...\n2. ...\n本轮用户问题中的指代默认绑定以上条目（若仅一项则列出该项并说明另一项未识别）。`  
   - **抽取策略 v0（规则）**：  
     - 取最近一条 `role=assistant` 的全文；  
     - 按 `\n\n`、`\n`、编号 `^\d+[\.、]`、`- `、`* ` 切分候选行；  
     - 过滤过短行；合并为最多 **K 条**（如 K=6），首条过长截断。  
   - **抽取策略 v1（可选）**：对 assistant 文本做一次 **短 LLM**（`json`：`bullets: string[]`），超时则回退 v0。

2. **注入位置**  
   - 与 `format_rag_snippets_system_block` 同层：先模板 `system_prompt`，再 **对话锚块**（若有），再 RAG 块。  
   - 避免与用户可见产品文案混淆：块标题含 **「仅供推理」**，且不要求前端展示。

3. **触发条件**（与 P0 检测结果及 §3.2 对齐）  
   - 当 **`anaphora_type`** 属于 §3.2 表中 **P1 列为「是」** 的类型，且 `history_messages` 非空时注入锚块（默认含 `pair_compare`、`ordinal` 及配置开启的 `ellipsis` / `continuation` / `single_entity` / `meta_confirm`；以 §4.5 yaml 为准）。

4. **风险与缓解**  
   - **误抽取**：块内加一句「若与本轮用户语义不符，以用户明确命名实体为准」。  
   - **Prompt 膨胀**：`CHATBOT_ANCHOR_BLOCK_MAX_CHARS`（如 1200）+ 条数上限。

**验收标准**

- 固定脚本「助手答两点 → 用户问两者区别」：回复中须先出现对两项的 **复述或编号对应**（可用自动化 judge 或人工抽检清单）。

---

### 4.3 P2：会话级结构化槽位（Structured Dialogue State）

**目标**：在 Redis/内存会话维度维护 **可指代对象列表**，在 assistant 落库后更新；下一轮指代 **优先读槽** 再拼锚块/检索，提高稳定性与可解释性。

**指代清单（§3.2）在本阶段必须落地**

| 要求 | 说明 |
|------|------|
| 槽位与编码对齐 | 持久化字段 **`last_anaphora_type`**（可选）取值必须为 §3.2 **编码**；`last_bullets` / `last_entities` 与 §3.2 表中 **P2 列** 描述一致。 |
| 读写策略 | 下一轮进入 P0/P1 前 **先读槽**；规则检测的 `anaphora_type` 可与槽位交叉校验（不一致时以槽位 bullets 优先或打监控）。 |
| schema 版本 | 槽位 JSON 带 **`schema_version`**，与 §4.5 yaml 中版本独立演进，迁移脚本须对照 §3.2 是否增删类型。 |

**技术要点**

1. **数据模型**（示例 JSON，存 `conv:anaphora:{user_id}:{session_id}` 或并入现有 meta Hash）  
   - `topic`: 可选字符串  
   - `last_assistant_bullets`: `string[]`（最多 N）  
   - `last_entities`: `{ "label": str, "source": "user|assistant" }[]`（可选）  
   - `updated_at`: epoch  
   - `schema_version`: int（便于迁移）

2. **写入时机**  
   - `ChatbotLangGraphRunner._persist_success` / Legacy 落库 assistant 之后，调用 **`update_anaphora_slots(user_id, session_id, assistant_text)`**（异步队列可选，避免阻塞 SSE 尾帧）。  
   - 实现：规则抽取同 P1 v0，或与 P1 共用函数，仅多一步持久化。

3. **读取时机**  
   - `load_history` 之后或 `kb_build_messages` 前：读取槽位；若槽位与本轮检测类型一致，**锚块优先用槽位 bullets**（比纯文本 re-parse 稳）。

4. **一致性**  
   - 多 worker：必须 Redis；内存模式文档声明「槽位不跨进程」。  
   - TTL：与会话 TTL 对齐，避免幽灵键。

5. **配置**  
   - `CHATBOT_ANAPHORA_SLOTS_ENABLED`  
   - `CHATBOT_ANAPHORA_SLOTS_MAX_BULLETS`

**验收标准**

- 长 assistant 回复后，槽位条数与人工标注要点一致性抽检达标率 ≥ 目标阈值；指代轮次 **澄清率** 下降。

---

### 4.4 P3：小模型 Coref JSON + 评测门禁

**目标**：对规则与槽位均 **低置信** 的 utterance，调用 **一次轻量 LLM**（低 `max_tokens`、结构化 JSON），输出指代类型与建议绑定；并建立 **回归评测集** 防止迭代回退。

**本版（首批落地）实现范围**：**① 窄触发**、**③ 短时缓存** 必须写入设计与代码；**② 与主回答「思考」流并行** 仅作演进方向，**本版不实施**，在下方单独标注「后期再考虑」及原因。

**指代清单（§3.2）在本阶段必须落地**

| 要求 | 说明 |
|------|------|
| JSON Schema | 输出字段 **`type`**（或 `anaphora_type`）必须为 §3.2 编码的 **封闭 enum**；不得输出表外字符串，否则校验失败并降级。 |
| 评测用例 | `tests/fixtures/...` 中每条用例须标注 **期望 `anaphora_type`**（§3.2），CI 断言规则路径或（夜间）LLM 路径与标注一致。 |
| 与 P0/P1 回写 | LLM 输出仅在通过校验后参与检索/锚块覆盖；日志须带 **清单编码** 便于与 §3.2 对账。 |

#### 4.4.1 本版必做①：窄触发（大部分请求不调 P3）

**原则**：P3 **不得**作为每轮前置必经步骤；仅当规则层判断为 **灰区** 时才调用 Coref LLM，以降低延迟与成本。

**建议触发条件（可配置化进 §4.5 yaml，代码默认值与之一致）**：

| 条件编号 | 条件说明 | 备注 |
|----------|----------|------|
| T1 | `CHATBOT_ANAPHORA_LLM_GATE_ENABLED=true` | 总开关；`false` 时整轮不调 P3 |
| T2 | `rules_confidence < τ`（如 τ=0.72，可配） | 规则分类器输出置信度不足 |
| T3 | **指代类型模糊**：规则输出 Top2 类型分差 `< δ`（如 δ=0.08） | 避免「像两者又像序位」等摇摆 |
| T4 | 本轮 `anaphora_type` ∈ **需消歧清单**（配置列表，如 `single_entity`、`ellipsis` 等高风险类）且 T2 或 T3 成立 | 可按业务收紧/放宽 |
| T5 | `enable_context=true` 且历史非空 | 无上下文则不调 P3（无输入意义） |

**合成逻辑（示例）**：`T1 AND T5 AND (T2 OR T3 OR (T4 AND (T2 OR T3)))`，最终以 yaml 布尔表达式或代码注释固定，避免实施时口径漂移。

**降级**：任一前置校验失败、或 P3 超时、或 JSON 非法 → **不调用** 或 **丢弃结果**，回退纯 P0/P1 路径；主链路不得失败。

#### 4.4.2 本版必做③：Coref 结果短时缓存

**目标**：同一会话、**语义相近**的连续追问（如连发「真的吗？」「你确定？」）避免重复打 P3。

**缓存键（建议）**：

- `key = f"{user_id}:{session_id}:{hash(normalize(query))}:{hash(assistant_tail)}"`  
  - `normalize(query)`：去空白、统一全半角、小写（按需）  
  - `assistant_tail`：上一轮 assistant **末段截断**（如后 800 字 hash），防止同会话换话题后误命中

**值**：校验后的 Coref JSON（或仅 `type` + `anchor_indices` + `confidence`）。

**存储**：优先 **Redis**（TTL 与多 worker 一致）；无 Redis 时进程内 LRU（文档声明多 worker **不共享**）。

**TTL 建议**：60～300s（可配 `CHATBOT_ANAPHORA_COREF_CACHE_TTL_SEC`）；**本轮 assistant 落库成功后** 使该 `session_id` 下与旧 `assistant_tail` 相关的条目 **主动失效**（或依赖 TTL 自然过期）。

**监控**：`anaphora_coref_cache_hit_total` / `miss_total`。

#### 4.4.3 后期再考虑②：主回答「思考」流式 + 与 Coref 并行

**状态**：**本版不实施**；保留为后续架构选项，需在 **独立设计评审** 后再立项。

**原设想**：主回答开启思考并流式展示；后台并行跑 Coref JSON LLM。

**暂不纳入本版的原因（摘要）**：

- 若 Coref 结果须 **写入本轮** `messages`（检索融合、对话锚、system 约束），则主模型在 Coref 完成前 **无法**以「已消歧的完整输入」开始推理；**与主模型同源「思考」token 真并行** 会与「本轮语义依赖 Coref」冲突（详见前文「并行与依赖」分析）。  
- 若 Coref **不参与**本轮 prompt，仅并行写缓存，则与 **本版 P3 目标**（灰区消歧写回本轮）不一致。  
- 若「思考」仅为 **非主模型的占位 SSE**，则属于产品/协议扩展，需单独定义事件类型与前端契约，超出本方案 P3 首版范围。

**后期若立项需单列**：协议设计（`reasoning` vs `delta`）、是否允许投机双跑、作废策略与 SLA。

**技术要点（与 4.4.1～4.4.3 并列的通用项）**

1. **契约**（示例）  
   - 输入：`last_user`、`last_assistant`（截断）、`current_query`。  
   - 输出 JSON：`{ "type": "...", "confidence": 0-1, "anchor_indices": [0,1], "rationale_zh": "..." }`  
   - 校验失败 → 回退 P0/P1 规则路径。

2. **调用策略（与 4.4.1 一致）**  
   - 满足窄触发条件且未命中 **4.4.2 缓存** 时调用；命中缓存则跳过 LLM、直接使用缓存对象（仍须做 schema 校验）。  
   - 超时、429、内容审核失败 → 降级无 P3。

3. **评测集**（`tests/fixtures/chatbot_anaphora_cases.yaml` 或独立目录）  
   - 每类指代 ≥10 条三轮对话脚本；  
   - CI：可选 **非 LLM** 断言（锚块是否生成、检索 query 是否融合）+ 周期性 **LLM-as-judge**（夜间任务）。

4. **观测**  
   - Metrics：`anaphora_llm_calls_total`（应远低于总会话量）、`anaphora_llm_fallback_total`、`anaphora_coref_cache_hit_total`、延迟直方图。

**验收标准**

- 灰区 case 人工盲评：指代正确率提升；**P3 调用占比** 在配置目标以下（如低于全量请求的 5%，可调）；P99 延迟在预算内；缓存命中率可观测。

## 6. 发布与灰度（企业级）

1. **特性开关**：P0～P2 各自独立开关，默认 P0 on、P1/P2 off，便于 A/B。  
2. **灰度维度**：按 `user_id` 哈希尾号或请求头 `X-Chatbot-Anaphora-Mode`（内网）放量。  
3. **回滚**：开关关闭即回退当前行为；槽位失败不影响主回答。  
4. **监控告警**：融合率、锚块生成率、LLM 门控失败率、平均 prompt tokens 上升阈值。

---

## 7. 安全与合规

- 锚块与槽位仅服务 **当次会话技术推理**，不在对外 API 中单独暴露为产品字段（除非产品明确要求「可解释性面板」）。  
- 日志中避免完整长文；仅记录类型、长度、哈希 id。  
- 跨租户：键必须带 `user_id` + `session_id`，防止串会话。
