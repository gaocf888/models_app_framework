# 吉泰部署运维方案（核心源码编译交付）

> **读者**：吉泰现场实施、交付负责人、值班运维。  
> **范围**：在结项在线栈（应用 + vLLM + EasySearch + Redis + MinIO + 可选 MinerU）上，对 **`app/` 业务 Python 做 `.so` 编译交付**，使客户宿主机与容器内均无业务明文源码。  
> **通用装机与五条业务验收**：仍以 [整体部署运维手册.md](./整体部署运维手册.md) 为准。本文只写「编译镜像」相对现网源码挂载/源码 COPY 的增量。  
> **源码地图（内部）**：[源码移交说明.md](./源码移交说明.md)。吉泰客户包 **不交** `app/` 下除 `app-deploy/` 以外的 Python。

**状态**：本方案为交付口径与实现策略。仓库中现有 `docker-mx/`、`docker-nvidia/` **保持不变**（内部排障、源码构建）。吉泰现场使用待新增的：

- `app/app-deploy/docker-mx-compiled/`
- `app/app-deploy/docker-nvidia-compiled/`

## 0. 目标与验收口径

| 目标 | 口径 |
|------|------|
| 客户磁盘 | 构建完成后删除 `app/` 中除 `app/app-deploy/` 以外的业务代码；不留 `.git` 与源码压缩包 |
| 容器内 | `models-app` 中业务逻辑以 **`.so`（Nuitka）** 存在，`docker exec` 后 **`cat` 不到业务明文 `.py`** |
| 客户仍可改 | `app/app-deploy/`（compose、`.env`）、`configs/`（Prompt / 业务 YAML）、`vllm-deploy/`、`rag_db-deploy/`、`mineru-deploy/` |
| 不承诺 | 无法从 `.so`、内存、镜像历史层 **逆向还原** 逻辑。有宿主机 root + Docker 的人仍可能做二进制分析 |

**验收检查（构建并删源码之后）：**

```bash
# 宿主机：业务 .py 应不存在（保留 app-deploy）
find app -name '*.py' ! -path 'app/app-deploy/*' | wc -l    # 期望 0

# 容器：业务明文 .py 应不存在（允许极薄 __init__.py / 编译失败白名单，见 §2.4）
docker exec models-app find /workspace/app -name '*.py' \
  ! -path '/workspace/app/app-deploy/*' | grep -v '__init__.py' || true

# 服务可用
curl -s "http://127.0.0.1:${APP_PORT:-8083}/health/"
```

## 1. 交付形态：什么变、什么不变

### 1.1 目录树（现场首次仍整包上传）

与结项包一致，**不改变路径结构**：

```text
models_app_framework/
  app/
    app-deploy/                 # 交给客户；含明文 compose / .env
      docker-mx/                # 内部源码构建（吉泰现场不用）
      docker-nvidia/            # 内部源码构建（吉泰现场不用）
      docker-mx-compiled/       # 吉泰沐曦：新增
      docker-nvidia-compiled/   # 吉泰英伟达：新增
    api/ llm/ services/ ...     # 仅构建期存在，完成后从宿主机删除
  configs/                      # 明文；bind-mount 进容器
  vllm-deploy/                  # 不变
  rag_db-deploy/                # 不变
  mineru-deploy/                # 不变
  requirements-大模型应用.txt
  deploy-docs/
```

### 1.2 两套 compiled 与现网对照

| 环境 | 现网（源码进镜像） | 吉泰（编译进镜像） |
|------|-------------------|-------------------|
| 沐曦 | `docker-mx/` + `Dockerfile-mx` + `docker-compose-mx.yml` | `docker-mx-compiled/` |
| 英伟达 | `docker-nvidia/` + `Dockerfile-nvidia` + `docker-compose-nvidia.yml` | `docker-nvidia-compiled/` |
| 应用解释器 | 沐曦：`/opt/conda/bin/python`（3.12）；英伟达：镜像 `python:3.11-slim` | **必须与对应现网 Dockerfile 同一解释器编 `.so`** |
| 启动命令 | 沐曦 `python -m uvicorn app.main:app`；英伟达 `uvicorn app.main:app` | 与现网同一条，勿混用 |

vLLM / EasySearch / MinerU 的 compose **不改**。应用 `.env` 业务变量、网络名、数据盘路径与《整体部署运维手册》第 5～6 节相同。

### 1.3 挂载原则（compiled 与源码版的唯一差异）

| 路径 | 是否挂进 `models-app` | 说明 |
|------|----------------------|------|
| `configs/` → `/workspace/configs` | **必须** | Prompt、厂级 YAML；客户改文案不重打镜像 |
| `app/app-deploy/` → 容器 | **不要作为运行依赖** | compose / `.env` 只在**宿主机**使用；容器内 uvicorn 不 import 该目录 |
| 整棵 `app/` → `/workspace/app` | **禁止** | 会盖掉镜像里的 `.so`；删源码后服务必挂 |
| 数据 / 模型 / 日志 | 与现网相同 | Redis、MinIO、FAISS、嵌入/重排、insightface 子目录等，见 [项目容器本地挂载和备份说明.md](./项目容器本地挂载和备份说明.md) |
| insightface | 可继续挂 `/workspace/app/small_models/pretrained/insightface` | **子目录**挂载，不会替换同包其它 `.so` |

## 2. 编译与构建改造（实现策略）

### 2.1 总体策略

1. **现网 Dockerfile 不改**，避免影响内部源码排障。
2. compiled 目录各提供：`Dockerfile`（**多阶段**）+ `docker-compose-*.yml`（`image`/`build` 指向 compiled Dockerfile，**增加 configs 挂载**，**不挂整棵 app/**）。
3. 构建在**目标现场同款 GPU 镜像**内完成（沐曦必须在 Metax conda 3.12 里编；英伟达必须在 cu121 + CPython 3.11 里编）。跨机拷 `.so` 会因 ABI 无法 import。
4. 编译范围：`app/` 下在线业务包 → `.so`。不编译：`app/app-deploy/`、`configs/`、以及不应进入在线镜像的 `app/train/`、`app/test_scripts/` 等。

推荐工具：**Nuitka `--module --nofollow-imports`**（完整 CPython 语法，大文件如 `analysis_graph_runner.py` 一并编译，不按体积跳过）。个别文件编不过时列入白名单，保留尽量薄的 `.py`，并在交付记录中列清单。不要用「只生成 `.pyc`」或「单阶段 COPY 后再 `rm *.py`」——前者易反编译，后者源码留在镜像层。Nuitka 比 Cython 慢，实验室全量构建可能数小时。

### 2.2 多阶段 Dockerfile（两条线结构相同）

**Builder 阶段（含源码，不对外）：**

1. 基座与现网一致：沐曦 `vllm-metax:...-py312-...`；英伟达 `python:3.11-slim-bookworm` + CUDA PyTorch。
2. 安装 `requirements-大模型应用.txt`，以及 `nuitka`（及 `ordered-set`、`zstandard`）、编译器（沐曦 yum `gcc/gcc-c++/make`；英伟达 apt `build-essential`）。不安装 `requirements-人脸识别-CPU.txt`（吉泰 compiled 不需要人脸识别）。
3. `COPY` 业务 `app/`（构建脚本排除 `app-deploy`、`train`、`test_scripts`）和 `configs/`（编译期若有测试可 COPY，**最终阶段 configs 以挂载为准**）。
4. 在**与运行相同的解释器**下执行编译（沐曦必须 `/opt/conda/bin/python`）。
5. 删除业务 `.py`（按白名单保留），保留 `.so`、空 `__init__.py`（若需要）、以及 json/yaml 等非 Python 资源。

**Runtime 阶段（交付镜像）：**

1. 同一基座 + 同一 pip 依赖（**不再 COPY 源码树**）。
2. 仅 `COPY --from=builder` 编译后的 `/workspace/app`。
3. **不要**把 builder 的整个 `/workspace` 或源码目录拷进最终层。
4. `WORKDIR /workspace`，`PYTHONPATH=/workspace`，入口与现网一致。

构建结束后在实施机执行 `docker builder prune`，避免 BuildKit 缓存里残留源码。

### 2.3 建议的 compiled 目录内容

```text
app/app-deploy/compiled-common/          # 两条线共用 Nuitka 入口（Dockerfile COPY 到 /tmp）
  compile_app.sh
  compile_app.py
  compile_keep_py.txt                    # 预置跳过编译的 app/ 相对路径

app/app-deploy/docker-mx-compiled/
  Dockerfile                             # 多阶段，FROM 与 docker-mx/Dockerfile-mx 相同
  docker-compose-mx-compiled.yml         # 挂 configs/，禁止挂整棵 app/
  compile_app.sh                         # 转调 compiled-common

app/app-deploy/docker-nvidia-compiled/
  Dockerfile
  docker-compose-nvidia-compiled.yml
  compile_app.sh
```

构建上下文仍是仓库根。Docker 只读取上下文根的 `.dockerignore`，故 **不在仓库根加排除 `app/train` 的 dockerignore**（以免改变现网 `COPY app`）。排除目录由 `compile_app.py` 在 builder 内删除。

Compose 要点（相对现网）：

- `build.context` 仍为**仓库根**（与现网相同，才能 `COPY requirements-*.txt`）。
- `build.dockerfile` 改为 compiled 路径。
- `models-app` **增加**：`${CONFIGS_HOST_PATH:-../../../configs}:/workspace/configs:ro`（路径按 compose 文件所在目录换算到仓库 `configs/`；若需现场改 Prompt 可去掉 `:ro`）。
- **删除/禁止**任何 `.../app:/workspace/app` 整目录 bind。
- 其余 Redis/MinIO/模型/数据卷、external 网络、`env_file: .env` 与现网对应文件对齐。
- `.env` 策略不变：改 `app/app-deploy/.env` 后 `cp` 到 compiled 子目录再 `up`。

### 2.4 编译范围与白名单

**应编译（在线核心）：** `app/api`、`app/llm`、`app/services`、`app/rag`、`app/nl2sql`、`app/auth`、`app/core`、`app/conversation`、`app/inspection_extract`、`app/analysis_agent` 等现网实际 import 的包。

**禁止编译 / 禁止打进在线镜像：**

| 路径 | 原因 |
|------|------|
| `app/app-deploy/` | 交付明文；宿主机编排 |
| `app/train/`、`app/test_scripts/`、`app/manage_scripts/` | 非现网运行时，体积大、易编失败 |
| `app/data_query_agent/`、`app/observability/` | 现网 `app.main` 启动链不 import |
| `configs/` | 明文挂载 |
| 权重、pretrained 二进制 | 挂载或 COPY 原样 |

**允许残留的明文：**

- `__init__.py`：Nuitka 不能把该文件当模块编译（须指定包目录）；按文件出 `.so` 时必须保留它们作为包标记。顶层 `app/__init__.py` 含 Nuitka loader 与 Python 3.12 importlib 的兼容补丁。
- `app/main.py`：uvicorn 入口，明文保留（Nuitka 编成 `main.so` 后 loader 缺 `__name__`，进程会在 import 阶段退出）。
- LangGraph 编排（`compile_keep_py.txt`）：`analysis_graph_runner.py`、`analysis_img_diag_runner.py`、`chatbot_graph_runner.py`、`img_diag_scope_graph.py`、`analysis_agent/graph/*`、`inspection_extract_v0/graph/pipeline.py` 等。Nuitka `.so` 上执行 `StateGraph.compile()` 会在 import 阶段占满 CPU 且迟迟不 listen。
- 小于 `COMPILE_MIN_BYTES`（默认 2KB）的薄模块：防护收益低、Nuitka 启动税高，默认留明文。
- Nuitka 编不过、且已评审的短文件（记录在交付清单）。
- 业务包内的 `.json` / `.yaml` / `.sql`（非源码，必须进镜像或改到 `configs/`）。

**实现时必须回归：**

- `import app.main` 与 `uvicorn app.main:app`（沐曦用 conda 解释器）。
- 使用 `__file__` 拼 `configs/` 的模块（如 `app/graph/paths.py`、`app/llm/graphs` 下若干文件）：`.so` 的 `__file__` 一般仍在同目录，但要以真实 `/workspace/configs` 挂载做一次 Prompt 加载验证。
- 五条业务各打通一条主路径（客服流式、检修、超温 NL2SQL、看图缺陷/泄爆），见手册第 7 节。

### 2.5 内部先打通、再上吉泰机

不要第一次在客户机上试全量 Nuitka。顺序：

1. 用与现场相同的基础镜像在实验室编过 `app.main` + 客服一条流式。
2. 再扩到检修 / 超温 / 看图。
3. 固化 `compile_app.sh` 排除列表与白名单。
4. 吉泰现场只执行「整包上传 → compiled compose build → 验收 → 删源码」。

## 3. 部署策略

### 3.1 首次部署（我方现场）

与现网相同的前置：Docker Compose V2、`vm.max_map_count`、GPU 驱动 / 沐曦或 NVIDIA Container Toolkit。组件顺序仍是：

**EasySearch → vLLM →（可选）MinerU → 应用 compiled 栈。**

前三步命令与《整体部署运维手册》第 4.1～4.3 节相同，**不要**改成 compiled。

应用栈按卡型二选一（**不要**再对 `docker-mx/` 或 `docker-nvidia/` 执行 `--build` 作为吉泰交付产物）。

**沐曦：**

```bash
cd app/app-deploy
cp .env.example .env
# 按手册第 5 节改 LLM / RAG / DB / SERVICE_API_KEYS / 网络名
cp .env docker-mx-compiled/.env
cd docker-mx-compiled
docker compose --env-file .env -f docker-compose-mx-compiled.yml up -d --build
```

**英伟达：**

```bash
cd app/app-deploy
cp .env.example .env
cp .env docker-nvidia-compiled/.env
cd docker-nvidia-compiled
docker compose --env-file .env -f docker-compose-nvidia-compiled.yml up -d --build
```

vLLM 侧仍按卡型 overlay：

```bash
cd vllm-deploy/docker
# 英伟达
docker compose --env-file ../.env -f docker-compose.yml -f docker-compose.nvidia.yml up -d --build
# 沐曦
# docker compose --env-file ../.env -f docker-compose.yml -f docker-compose.mthreads.yml up -d --build
```

`LLM_DEFAULT_MODEL` 必须与 `vllm-deploy/config/models.yaml` 的 `served_model_name` 一致。

### 3.2 构建成功后的「去源码」步骤（必须按序）

在 **health 通过、五条业务抽检通过** 之后执行，不要先删再测。

1. 记录镜像 tag / Image ID：`docker images | grep models-app`（或 compose 项目实际镜像名）。
2. 建议 `docker save` 一份到实施 U 盘/内网盘，作为该现场基线，避免日后误 `--build`。
3. 删除宿主机业务源码，**保留** `app/app-deploy/`：

```bash
# 在仓库根执行；先确认当前不在误删 app-deploy
# 示例：删除 app 下除 app-deploy 外的目录（实施时用明确清单，勿盲目 rm -rf app）
```

4. 删除 `.git`、源码 `tar.gz` / zip、家目录与 `/tmp` 残留。
5. `docker builder prune -af`（确认无其它构建任务后）。
6. 再跑一遍 §0 的 find / health 检查。

### 3.3 构建之后现场磁盘应留下什么

| 保留 | 删除 |
|------|------|
| `app/app-deploy/`（含 compiled compose、`.env`、日志目录） | `app/api`、`app/llm`、`app/services`、`app/rag` 等业务包 |
| `configs/` | `.git` |
| `vllm-deploy/`、`rag_db-deploy/`、`mineru-deploy/` | 构建用源码压缩包 |
| 数据盘、模型权重（`/aidata/...`） | Docker 构建缓存中的源码层（prune） |
| 已构建的 `models-app` 镜像 | — |

### 3.4 严禁事项

- 构建后对 compiled compose 再执行 **`up --build`**：此时上下文 `COPY app` 只剩 `app-deploy`，会打出空心镜像。
- 把宿主机 `app/` 挂到 `/workspace/app`。
- 用英伟达编的 `.so` 跑沐曦容器（或相反）。
- 吉泰交付误用未编译的 `docker-mx/` / `docker-nvidia/` 并留下整棵 `app/`。

日常启动改为：

```bash
# 已有镜像，不再 --build
cd app/app-deploy/docker-mx-compiled          # 或 docker-nvidia-compiled
docker compose --env-file .env -f docker-compose-mx-compiled.yml up -d
```

## 4. 运维策略

### 4.1 角色分工

| 事项 | 客户可做 | 需我方 |
|------|----------|--------|
| 改端口、密钥、TTL、表白名单、模型名 | `.env` + 重启容器 | — |
| 改客服/检修/超温 Prompt | 改 `configs/`，重启或确认进程会重载 | 若代码写死模板再发新镜像 |
| 换 vLLM 预设 / 权重 | `vllm-deploy` | 应用 `LLM_DEFAULT_MODEL` 对齐 |
| EasySearch 密码、数据盘 | `rag_db-deploy/.env` | 应用 `RAG_ES_PASSWORD` 同步 |
| 接口、Graph、鉴权、RAG 代码缺陷 | — | **新 compiled 镜像**（实验室编译 → 现场 `docker load` 或短时带源码构建后再删） |
| `docker exec` 读业务 `.py` | 应读不到明文 | 排障靠日志 + 环境变量，不在客户机解开 `.so` |

### 4.2 日常操作

与手册相同：`docker compose logs`、`/health/`、vLLM `/health`、EasySearch `_cluster/health`。

差异：

- **不要**在客户机改业务 `.py` 后热挂载。
- 应用日志仍挂 `app/app-deploy/logs` → `/workspace/logs`。
- 配置类问题先查 `.env` 与 `configs/`，再查 vLLM `MODEL_PRESET`，最后才怀疑镜像内逻辑。

### 4.3 升级应用（无源码现场）

1. 我方在实验室用**同一卡型 compiled Dockerfile** 出新镜像。
2. `docker save` / 内网仓库 → 现场 `docker load`。
3. 改 compose 的 `image:` tag（若固定 tag 则 load 覆盖后 `up -d --force-recreate`）。
4. **仍不要** `--build`。

若必须在现场编译：短暂恢复业务源码 → compiled `--build` → 验收 → 再次执行 §3.2 去源码。

### 4.4 备份与回滚

数据备份范围与 [项目容器本地挂载和备份说明.md](./项目容器本地挂载和备份说明.md) 相同（ES、Redis、MinIO、会话、检修任务、FAISS）。

**额外必备：** 该现场的 `models-app` 镜像 tar（或仓库 digest）。没有这份镜像，客户机在删除源码后 **无法重建应用容器**。

回滚：停应用 → `docker load` 旧镜像 → `up -d`（无 `--build`）→ 数据盘按手册还原。

### 4.5 排障（无源码）

| 现象 | 先查 |
|------|------|
| 503 业务路由 | `SERVICE_API_KEYS` |
| 连不上 vLLM / ES | 容器名、**容器内端口**、external 网络 |
| Prompt 不生效 | 宿主机 `configs/` 是否挂到 `/workspace/configs`；是否改错文件 |
| `ModuleNotFoundError: app` | 是否误挂整棵 `app/`；是否误 `--build` 覆盖镜像 |
| `undefined symbol` / 无法 import `.so` | 镜像不是本机卡型/Python 编的；或混用了 mx 与 nvidia compiled |
| 思考模式 / 模型名 | vLLM 日志 `default_chat_template_kwargs`、`LLM_DEFAULT_MODEL` |

容器内允许：看 `/workspace/configs`、环境变量、`pip show`、GPU 是否可见。不允许也不需要：在客户机反编译 `.so`。

### 4.6 权限建议

交付说明中写清：客户运维使用 `compose up/down/logs` 与改 `.env`/`configs/`。非必要不开放随意 `docker exec` 进 `models-app` 做交互式 Python。这不能替代编译，只能降低「直接抄文件」的便利性。
