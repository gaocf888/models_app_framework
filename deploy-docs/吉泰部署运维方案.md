# 吉泰部署运维方案（`app/services` 部分编译交付）

> **读者**：吉泰现场实施、交付负责人、值班运维。  
> **范围**：在结项在线栈（应用 + vLLM + EasySearch + Redis + MinIO + 可选 MinerU）上，对 **`app/services` 做 Nuitka `.so` 编译**，其余业务包仍为源码；现场 **bind-mount 整棵 `app/` + `configs/`**。  
> **通用装机与五条业务验收**：仍以 [整体部署运维手册.md](./整体部署运维手册.md) 为准。上线命令以 [app/app-deploy/README-simple-deploy.md](../app/app-deploy/README-simple-deploy.md) §1.1 / §3.2.1 为准。  
> **源码地图（内部）**：[源码移交说明.md](./源码移交说明.md)。

**状态（当前吉泰采用）**：`app/services/` 部分源码编译 + 全量挂载。仓库中现网 `docker-mx/`、`docker-nvidia/` **保持不变**（内部排障）。整包 `app/` 编进镜像的 `compiled-common/docker-*-compiled/` **并存、不要混用**，不是吉泰现场入口。

吉泰现场使用：

- `app/app-deploy/compiled-common-part/docker-nvidia/`
- `app/app-deploy/compiled-common-part/docker-mx/`

交付前编译入口：`app/app-deploy/compiled-common-part/compile.sh`（实验室执行，现场不再编译）。

## 0. 目标与验收口径

| 目标 | 口径 |
|------|------|
| 客户磁盘 | `app/services/` 以 **`.so` + `__init__.py`** 为主（白名单可留少量 `.py`）；`app/api`、`app/llm`、`app/main.py` 等其余包仍为明文；`configs/` 明文 |
| 容器内 | 与宿主机同一棵树：compose **挂载** `app/` → `/workspace/app`、`configs/` → `/workspace/configs`。镜像 **不 `COPY` 业务源码** |
| 客户仍可改 | `app/app-deploy/`（compose、`.env`）、`configs/`、未编译的 `.py`（改完重启 `models-app`）；**不要**改已编成 `.so` 的 services 逻辑 |
| 不承诺 | 无法从 `app/services` 的 `.so` **逆向还原** 逻辑 |

**验收检查（实验室编完、现场拉起之后）：**

```bash
# 宿主机：services 业务明文应很少（允许 __init__.py / 白名单）
find app/services -name '*.py' ! -name '__init__.py' | wc -l

# 容器内与宿主机一致（因为挂载）
docker exec models-app find /workspace/app/services -name '*.so' | head
curl -s "http://127.0.0.1:${APP_PORT:-8083}/health/"
```

编译报告：`app/services/.compile_report.txt`、失败保留项 `.compile_whitelist.txt`。

## 1. 交付形态：什么变、什么不变

应用栈三种方式对照见 `README-simple-deploy.md` §1.1。吉泰只用下表第三列。

### 1.1 目录树

```text
models_app_framework/
  app/
    app-deploy/
      docker-mx/ / docker-nvidia/     # 完全源码部署（内部；吉泰现场不用）
      compiled-common/                # 整包 app/ 编译进镜像（备用；吉泰现场不用）
      compiled-common-part/           # 当前吉泰
        compile.sh / compile_services.py / compile_keep_py.txt
        docker-nvidia/                # 运行 Dockerfile + compose（现场）
        docker-mx/
    services/                         # 交付树中以 .so 为主
    api/ llm/ ...                     # 仍为源码，随 app/ 一并挂载
  configs/                            # 明文；bind-mount
  vllm-deploy/ / rag_db-deploy/ / mineru-deploy/
```

### 1.2 与现网对照

| 环境 | 现网（完全源码，`COPY` 进镜像） | **当前吉泰（部分编译 + 挂载）** |
|------|-------------------------------|--------------------------------|
| 沐曦 | `docker-mx/` + `Dockerfile-mx` | `compiled-common-part/docker-mx/` |
| 英伟达 | `docker-nvidia/` + `Dockerfile-nvidia` | `compiled-common-part/docker-nvidia/` |
| 应用解释器 | 沐曦 conda 3.12；英伟达 CPython 3.11 | **必须用同一解释器编 `app/services` 的 `.so`** |
| 启动命令 | 沐曦 `python -m uvicorn app.main:app`；英伟达 `uvicorn app.main:app` | 与现网同一条，勿混用 |
| 业务代码进容器 | Dockerfile `COPY app` + `configs` | **不 COPY**；挂载 `app/` + `configs/` |
| 运行镜像 | 构建时打进源码 | **现场 `up --build` 才打**（基座 + pip）；实验室编译镜像不用于部署 |

vLLM / EasySearch / MinerU 的 compose **不改**。应用 `.env` 业务变量、网络名、数据盘路径与《整体部署运维手册》第 5～6 节相同。

### 1.3 挂载原则（与整包 compiled 相反）

| 路径 | 是否挂进 `models-app` | 说明 |
|------|----------------------|------|
| 整棵 `app/` → `/workspace/app` | **必须** | 含已编 `.so` 的 `services/` 与其余明文包 |
| `configs/` → `/workspace/configs` | **必须** | Prompt、厂级 YAML |
| `app/app-deploy/` → 容器 | **不要作为运行依赖** | compose / `.env` 只在宿主机使用 |
| 数据 / 模型 / 日志 | 与现网相同 | 见 [项目容器本地挂载和备份说明.md](./项目容器本地挂载和备份说明.md) |

**不要**用 `compiled-common/docker-*-compiled/` 起吉泰：那套 **禁止** 挂 `app/`，会与本口径冲突。

## 2. 编译（交付前，实验室）

### 2.1 总体策略

1. **现网 `docker-mx/` / `docker-nvidia/` 不改。**
2. 只编 **`app/services`**。`app/api`、`app/llm`、`app/main.py`、LangGraph runner 等在 services 之外，保持明文（挂载后可改、重启生效）。
3. 必须在 **与运行相同的 Docker 基座解释器** 里编：沐曦 Metax conda 3.12；英伟达 `python:3.11-slim` + cu121。不要用宿主机 / Windows Python。跨卡型拷 `.so` 会因 ABI 无法 import。
4. `compile.sh` **只打** `models-app-*-part-compile`，编完删除对应 `.py`。**不打**运行镜像。
5. 工具：Nuitka `--module --nofollow-imports`。失败项留 `.py` 并写入 `.compile_whitelist.txt`。

### 2.2 目录与文件

```text
app/app-deploy/compiled-common-part/
  compile.sh / compile_services.py / compile_keep_py.txt
  docker-nvidia/   docker-mx/
    Dockerfile                 # 运行镜像：无 COPY app/configs
    docker-compose-*.yml       # 现场；挂 app/ + configs/
    Dockerfile.compile         # 仅实验室
    docker-compose.compile.yml # 仅实验室；现场不用
```

运行镜像名：`models-app-nvidia-part` / `models-app-mx-part`。编译镜像：`*-part-compile`（**不要交给客户去 run**）。

本栈 compose 的 `env_file` 与现网相同，为子目录 **`.env`**（从上级 `app/app-deploy/.env` 复制）。

### 2.3 编译范围

**应编译：** `app/services/**/*.py`（跳过 `__init__.py`、路径含 `_bak_` / `备份` 的文件、`compile_keep_py.txt` 列出的相对路径）。

**不编译（随 `app/` 挂载、保持明文）：** `app/api`、`app/llm`、`app/rag`、`app/main.py`、`app/app-deploy/`、`configs/` 等。

### 2.4 实验室命令

```bash
cd app/app-deploy/compiled-common-part
chmod +x compile.sh
sed -i 's/\r$//' compile.sh    # 若报 /bin/sh^M
./compile.sh nvidia            # 沐曦现场须用 mx 另编一套
```

看 `app/services/.compile_report.txt`。编完再打包给客户；**现场不再跑 `compile.sh`**。

## 3. 部署策略

### 3.1 首次部署（我方现场）

前置与现网相同：Docker Compose V2、`vm.max_map_count`、GPU 驱动 / Container Toolkit。顺序：

**EasySearch → vLLM →（可选）MinerU → 应用 `compiled-common-part` 栈。**

前三步命令与《整体部署运维手册》第 4.1～4.3 节相同。

应用栈按卡型二选一（**不要**对 `docker-mx/`、`docker-nvidia/` 或 `compiled-common/docker-*-compiled/` 做吉泰交付 `up`）。

**英伟达：**

```bash
cd app/app-deploy
cp .env.example .env
# 按手册第 5 节改 LLM / RAG / DB / SERVICE_API_KEYS / 网络名
cp .env compiled-common-part/docker-nvidia/.env
cd compiled-common-part/docker-nvidia
docker compose --env-file .env -f docker-compose-nvidia.yml up -d --build
```

**沐曦：**

```bash
cd app/app-deploy
cp .env.example .env
cp .env compiled-common-part/docker-mx/.env
cd compiled-common-part/docker-mx
docker compose --env-file .env -f docker-compose-mx.yml up -d --build
```

`--build` 此时打的是**运行镜像**（基座 + pip），不含业务 COPY，**允许、且首次必须**。

vLLM 仍按卡型 overlay（手册 4.2）。`LLM_DEFAULT_MODEL` 必须与 `vllm-deploy/config/models.yaml` 的 `served_model_name` 一致。

### 3.2 现场磁盘应留下什么

| 保留 | 不要做 |
|------|--------|
| 整棵 `app/`（其中 `services/` 已是 `.so`） | **不要**删 `app/api` 等——容器靠挂载跑 |
| `configs/`、`app/app-deploy/` | **不要**用整包 compiled 的「删光业务 `.py`」步骤 |
| `vllm-deploy/`、`rag_db-deploy/`、`mineru-deploy/` | 不要把 `*-part-compile` 镜像当运行镜像 |
| 数据盘、模型权重 | 不要用英伟达编的 `.so` 跑沐曦（或相反） |

### 3.3 严禁事项

- 吉泰现场误用 `docker-mx/` / `docker-nvidia/`（会 `COPY` 源码进镜像）或 `compiled-common/docker-*-compiled/`（不挂 `app/`）。
- 现场再跑 `compile.sh`（没有 `services` 明文会空编/失败）。
- 混用沐曦 / 英伟达 `.so`。
- 把 `APP_HOST_PATH` 指到空目录或未含 `.so` 的树。

日常启动（已有运行镜像时可省略 `--build`）：

```bash
cd app/app-deploy/compiled-common-part/docker-nvidia   # 或 docker-mx
docker compose --env-file .env -f docker-compose-nvidia.yml up -d
```

## 4. 运维策略

### 4.1 角色分工

| 事项 | 客户可做 | 需我方 |
|------|----------|--------|
| 改端口、密钥、TTL、表白名单、模型名 | `.env` → 再 `cp` 到 compose 子目录 `.env` + 重启 | — |
| 改客服/检修/超温 Prompt | 改 `configs/`，重启或确认重载 | — |
| 改未编译的 `.py`（如 `app/api`、`app/llm`） | 改宿主机文件后重启 `models-app` | 复杂缺陷仍建议我方发版 |
| 改 `app/services` 逻辑 | — | 实验室重新 `./compile.sh`，替换交付树中的 `.so` |
| 换 vLLM 预设 / EasySearch 密码 | 与手册相同 | 应用侧变量对齐 |

### 4.2 日常操作

与手册相同：`docker compose logs`、`/health/`、vLLM `/health`、EasySearch `_cluster/health`。

差异：

- 必须在 `compiled-common-part/docker-nvidia/`（或 `docker-mx/`）下操作，并 `--env-file .env`。
- 应用日志仍挂 `app/app-deploy/logs` → `/workspace/logs`。
- 配置类问题先查子目录 `.env` 与 `configs/`，再查 vLLM。

### 4.3 升级应用

1. **只改 services：** 实验室 `./compile.sh` → 同步 `app/services/*.so` 到现场挂载目录 → `restart models-app`（一般不必重打运行镜像）。
2. **改基座 / pip / Dockerfile：** 现场对该 compose 再 `up -d --build`（镜像仍无业务 COPY，安全）。
3. **不要**对吉泰机执行整包 `compiled-common` 的 `--build`。

### 4.4 备份与回滚

数据备份范围与 [项目容器本地挂载和备份说明.md](./项目容器本地挂载和备份说明.md) 相同。

**额外：** 保留该现场的 `app/` 树（含 `services` `.so`）以及运行镜像 `models-app-*-part`。回滚：停应用 → 还原 `app/` 与数据盘 → `up -d`。

### 4.5 排障

| 现象 | 先查 |
|------|------|
| 503 业务路由 | `SERVICE_API_KEYS` 是否进了 compose 子目录 **`.env`** |
| 连不上 vLLM / ES | 容器名、容器内端口、external 网络 |
| Prompt 不生效 | 宿主机 `configs/` 是否挂到 `/workspace/configs` |
| `ModuleNotFoundError: app` | `APP_HOST_PATH` 是否挂到仓库 `app/` |
| `undefined symbol` / 无法 import `.so` | `.so` 不是本机卡型/Python 编的；或混用了 mx 与 nvidia |
| 思考模式 / 模型名 | vLLM 日志、`LLM_DEFAULT_MODEL` |

容器内允许看 `/workspace/app`、`/workspace/configs`、环境变量、GPU。不要在客户机反编译 `.so`。
