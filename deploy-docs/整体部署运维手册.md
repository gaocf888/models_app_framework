# 整体部署运维手册（结项移交）

> **读者**：实施、值班、运维。  
> **范围**：结项交付包内的在线栈（应用 + vLLM + EasySearch + Redis + MinIO + 可选 MinerU）。  
> **不包含**：检修 V0 / Paddle 版面侧车、GraphRAG/Neo4j、Prometheus 独立栈、小模型 GPU 通道、人脸 Milvus。  
> **源码地图**：见同目录 [源码移交说明.md](./源码移交说明.md)。

**版本**：对齐 `dev_zajt` 结项结构（2026-09）。

---

## 1. 结项业务线与组件依赖

五条现网业务都走同一套 FastAPI 应用（默认宿主机端口 **8083**），请求头必须带：

```http
Authorization: Bearer <SERVICE_API_KEY>
```

密钥写在 `app/app-deploy/.env` 的 `SERVICE_API_KEYS`（逗号分隔）或 `SERVICE_API_KEY`。未配置时业务路由返回 **503**。

| 业务线 | 主路径 | 还依赖 |
|--------|--------|--------|
| **智能客服（AI 问答）** | 应用 + vLLM + EasySearch + Redis（+ MinIO 若上传图） | 知识库 namespace（厂级知识、可选 NL2SQL 三件套） |
| **检修报告结构化解析** | 应用 + vLLM + MinIO | 扫描件 PDF 时还要 **MinerU** 与共享 IO 目录 |
| **超温分析（综合分析）** | 应用 + vLLM + EasySearch + Redis + **业务 MySQL** | NL2SQL 知识（`nl2sql_schema` / `nl2sql_biz_knowledge` / `nl2sql_qa_examples`） |
| **缺陷识别（看图诊断）** | 同上 + MinIO（必传现场图） | 视觉多模态模型；台账 HITL 可能多轮确认 |
| **泄爆分析（看图诊断）** | 同上；图片可选 | 事故锚点向前约 3 天取数 |

公共依赖关系：

```
EasySearch（RAG / 会话冷层）
    ↓
vLLM（大模型 / 多模态）
    ↓
MinerU（仅扫描 PDF 检修解析时）
    ↓
应用栈：Redis + MinIO + models-app
    ↘ 业务 MySQL（超温 / 看图诊断 / 客服内嵌查数）
```

## 2. 交付目录与容器

| 组件 | 目录 | 容器名 | 是否必需 |
|------|------|--------|----------|
| 大模型推理 | `vllm-deploy/` | `vllm-service` | **是** |
| 向量 + 全文 | `rag_db-deploy/` | `rag-easysearch` | **是** |
| 应用 API | `app/app-deploy/` | `models-app` | **是** |
| 会话 / 队列 | 应用 compose 内 | `models-app-redis` | **是** |
| 对象存储 | 应用 compose 内 | `models-app-minio` | **是**（检修上传、看图、客服配图） |
| 扫描 PDF | `mineru-deploy/` | `mineru-api` | 检修解析扫描件时 **是** |

Docker 网络（名称须与各 `.env` 一致，`docker network ls` 可核对）：

| 变量（应用 `.env`） | 默认名 | 对端 |
|---------------------|--------|------|
| `VLLM_DOCKER_NETWORK` | `docker_vllm-network` | `vllm-service` |
| `RAG_DOCKER_NETWORK` | `ai-stack` | `rag-easysearch` |
| `MINERU_DOCKER_NETWORK` | `mineru-stack` | `mineru-api` |

**端口两套口径（必读）**

- **容器互访**：用服务名 + **容器内端口**。例如 `http://vllm-service:8000/v1`、`https://rag-easysearch:9200`、`http://models-app-minio:9000`。  
- **宿主机 curl / 浏览器**：用映射口。EasySearch 若 `.env` 中 `EASYSEARCH_PORT=9500`，探活是 `https://127.0.0.1:9500`，**不要**把应用里的 `RAG_ES_HOSTS` 改成 `:9500`。

## 3. 环境前置

- Docker Engine + Compose V2。
- Linux 生产机；内存按「应用 + ES + vLLM」合计规划（27B 级模型建议远大于 32GB，以实测为准）。
- **EasySearch**：宿主机 `vm.max_map_count` ≥ 262144：

```bash
sysctl -w vm.max_map_count=262144
echo 'vm.max_map_count=262144' | tee /etc/sysctl.d/99-easysearch.conf
sysctl --system
sysctl vm.max_map_count
```

- **GPU**  
  - 英伟达：驱动 + NVIDIA Container Toolkit；应用用 `app/app-deploy/docker-nvidia/`，vLLM 用 compose overlay `docker-compose.nvidia.yml`。  
  - 沐曦：厂商运行时；应用用 `docker-mx/`，vLLM 用 `docker-compose.mthreads.yml`。  
  **一台机器只选一条主路径**，不要两套应用栈同时占用同一组容器名（`models-app`、`models-app-minio` 等）。

- 宿主机已存在模型与数据目录（示例，以现网 `.env` 为准）：嵌入/重排、vLLM 权重、`EASYSEARCH_DATA`、Redis/MinIO 数据盘。

## 4. 分步部署

顺序：**EasySearch → vLLM →（需要扫描件时）MinerU → 应用栈**。  
未部署 MinerU 时，先执行 `docker network create mineru-stack`，否则应用 compose 会因 external 网络不存在而失败。

### 4.1 EasySearch

```bash
cd rag_db-deploy
cp .env.example .env
# 修改 EASYSEARCH_PASSWORD、EASYSEARCH_DATA、EASYSEARCH_PORT（宿主机 9200 被占用则改为 9500 等）
docker compose --env-file ".env" -f "docker-compose.easysearch.yml" up -d
```

容器内改 admin 密码、初始化说明见 `rag_db-deploy/README.md`。  
健康检查（**宿主机端口**与 `EASYSEARCH_PORT` 一致）：

```bash
curl -k -u admin:<密码> "https://127.0.0.1:9200/_cluster/health?pretty"
# 若 EASYSEARCH_PORT=9500：
curl -k -u admin:<密码> "https://127.0.0.1:9500/_cluster/health?pretty"
```

期望 `status` 为 `yellow` 或 `green`。若日志出现 `vm.max_map_count too low`，先做第 3 节内核参数，再 `docker compose ... up -d`。

### 4.2 vLLM（Docker Compose，不用 `deploy.sh`）

`.env` 放在 **`vllm-deploy/` 根目录**。在 `docker/` 下执行 compose 时必须带 `--env-file ../.env`，否则 `BASE_IMAGE`、`MODEL_PRESET` 等不会生效。

```bash
cd vllm-deploy
cp .env.example .env
```

按显卡改 `.env`（示例）：

```env
# 英伟达
BASE_IMAGE=nvidia/cuda:12.3.0-runtime-ubuntu22.04
VLLM_REQUIREMENTS_PROFILE=full
CUDA_VISIBLE_DEVICES=0,1
GPU_DEVICE_COUNT=all
MODEL_PRESET=qwen3.6-27b
TENSOR_PARALLEL_SIZE=2
VLLM_PORT=8000
MODEL_PATH=/aidata/models/llm

# 沐曦则改为：
# BASE_IMAGE=cr.metax-tech.com/public-ai-release/maca/vllm-metax:0.17.0-maca.ai3.5.3.307-torch2.8-py312-kylinv11-amd64
# VLLM_REQUIREMENTS_PROFILE=extras
# MX_VISIBLE_DEVICES=0,1
```

启动前确认 `docker/docker-compose.yml` 里 `build.dockerfile` 与平台一致：英伟达用 `docker/Dockerfile-nvidia`，沐曦用 `docker/Dockerfile-mx`。

```bash
cd vllm-deploy/docker
# 英伟达：基座 compose + nvidia overlay
docker compose --env-file ../.env -f docker-compose.yml -f docker-compose.nvidia.yml up -d --build

# 沐曦：
# docker compose --env-file ../.env -f docker-compose.yml -f docker-compose.mthreads.yml up -d --build
```

`MODEL_PRESET` 必须在 `vllm-deploy/config/models.yaml` 中存在，且其中 `served_model_name` 与应用 `LLM_DEFAULT_MODEL` **完全一致**。  
`VLLM_PORT` 为宿主机映射口（常为 8000；冲突可改），**容器内仍是 8000**，应用侧继续写 `http://vllm-service:8000/v1`。

```bash
curl -s "http://127.0.0.1:${VLLM_PORT:-8000}/health"
```

看日志：

```bash
cd vllm-deploy/docker
docker compose --env-file ../.env -f docker-compose.yml -f docker-compose.nvidia.yml logs -f vllm
```

### 4.3 MinerU（检修扫描 PDF 时）

```bash
cd mineru-deploy
cp .env.example .env
# 必改 MINERU_MODELS_HOST_PATH、MINERU_IO_HOST_PATH
# MINERU_IO_HOST_PATH 必须与应用 .env 中同名变量指向同一宿主机目录
docker network create mineru-stack || true
docker compose --env-file .env -f docker-compose.cpu.yml up -d
# GPU 机可用 docker-compose.gpu.yml，见 mineru-deploy/README.md
```

应用侧：`MINERU_ENABLED=true`，`MINERU_BASE_URL=http://mineru-api:8000`（**不要**写成宿主机映射口）。

### 4.4 应用栈

```bash
cd app/app-deploy
cp .env.example .env
# 按第 5 节改完后再启动
```

**英伟达（结项现网常见）：**

```bash
cp .env docker-nvidia/.env
cd docker-nvidia
docker compose --env-file .env -f docker-compose-nvidia.yml up -d --build
```

**沐曦：**

```bash
cp .env docker-mx/.env
cd docker-mx
docker compose --env-file .env -f docker-compose-mx.yml up -d --build
```

改完上级 `.env` 后必须再 `cp` 到 `docker-nvidia/` 或 `docker-mx/`，否则 compose 的 `env_file: .env` 读的是子目录那份。

健康检查：

```bash
curl -s "http://127.0.0.1:${APP_PORT:-8083}/health/"
```

期望 `{"status":"ok"}` 一类成功响应。

**端口冲突：** 若报 `Bind for 0.0.0.0:9000 failed: port is already allocated`，在 `.env` 改 `MINIO_PORT`（如 9010）、`MINIO_CONSOLE_PORT`（如 9011），再复制到 `docker-nvidia/.env` 后重新 `up`。  
**不要改** `CHATBOT_IMAGE_MINIO_ENDPOINT=models-app-minio:9000`（那是容器内端口）。

同理 `APP_PORT`、MinIO 控制台 9001 被占用时只改宿主机映射。

## 5. 必改配置（应用 `.env`）

完整键名见 `app/app-deploy/.env.example`。下面只列**不改会起不来或五条业务不可用**的项。

### 5.1 全业务公共

```env
SERVICE_API_KEYS=<接方新生成的密钥，勿沿用示例>
LLM_DEFAULT_ENDPOINT=http://vllm-service:8000/v1
LLM_DEFAULT_MODEL=<与 vLLM served_model_name 一致，如 qwen3.6-27b>
RAG_ES_HOSTS=https://rag-easysearch:9200
RAG_ES_USERNAME=admin
RAG_ES_PASSWORD=<与 rag_db-deploy/.env 相同>
RAG_ES_VERIFY_CERTS=false
REDIS_URL=redis://redis:6379/0
VLLM_DOCKER_NETWORK=docker_vllm-network
RAG_DOCKER_NETWORK=ai-stack
MINERU_DOCKER_NETWORK=mineru-stack
CHATBOT_IMAGE_MINIO_ENDPOINT=models-app-minio:9000
CHATBOT_IMAGE_MINIO_ACCESS_KEY=<与 MINIO_ROOT_USER 一致>
CHATBOT_IMAGE_MINIO_SECRET_KEY=<与 MINIO_ROOT_PASSWORD 一致>
```

离线嵌入/重排（生产建议）：

```env
EMBEDDING_MODEL_PATH=/workspace/models/embeddings/bge-small-zh-v1.5
RAG_RERANKER_MODEL_PATH=/workspace/models/rerank/bge-reranker-base
EMBEDDING_MODELS_HOST_PATH=/aidata/models/embeddings
RERANKER_MODELS_HOST_PATH=/aidata/models/reranker
```

英伟达分卡（vLLM 占 0 号卡、应用重排占 1 号卡的典型写法）：

```env
APP_NVIDIA_VISIBLE_DEVICES=all
RAG_RERANKER_DEVICE=cuda:1
CHATBOT_INTENT_LLM_DEVICE=cuda:1
```

若 `APP_NVIDIA_VISIBLE_DEVICES=1`（容器只看见一张卡），则 `RAG_RERANKER_DEVICE` 必须为 `cuda:0`。

### 5.2 智能客服

```env
CHATBOT_GRAPH_ENABLED=true
CHATBOT_INTENT_ENABLED=true
CHATBOT_INTENT_BACKEND=rules
CHATBOT_PROMPT_DEFAULT_VERSION=boiler_v1
CHATBOT_NL2SQL_ROUTE_ENABLED=true
CHATBOT_PLANT_KB_ENABLED=true
CHATBOT_PLANT_KB_NAMESPACE=Power_plant_knowledge
```

客服要查数时，还需第 5.3 节业务库与 NL2SQL 知识摄入。

### 5.3 超温分析 / 看图诊断（共用业务库）

```env
DB_HOST=host.docker.internal
DB_PORT=3306
DB_USER=...
DB_PASSWORD=...
DB_NAME=...
# 或完整 DB_URL=
ANALYSIS_NL2SQL_TABLE_SCOPE_DEFAULT=<表白名单，库表变更必须同步>
ANALYSIS_SYNTHESIS_STRATEGY_OVERHEAT_GUIDANCE=v2
```

容器内访问宿主机 MySQL 用 `host.docker.internal`。表白名单与 RAG 中 `nl2sql_schema` 必须一起更新。

看图诊断建议确认：

```env
ANALYSIS_IMG_DIAG_VISION_TIMEOUT_SECONDS=300
ANALYSIS_IMG_DIAG_LANE_TIMEOUT_SECONDS=360
ANALYSIS_IMG_DIAG_SCOPE_HITL_ENABLED=true
```

多模态模型首图可能数分钟；超时过短会出现「连接中」后 SSE 被掐断（`httpx.ReadTimeout`）。

Qwen3.6 等 `max_model_len` 较小的模型，超温长章节可能超窗，可将 `ANALYSIS_SYNTHESIS_V2_SEGMENT_MAX_TOKENS` 从 4096 降到 2048（以现网 `.env` 为准）。

### 5.4 检修报告结构化解析

```env
INSPECT_EXTRACT_ENABLED=true
MINERU_ENABLED=true
MINERU_BASE_URL=http://mineru-api:8000
MINERU_IO_HOST_PATH=<与 mineru-deploy 相同的宿主机目录>
```

**不要**为结项去部署 `paddleocr-layout-deploy`，也**不要**把 `INSPECT_EXTRACT_V0_ENABLED` 当作现网主路径。

## 6. 配置分层（改错文件会「改了不生效」）

| 层级 | 谁读 | 改完怎么生效 |
|------|------|----------------|
| Compose 插值 | 宿主机 `docker compose` | 端口、网络名、卷路径。改后需 `up -d`（必要时重建容器） |
| 容器环境变量 | `app/core/config.py` 的 `os.getenv` | `env_file: .env` 整份注入。改业务变量后 **重启 `models-app`** |

应用**不会**自己 `load_dotenv` 读磁盘上的 `.env`。

## 7. 按业务线验收

以下默认应用 `http://127.0.0.1:8083`，密钥为 `$KEY`。先通过 `/health/`。

### 7.1 智能客服（AI 问答）

```bash
curl -N -X POST "http://127.0.0.1:8083/chatbot/chat/stream" \
  -H "Authorization: Bearer $KEY" \
  -H "Content-Type: application/json" \
  -d '{"user_id":"u_handover","session_id":"s_chat_001","query":"你好","enable_rag":true,"enable_context":true}'
```

期望：出现增量 `delta`，尾帧 `finished=true`；启用 RAG 时结束帧 `meta` 可含 `rag_citations`。  
同一 `user_id + session_id` 再问一轮，确认上下文仍在。  
会话列表：`GET /chatbot/sessions?user_id=u_handover`。

配图：先 `POST /chatbot/upload`，把返回 URL 放入 `image_urls`。

### 7.2 检修报告结构化解析

```bash
# 1) 上传（docx/pdf/md/txt；老式 .doc 会 400）
curl -s -X POST "http://127.0.0.1:8083/inspection-extract/upload" \
  -H "Authorization: Bearer $KEY" \
  -F "file=@./sample.docx"

# 2) 同步提取（content 填上一步 url；source_type 按文件类型）
curl -s -X POST "http://127.0.0.1:8083/inspection-extract/run" \
  -H "Authorization: Bearer $KEY" \
  -H "Content-Type: application/json" \
  -d '{"user_id":"u_handover","session_id":"s_insp_001","source_type":"docx","content":"<upload返回的url>"}'
```

期望：`ok=true`，`records` 有结构化条目。扫描 PDF 失败时查 MinerU 容器与 `MINERU_IO_HOST_PATH` 是否与应用共用。  
大文件用 `POST /inspection-extract/run/async`，再 `GET /inspection-extract/jobs/{job_id}`。

### 7.3 超温分析（综合分析）

```bash
curl -N -X POST "http://127.0.0.1:8083/analysis/run-with-nl2sql-stream" \
  -H "Authorization: Bearer $KEY" \
  -H "Content-Type: application/json" \
  -d '{"user_id":"u_handover","session_id":"s_oh_001","analysis_type":"overheat_guidance","query":"请分析1号炉最近超温情况并给出处置建议"}'
```

期望：SSE 依次出现 `started` →（取数阶段可能较久无帧）→ `meta` → `summary_delta` → `finished`。  
`analysis_type` 必须为 `overheat_guidance`。  
完整 JSON 不在流内，用尾帧/`meta` 的 `request_id` 调 `GET /analysis/traces/{request_id}`。

前置：业务库连通、表白名单覆盖超温相关表、NL2SQL 三个 namespace 已摄入。

### 7.4 缺陷识别（看图诊断）

```bash
# 1) 上传现场图
curl -s -X POST "http://127.0.0.1:8083/analysis/img-diag/upload" \
  -H "Authorization: Bearer $KEY" \
  -F "file=@./defect.jpg"

# 2) 流式诊断（image_urls 填上一步 url）
curl -N -X POST "http://127.0.0.1:8083/analysis/run-img-diag-stream" \
  -H "Authorization: Bearer $KEY" \
  -H "Content-Type: application/json" \
  -d '{"user_id":"u_handover","session_id":"s_def_001","query":"请帮我分析图片缺陷","img_diag_subtype":"defect_ident","image_urls":["<upload url>"]}'
```

- `img_diag_subtype=defect_ident` 时 **至少 1 张图**，否则 422。  
- 可能先收到 `img_diag_scope_input_required`（机组/受热面 HITL），用返回的 `resume_token` 调 `POST /analysis/run-img-diag-resume-stream` 确认后续跑。  
- 视觉臂可能数分钟无 SSE，属模型推理慢，不是「没连上」。超时见第 5.3 节。

### 7.5 泄爆分析（看图诊断）

与 7.4 相同接口，仅改：

```json
"img_diag_subtype": "leakage_burst"
```

图片可选。取数窗口为事故锚点向前约 3 天。HITL / resume 流程与缺陷识别相同。

## 9. 日常运维

```bash
# 应用（在 docker-nvidia 或 docker-mx 目录）
docker compose --env-file .env -f docker-compose-nvidia.yml ps
docker compose --env-file .env -f docker-compose-nvidia.yml logs -f models-app
docker compose --env-file .env -f docker-compose-nvidia.yml restart models-app

# vLLM（与启动时相同的 -f 组合）
cd vllm-deploy/docker
docker compose --env-file ../.env -f docker-compose.yml -f docker-compose.nvidia.yml ps
docker compose --env-file ../.env -f docker-compose.yml -f docker-compose.nvidia.yml logs -f vllm
docker compose --env-file ../.env -f docker-compose.yml -f docker-compose.nvidia.yml restart vllm

# EasySearch
cd rag_db-deploy
docker compose --env-file .env -f docker-compose.easysearch.yml logs -f
```

- 只改 LLM/RAG/业务开关：重启 `models-app`。  
- 改端口/卷/网络：`up -d`。  
- 换大模型：改 vLLM `MODEL_PRESET` 并重启 vLLM，同步改应用 `LLM_DEFAULT_MODEL`。  
- **不要**同时启动 CPU `docker-compose.yml` 与 `docker-nvidia`（容器名冲突）。

## 10. 排障速查（按业务线）

通用 5 分钟检查见 [online-services-oncall-runbook.md](./online-services-oncall-runbook.md)。历史坑见 [问题处理清单.md](./问题处理清单.md)。

| 现象 | 先查 |
|------|------|
| 全部业务 503 | `SERVICE_API_KEYS` 是否注入容器 |
| 全部业务连不上模型 | `LLM_DEFAULT_ENDPOINT` 是否为 `vllm-service`；vLLM `/health`；模型名是否一致 |

| 看图一直「连接中」 | 视觉超时；vLLM 看图是否卡住；确认范围后是否重复跑视觉 |
